# Cross-checking the barycentric correction against pulsar-timing codes

How the in-model barycentric correction of `rvinstrument` `data_format: raw_redshift`
(`src/exozippy/components/rvinstrument/redshift.py`) is checked against pulsar-timing
codes, so that anyone can repeat it. None of these codes is an EXOZIPPy dependency;
install them in a throwaway environment.

The roles:

- **PINT is the regression reference.** A small committed table of PINT's `c z_B`
  (`tests/fixtures/raw_redshift/pint_zb.txt`: four sites x three stars x six epochs) is
  regenerated by `tests/fixtures/raw_redshift/make_pint_fixture.py`, whose docstring
  records the exact PINT version (pint-pulsar 1.1.8), the kernel (DE432s), the clock
  (TT(TAI), no BIPM, no observatory clock file) and the IERS tables (astropy's bundled
  ones, auto-download off). `tests/test_raw_redshift.py::
  test_barycentric_redshift_matches_pint_the_regression_reference` compares the model
  with it on the same kernel. Per (site, star) the two differ by a constant -- the
  observatory clock convention, below -- plus at most **0.032 mm/s**; the test's
  tolerance is 0.05 mm/s. That is not the float64 floor (0.0004 mm/s, below): it is the
  two models' genuine differences, so the tolerance sits just above what was measured
  and a 0.02 mm/s regression in any term trips it. The test needs DE432s (10 MB, which
  astropy fetches by name and caches); it is marked `network` and skips, rather than
  falling back to the builtin ephemeris (mm/s away), when the kernel cannot be loaded.
  DE432s and DE440 differ by up to 0.04 mm/s in this correction, so both sides must use
  the same kernel.
- **TEMPO2 (native mode) is the independent cross-check**, run by hand with the scripts
  described below; its numbers are recorded here, not tested.
- **TEMPO (TEMPO1) is history only**: it has no polar-motion model, which is all of its
  0.21 mm/s RMS difference (see the end of this note).

## Results (the model as of PR #565)

Five sites (Keck, Kitt Peak, McDonald, La Palma, Las Campanas) x four stars (Barnard's
star, tau Ceti, alpha Cen A, a Gaia-4-like star) at 640 epochs over 2023-2025 ("long")
and 1835 epochs at 5-min spacing through one night ("dense"), DE440 on every side, per
(site, star) constant removed:

| comparison | long: RMS / max | dense: RMS / max |
|---|---|---|
| this model - PINT | 0.012 / 0.042 mm/s | 0.015 / 0.050 mm/s |
| this model - native TEMPO2 | 0.016 / 0.053 mm/s | 0.018 / 0.078 mm/s |
| PINT - native TEMPO2 | 0.015 / 0.048 mm/s | 0.013 / 0.060 mm/s |

The model agrees with each timing code about as well as the two agree with each other.
The constant removed per (site, star) is the observatory clock term `(GM_E/r +
v_rot^2/2 - W0)/c`: the timing codes count the observer's clock in TT, on the geoid
(potential W0), and this model in the observer's own proper time. It is -0.09 mm/s at
McDonald and -0.21 mm/s at Keck, matches the measured constant (averaged over the stars)
to about 0.01 mm/s at every site, and is absorbed by every instrument zero point
(`src/exozippy/components/rvinstrument/rvinstrument.md`, "Validation").

## Installing the codes

- **TEMPO (TEMPO1) 13.103** (historical; kept so the WE14 comparison can be repeated) (git `13.100-44-gaaf34c4`): build it from the SourceForge git repository
  (`git clone https://git.code.sf.net/p/tempo/tempo`, then `./prepare && ./configure &&
  make`). The build takes about a minute. Make a private runtime directory (`$TEMPO`)
  holding a `tempo.cfg`, the `clock/` tree and an `obsys.dat` with your sites' ITRF XYZ.
  The shipped `ut1.dat` stops in 2021, so regenerate it from an IERS EOP C04 file (for
  example the one TEMPO2 ships). TEMPO1 has no polar-motion model.
- **TEMPO2 and PINT** from conda-forge, into their own environment:
  `conda create -p <scratch>/tempo-env -c conda-forge tempo2 pint-pulsar` (the comparison
  used tempo2 2026.04.1 and pint-pulsar 1.1.8).

## The method

The method is Wright & Eastman (2014) Appendix A's, applied to all three codes. Each
(site, star, UTC epoch) is set up as a "pulsar":

- the star is re-referenced to that day (POSEPOCH = PEPOCH = the day, astrometry
  propagated with `erfa.pmsafe`);
- F0 = 1 Hz, F1 = 0, DM = 0.

The topocentric polyco frequency is then `nu_obs / nu_SSB`, the barycentric correction
with nothing of the star left in it. Re-referencing per day keeps each code inside its
exact regime. The star's secular-acceleration factor is applied afterwards,
analytically.

Native TEMPO2 (not `-tempo1` prediction mode) and PINT use IAU 2006/2000A and polar
motion, as EXOZIPPy does. TEMPO1 and TEMPO2's `-tempo1` polyco mode omit polar motion,
which is the sidereal-day residual Wright & Eastman reported.

## Floating-point floor

A single float64 Julian Date quantizes at ~40 microseconds. That puts a floor of 0.0004
mm/s RMS on any comparison at a ground site, which comes from the Earth's rotational
acceleration. No quad-precision time path is needed at this level.

## TEMPO1: a historical note

Wright & Eastman (2014) validated against TEMPO2 in its `-tempo1` prediction mode, and
TEMPO1 itself was compared here for continuity. Both leave polar motion out of the
observatory's velocity. Against this model the difference is 0.21 mm/s RMS (0.63 max)
with a sidereal-day signature; with polar motion switched off in this model it drops to
0.03 mm/s RMS (0.13 max). Polar motion is real (~0.3 mm/s), so TEMPO1 is no longer a
reference for this correction at the sub-mm/s level.
