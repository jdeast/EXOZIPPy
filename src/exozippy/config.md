# ConfigManager, the relaxation engine, and parameter naming

Everything that resolves a number before any PyMC node exists: `src/exozippy/config.py`
(defaults, hints, overrides, the relaxation engine, the three user-facing spellings of an
element) and `src/exozippy/linking.py` (link expressions in a params file).

Read this before adding a hint or override channel, changing how a config value is
resolved, or touching the parameter naming or link syntax. Related: parameters themselves
are `src/exozippy/components/parameter.md`; the manifest vocabulary is
`src/exozippy/components/components.md`. The ban on writing into
`config_manager.user_params` from a component is one of the invariants kept in full in the
trunk `CLAUDE.md`.

## ConfigManager and the relaxation engine

`src/exozippy/config.py` is the initialization backbone. It:

1. Loads all `defaults.yaml` files (one per component subdirectory) into `base_defaults`.
2. Loads all `symbolic_physics.py` files; calls `get_symbol_map(component_config, system_config)` — both arguments required, the second being the whole parsed config so a builder can reference another component's instances — to translate abstract symbols to indexed paths (`star.0.mass`, `lens.0.t_E`, …) and collects `RELATIONS` (SymPy equations).
3. Manages a **precedence** ladder -- one ordered table deciding which statement about a parameter wins: `config.PRECEDENCE_LADDER`, the ONE place its levels are written (review 3.14.22: every `PRECEDENCE_*` constant is read off it, and a `defaults.yaml` `rank:` NAMES one of its keys, so an ordering can be permuted by editing one dict). Top to bottom:
   - `USER = 100` -- the params file.
   - `DERIVED_USER = 80` -- reported for a value derived from user values only; a component may also push a hint here (a start computed from the user's own numbers, `Star._seed_pm_from_sgra_prior`).
   - `DERIVED_DATA = 60` -- a component's data-derived hint (an RV offset, a peak-finder seed, a galactic-model proper motion).
   - `LIKELIHOOD_BACKED = 55` -- a DECISION level only, never reported: the start of a parameter a stiff likelihood backs (see "Precedence, and which value absorbs a discrepancy" below).
   - `DERIVED_MIXED = 40` -- reported for a value derived from a mix; the level of a standalone solver's answer and of the 3+-body lens seeds.
   - `MULENS_SOURCE_DISTANCE = 30` and `MULENS_LENS_DISTANCE = 25` -- the microlensing distance guesses (~8 kpc bulge source, ~4 kpc lens). Both beat the 10 pc `defaults.yaml` backstop and yield to the user; the lens yields to the source, so a relative parallax the other values imply is absorbed by the LENS distance. Named constants since review 4.6.2.
   - `DEFAULT = 20` -- a `defaults.yaml` value.
   - `DEFAULT_WEAK = 10` -- a `defaults.yaml` value written `rank: DEFAULT_WEAK` (the stellar proper motions, the planet mass and radius): absorbs before any ordinary default.

   **The rename stops at two contract boundaries** (review 3.14.14, 2026-08-27). The ladder's named levels are `PRECEDENCE_*`; they used to be `RANK_*`, which read as a quality score and never was one -- a `defaults.yaml` value is not worse evidence than a user value, it simply loses to it. But the **field** keeps its historical name where a name is published: `rank:` in `defaults.yaml`, and `"rank"` as a wire-format key (`config.py`'s provenance dict, `introspect.py`'s field allowlist, `rank: number | null` in the GUI's `api.ts`). So `add_hint(path, value, rank)` and the local variables carrying that field's value are still spelled `rank`, deliberately. Since review 3.14.22 the VALUE of a `defaults.yaml` `rank:` is a ladder NAME (`rank: DEFAULT_WEAK`); a bare number raises naming the levels (`config.ladder_level`). It is not a params-file key (it is not in `USER_PARAM_KEYS`), so no user file breaks.

   `ConfigManager._provenance_label` collapses a precedence level to the coarse source the startup table, `export_solution` and the GUI report -- "user", "data", "solved", "default". The two data levels are named in the **set** `DATA_PRECEDENCES`, not tested as a numeric band, and that is not a style choice: they do not bracket a contiguous range, since `PRECEDENCE_DERIVED_MIXED` (40) sits between them and `PRECEDENCE_DERIVED_USER` (80) above them and both are SOLVER levels, so the obvious `>= 30 and < PRECEDENCE_USER` test would report every engine-derived value as data-derived. The predicate previously hardcoded the two literals, which failed the other way -- any new intermediate data level silently reported "solved". **A new data level must be added to `DATA_PRECEDENCES` in the same commit that introduces it.** `LIKELIHOOD_BACKED` is deliberately not in it: a backed start reports the rank it came with. Tests: `tests/test_provenance_labels.py`.
4. Runs the **relaxation engine** (`resolve_and_validate_parameters`, which builds the inputs; the rule itself is `src/exozippy/relaxation.py`): it decides every start value from the seeds and the relations, and reports what it could not honor. The rule is the next section's.
5. Carries a preliminary `init_scale` for every engine symbol: DECLARED (defaults.yaml, a component `add_scale_hint`, a user `sigma`) where there is one, else PROPAGATED from the sampled parameters through the relations. These are **preliminary only** (see `src/exozippy/whitening.md`): sampled parameters get their real scale from the startup probe, and soft-bound barrier steepness is measured numerically post-whitening. They are also the unit the engine splits a correction in and judges a relation in. `init_scale` is **not user-facing**: entries in a params file are stripped with a warning at ConfigManager construction. A SAMPLED element with no scale from any of those sources RAISES at build (`Parameter.build_pymc`, review 3.14.22): it used to fall back to a tenth of its bound span, a silent modeling choice wherever the scale is the prior width.

Components push hints via `config_manager.add_hint(path, value, rank)` during stages 1-3. The hint system is the correct way for components to propose data-driven initial guesses; they are layered in after defaults but before the solver runs. It is the **only** correct way for a start value: a plain manifest `"initval"` option is merged as `{**cfg, **options}` *after* `resolve()`, so it never acquires a rank and beats the user's params file outright. `transit.baseline` (the per-file median flux) carried its median that way until 2026-08 and so silently discarded an explicit `transit.<name>.baseline` -- including the EXOFASTv2 solution shipped in `examples/gj1214`, whose start logp is the one shipped example the move to `Transit._hint_baseline` changes. The measurement happens in `load_data` (stage 1) and the hint is pushed in `register_parameters` (stage 3), which is the whole reason the channel is available at all; a non-finite median is skipped with a warning so the defaults.yaml 1.0 (also `load_data`'s own no-data seed) stands. Compare `rvinstrument`'s `gamma` (median RV), `mulensinstrument`'s `f_source`/`log_f_total`/`q_source`, `Instrument._prepare_gp`'s amplitude and the RV semi-amplitude, all of which were already hints. The RV semi-amplitude hint sits on the DERIVED `planet.K`, which is the same statement as the planet's mass (JDE 2026-10-14: K and mass/msini are one quantity), so it must move the mass and nothing else -- never the orbit's default cos i or e/omega, which would start a transit fit face-on.  The tier order does that: the sampled mass coordinate (`planet.mass`, or `planet.msini` under m sin i coordinates) is DEFAULT_WEAK, below every other seed K reads, so it absorbs the hint alone, at the final solve's P, e, sin i and host mass.  Where that cannot hold, `Planet._push_rv_mass_hints` does not push it: a user value on any mass coordinate (or on K) supersedes it (a `unit:`-only entry states no value and supersedes nothing), recorded through `ConfigManager.supersede_hint` and reported in the solve diagnostics as kind "superseded"; a log_q planet beside RVs (DEFAULT log_q) is logged instead.  The rule this generalizes: when a hint and a user value are ONE quantity, the component that knows it lets the higher tier replace the lower, as on one element.

**`resolve()` layers `self.hints` too, UNDER the user's params and OVER defaults and both override channels.** The relaxation engine is not the only reader of a start value: several components ask `resolve()` for one at stage 2/3, before the engine has run at stage 4, and `Orbit` builds `tc`'s HARD window as `tc_init +/- P/2` from what it sees there -- so a seed invisible to `resolve()` does not merely start the chain in the wrong place, it makes the right place unreachable and `Parameter.build_pymc` correctly calls that fatal. Until review 3.14.3 `resolve()` layered `param_overrides` and `scale_hints` but not `hints`, so any component that had to seed a value a stage-3 reader would see was forced to write it through TWO channels -- `add_hint` for the engine, the ledger, `initval_source` and provenance, plus `add_override` for `resolve()` -- and `globalsearch.seed_start` did exactly that, computing one number once and writing it twice. The order is the rule and must not be "simplified": `resolve()` has no ledger to consult, so the position of the loop is the only thing that keeps a component's guess from overwriting a number the user typed, and it is the same ordering the engine enforces (step 1.5's `< PRECEDENCE_USER` guard). Hints touch `initval` and nothing else -- never a bound, a prior or a scale -- and they are read under the same three spellings and the same most-specific-wins traversal (`_lookup_keys`) as every other field, so a broadcast `star.distance` covers every element and `star.0.distance` refines it. They are stored in internal units, so the layering divides by the element's own user -> internal factor (`internal_factor / elem_scaling[i]`), not by the defaults-unit one: a hint on a planet mass the user relabelled `earthMass` is otherwise 318x wrong. Tests: `tests/test_hint_resolution.py`, plus `tests/test_global_search.py`'s stage-2 `tc` window.

Every hint channel -- `add_hint`, `add_scale_hint`, `add_seed_hints`, `seed_start_value` -- turns the component's path into the index form `resolve()` looks up and its number into internal units through the **one** helper `ConfigManager._translate_and_scale`, which in turn defers to `canonical_param_key` for the translation itself. Both halves matter and both fail silently: a hint filed under an untranslated `star.Lens.distance` is never found by `resolve()` (the component's bulge scale vanishes and the generic default stands), and a hint left in the user-facing unit is wrong by whatever the conversion factor is (57x for a deg -> rad angle). `add_scale_hint` carried a line-for-line copy of that body until 2026-08, under a docstring that already claimed the sharing. Cover: `tests/test_config_hint_paths.py`.

**A component states the unit of a number it computed: `add_hint(path, value, unit="m/s")`** (and `add_scale_hint(..., unit=)`). Without `unit=` the value is read in the parameter's resolved USER unit -- a user `unit:` override honored -- which is right for a number taken from the user's own params or from `resolve()`, and wrong for one a component computed in a fixed unit. `RVInstrument`'s gamma start (the file's mean RV, in m/s) and `Planet`'s K start used to be pushed bare, so `rvinstrument.0.gamma: {unit: km/s}` read 12002 m/s as 12002 km/s and started gamma 1000x off (review 1.5.10). With `unit=` the value goes from that unit straight to the parameter's `internal_unit` through `unit_conversion`; a parameter with no `internal_unit` raises, naming both. The stated-unit callers today: rvinstrument gamma, planet K, orbit gammadot/gammaddot, the lens alpha display hint (deg), and `Instrument`'s GP-amplitude and robust `out_scale` starts (`hint_unit`). When the stated unit is the defaults unit the factor is the same `unit_conversion` call as before, so no example without a `unit:` override moves. Test: `tests/test_conversion_rv_units.py`.

**`add_seed_hints` takes ONE seeder per fit: a second registration RAISES** (review 2.1.25, JDE ruling 2026-09-30). Every call names its caller with a required `source=` label (e.g. `peak finder (<prefix>)`), recorded as `seed_hint_source`; a call without `replace=True` while sets are already registered raises `ValueError` naming both the existing and the new caller. `replace=True` is the explicit override -- the existing sets are discarded (what `peak_find: true` asks for; with the peak finder the only seeder in the tree since the MMEXOFAST hand-off was removed, 2026-10-01, no live call replaces anything). History, because each step looked right: it ASSIGNED until review 2.1.12, so a second seeder silently discarded the first (the built-in peak finder run after MMEXOFAST replaced every MMEXOFAST solution, binary-lens s/q/alpha included, with one point-lens set); 2.1.12 made it APPEND, but seed `k` combines the user's per-seed `initval: [a, b, c]` element `k` with component set `k`, and every list must be length K or 1 -- so a K summed over two unrelated seeders (MMEXOFAST 2 + peak finder 1 = 3) is a number the user cannot know, breaking the rule that per-seed lists are applied as one set. Nothing needs two seeders today; if a real case appears, the upgrade is to PAIR set `k` with set `k` (raising on a length mismatch or a disagreement on a shared path), never to concatenate. Sets are never deduplicated: a caller that pushes the same file twice has a bookkeeping bug to fix at its source (MulensEvent's stage-3 re-push of an explicit MMEXOFAST file was deleted for exactly that, review 1.6.15). Seed hints are invisible to `user_params` and to `probe_derivable` (`probe_start` sees seed 0), so "has something already seeded this?" is asked of `seed_hint_sets` / `seeded_paths()`. Cover: `tests/test_peakfind.py`, `tests/test_probe_derivable.py`.

Manifest options that carry a **structural** value -- a shape, an `expr_key`, a `table_note`, a `force_node`, a `mask`, an `inactive_value` -- are not start values and stay options. A bound a component derives from the config to select one branch of a degeneracy (`Orbit`'s one-period `tc` window, `cosi`'s half-plane `lower`) is structural in purpose but numeric in kind, and it used to be a bare option too -- which silently REPLACED a user's own `tc`/`cosi` bound (`tc: {lower: T0 - 0.3, upper: T0 + 0.3}` built its transform on `T0 +/- P/2`; review 1.8.17). Both are now options with a gap (below).

**Which channel a component-imposed number takes -- the rule.** A component never writes `user_params`, and a number it imposes on a field the user can also write (`initval`, `lower`, `upper`, `mu`, `sigma`) goes through exactly one of three channels, chosen by what the user must be able to do with it:

- a **start** -> `add_hint` (ranked, under the user; never a bound or a prior);
- a **validity limit** (past it the likelihood is NaN or infinite, or the model is outside its domain), a pin of an unread element, or a component prior/start the user may replace -> `"overrides"` (layered under the user; bounds CLIP, so the user may tighten but not loosen, and `resolve` warns when it clips);
- a **modelling default bound** the user must be able to tighten OR loosen -> an option **with a gap** (`user_wrote_field` + NaN).

A **bare** numeric option on one of those five fields is never right for an element the user can write: it replaces the user's value with no message. The converse misuse is quieter but real: a preference sent through `"overrides"` cannot be loosened by the user (it clips, with a warning). The audit that followed review 1.8.17 checked every component against this rule; its open findings are in the review doc.

What used to head that list, and no longer does, is the `ybigomega >= 0` BOUND: `_restrict_bigomega_halfplane` truncated the ascending node to one half-plane to select one branch of an exact degeneracy, and a hard truncation biases a posterior that hugs the boundary (review 1.8.3; measured on `examples/HIP1349`, `Omega = 176.5 +/- 2.7` against DMSA's `172.6 +/- 3.4` with zero origin-crossings in 16k draws). The bound is gone -- the two modes are antipodal in the sampled direction vector and a line through the origin joins them with no likelihood barrier -- and the branch is now selected AFTER sampling, by a fold applied once where the draws are decoded (`src/exozippy/components/orbit/orbit.md`). The seed that points the direction vector at the user's `bigomega` is still a structural option; the bound that excluded half the plane was not a structural value at all but a modeling choice, and it is now made where it can be undone.

Manifest entries take an `"overrides"` dict (`{field: value_or_per_element_list}`, forwarded to `resolve(internal_overrides=...)`) for component-computed per-element **defaults**. Unlike the manifest's other options, which are merged *over* the resolved config and so beat the user's params file, these are layered *under* it — use them whenever the user must still be able to override. `NaN` in a per-element list means "leave this element alone"; `±inf` is a real bound and is applied. `apply_value` special-cases the two bound keys as `max(lower)` / `min(upper)`, and the user's own params go through that same function, so a bound supplied through `"overrides"` combines as `max(user_lower, component_floor)` **order-independently**. That is what makes `"overrides"` the right channel for a component-imposed floor (see the IMF floor in `src/exozippy/components/star/star.md`, `Instrument._register_noise`'s jitter-variance floor, and `MulensInstrument`'s `neighbor_fraction` on its physical `[0, 1]`, review 2.1.26(b), `tests/test_neighbor_flux.py`) and `"options"` the wrong one: options would replace -- and so silently *lower* -- a bound the user had tightened. Because the combination is a clip, a component bound may still beat the user's; reserve bound overrides for **validity** limits (past which the likelihood is NaN or infinite), not for preferences, and note that `resolve` logs a warning naming the parameter whenever an override bound clips a user's.

A component bound that is a **modelling default** -- one the user must be able to tighten *or loosen* -- fits neither channel as they stand: `"overrides"` clips, and a bare option replaces the user's value. The shape that works is an **option with a gap**: the component asks `Component.user_wrote_field(param, field)` (read-only on `user_params`, the three spellings) which elements the user bounded, writes the derived value on the others and `NaN` on those, and `Component.layer_options` -- the one place `{**cfg, **options}` is formed -- keeps the resolved value wherever a per-element NUMERIC option says NaN, the same "leave this element alone" the overrides channel has always had. The live cases are `Instrument._register_robust`'s hogg `out_scale` cap of 10x the median error (review 8.6.3, `src/exozippy/components/instrument.md`), `Star`'s lifted `loggsed` barrier on unread stars, and `Orbit`'s `tc`/`tc_sampled` window and `cosi` half-plane (review 1.8.17; `tests/test_tc_user_bounds.py`); a scalar option, a list with no NaN, or a non-numeric option are untouched, so no existing manifest option changed meaning. Tests: `tests/test_robust_cap.py` (both directions, end to end).

`ConfigManager.add_override(path, **fields)` is the same `"overrides"` channel reached **by path**, for a component that must constrain a parameter another component owns and so has no manifest to hang it on. It takes any of the three spellings `resolve()` accepts (`comp.param` broadcasts to every element), values are in the parameter's defaults.yaml unit, and `resolve()` applies it through the same `apply_value` pass as `internal_overrides`, before the user's params -- so all of the paragraph above holds verbatim, warning included. Its one caller today is `SED._inject_grid_bounds`, whose BC grid coverage bounds `star.teffsed`/`star.loggsed`/`star.feh`/`star.av` -- hard bounds on the three sampled ones, a soft barrier on the derived `loggsed` (see "Bands, filters, and SED flux constraints", now `src/exozippy/components/sed/sed.md`).


`src/exozippy/components/defaults.yaml` (no component key, straight parameter names) holds root-level defaults shared by several components; `resolve()` layers the component's own block over it. Today it carries only the GP blueprint.

## Precedence, and which value absorbs a discrepancy (review 3.14.22)

Start values come from SEEDS -- a user value, a component hint, a `defaults.yaml` value -- and the relations of every component's `symbolic_physics.py` tie them together. When the seeds disagree about a relation, something has to give. The rule that decides what (design "KS", JDE ruling 2026-10-14) is implemented in `src/exozippy/relaxation.py` and has three steps:

1. **WHICH TIER MOVES is decided by provenance, strictly in order.** Seeds are fixed tier by tier from the top of the ladder down. A seed whose symbol the higher tiers already determine is ABSORBED -- re-derived from them -- and a tier's own seeds move only when, with every lower tier still free, the relations cannot otherwise hold. A higher tier is never traded against a lower one, whatever any scale says. **Only SEEDS carry a precedence**: a symbol nobody seeded (`theta_E`, `mu_rel`, a derived mass) has none, so it can never win or lose a tie, and a `defaults.yaml` value on a DERIVED element seeds nothing at all -- it cannot reach the model, so it is only a FILL, giving a value to a symbol nothing else determines. A HINT on a derived element (the RV semi-amplitude, the peak finder's `t_E`) is a seed at its tier: it is information.
2. **USER VALUES ON DERIVED ELEMENTS are kept in order.** A user value on a SAMPLED element is produced exactly. One on a DERIVED element (or an inactive one, or a path that is no parameter of this model) is a CANDIDATE: candidates are taken one at a time, shallowest derivation first -- depth is 1 + the deepest input of the step that derives the value from the sampled seeds -- with ties broken by params-file order (JDE R-a). Each is honored exactly if every relation can still hold with it and every value kept before it, otherwise it is DROPPED: re-derived from what was kept, and reported by name (a `kind: "dropped"` diagnostic, which `ModelAuditor.check_user_starts` words as reason `dropped`, naming the values kept before it). Nothing is ever partially honored. Relations the RIGID user values break among themselves, before any candidate is considered, can be satisfied by no start: they are reported as contradictions (`kind: "contradiction"`, severity error) and take no part in the solve.
3. **HOW MUCH MOVES, inside the one tier that has to absorb, is the minimum-norm displacement in init_scale units** -- a Gauss-Newton step over that tier's new seeds, the Jacobian taken by finite differences through the recorded propagation plan, every satisfied check kept satisfied. A scale only ever splits a correction between seeds of the SAME tier, so a scale that is orders of magnitude wrong (and the preliminary ones can be, JDE 2026-10-06) can mis-split that one tier's correction but cannot move a higher tier, a user value, or anything outside its bounds.

**What a tier cannot absorb inside its bounds ESCALATES to the tiers above it** (review 1.1.11, JDE approved 2026-10-25). When step 3's settle leaves a relation violated -- every seed of the absorbing tier that the relation reads has hit a bound -- the tier's seeds are HELD where its settle left them, and the next tier UP that holds a seed upstream of the violated relation settles the remainder, by the same minimum-norm step, moving only those seeds and keeping every satisfied relation satisfied. If that tier also runs into its bounds, the next one up takes what is left, and so on up to (never including) `USER`. So step 1's order still holds lexicographically: a higher seed moves only by the part the lower tiers provably cannot absorb, and it is never traded against them. A user value is never moved (rigid and kept values are not seeds). If even the highest movable tier cannot close the gap, every escalated move is UNDONE and the relation is reported exactly as before -- a `kind: "unsettled"` warning, "The <tier> starts could not satisfy ... inside their bounds" -- so a start that was never left violated, and one that cannot be repaired, is bit-identical to what it was before escalation existed. A successful escalation is logged at INFO and recorded in the keep report (`_last_keep_report["escalated"]`); the moved seeds report the solved level like any settled seed. Whether a settled seed MOVED is judged in the scale the settle split its correction in, read off the plan the settle started from: a seed on a DERIVED element (a data-seeded `t_E`) has no declared or leaf scale, only the one its relations imply there, and the first escalation that moved one (the 2L1S configs of `tests/test_dc18_arch_config.py`) raised for want of it. A second case: the 2L1S DC2018 architecture config (synthetic event, `log_q` -3) used to leave `mlens_total = M_star + M_planet` violated at `MULENS_LENS_DISTANCE`, whose settle stopped the lens distance at 4005 pc. Now the source distance (30) is tried and does not move, and `DERIVED_DATA` (60) absorbs the rest, by a minimum-norm split among the data-seeded `t_E` (2.32 -> 12.53 d; the synthetic event has 12) and the four galactic-model proper motions (3-5 mas/yr each), with `logmass` almost unmoved (its 0.001 dex scale). The worked case: `examples/DC2018_128` with only the target position and a user `mulensevent.t_E: 17`, and `q` unseeded. At `DEFAULT` the companion's `log_q` (default -3) was driven to its -9 bound, the companion mass being the only absorber of `mlens_total = M_star + M_planet`, which would have had to go negative; the relation used to be left violated and the model started at t_E 42.5 d with a `check_user_starts` miss. Escalation sent the residual to the lens distance at `MULENS_LENS_DISTANCE`, which absorbed to ~6895 pc, and the model started at t_E 17.000 -- with `log_q` held on the bound its DEFAULT settle had left it at. Since review 8.6.42 the companion's mass coordinate is `LIKELIHOOD_BACKED` (below), so `log_q` keeps its -3 default and the lens distance absorbs at its own tier with no escalation at all; the escalation itself is unchanged and still covers any tier that runs into its bounds. (Re-ranking the lens-mass guess instead was measured and rejected: at rank 20 the lens MASS absorbs `theta_E^2 = kappa M pi_rel`, leaving the lens at its 4 kpc guess with a parallax the data reject.) Tests: `tests/test_ks_engine.py` (the escalation toys), `tests/test_peakfind_default.py` (the DC2018_128 case).

**What it replaced, and why each is gone.** The old engine seeded EVERY symbol with its `defaults.yaml` value at a rank, then relaxed: a relation with one unknown was solved for it (Condition A), and a fully known, violated one rewrote its lowest-ranked symbol, ties broken by the alphabetical order of the path (Condition B). A solved value took the minimum of its inputs' ranks, with floors, a Jacobian refinement, a satisfied-equation promotion (8.6.22), an oscillation pin and a Contradiction Clause; `defaults.yaml` carried `rank: 5` on eight parameters to steer Condition B. Two consequences were demonstrated (3.14.22): `theta_E` could never absorb a pinned `t_E` because `t` sorts after `p`, and a NEGATIVE companion mass was preferred over moving the host because `planet.0.mass` sorts before `star.0.mass` (DC2018_128 with a lens-mass hint at rank 22: start logp -912820). All of that is deleted; the propagation step (solve a relation for its one unknown, with the custom solvers, the cached `sp.solve`, the nsolve fallback, the in-bounds test and the multi-root scoring of 2.1.15) is kept as the engine's only way to derive a value.

**How the settle is solved, and its degenerate starts.** Gauss-Newton minimum-norm steps through the plan, each residual normalized by its own scale at the CURRENT point, finished by SLSQP on the same problem where the steps stall; first from the anchors and then, if that does not settle, from a start about one scale away in a fixed, unequal direction. The second start exists because two proper motions at the same default make `mu_rel = 0`, where `|mu_rel|` is a kink and `t_E = theta_E/mu_rel` has no finite value -- a gradient there is meaningless (`examples/DC2018_128` with only `t_E` pinned). The minimum norm is always measured from the anchors. The pseudo-inverse is cut at 1e-6 of its largest singular value: a direction the relations barely see is finite-difference noise, and inverting it was measured to throw the four ob09020 proper motions to their 1e5 bounds. A relation that is UNDEFINED at a point (`nan`: `atan2(0, 0)`) states nothing there; one that is INFINITE (a finite pinned `t_E` against `mu_rel = 0`) is violated -- the engine evaluates in numpy scalars so that `x / 0` is an infinity and not an exception. A double root (`|mu_rel| = +-sqrt(0)`) takes the branch that stays in bounds one scale away. **A settle moves, and clips into bounds, only the coordinates some check reaches**; every other seed of the tier keeps its anchor exactly, even one outside its bounds (review 1.6.21). The Gauss-Newton step used to clip the WHOLE movable vector, so any settle at `DEFAULT` parked every out-of-bounds default on its bound and reported it as moved (`DERIVED_MIXED`, "solved"). The case that found it: a `type: static` orbit pairing a DC2018 1L2S event's two sources makes a stage-1 probe settle the orbit's eccentricity alternatives at `DEFAULT` (the role guess below). The source's `t_0` default, 2460000, lies outside the event's window, so it landed on the window's upper edge looking informed, the peak finder held it there, and the build refused the start. A leaf's own bound is not the settle's business. Tests: `tests/test_ks_engine.py` (`test_a_settle_never_moves_a_seed_no_check_sees`), `tests/test_dc18_arch_config.py`.

**A root chosen by order alone waits.** A squared relation (`mu_rel_mag**2 = mu_ra**2 + mu_dec**2`, the `pi_rel`--`|pi_E|` shortcut) gives two roots no evaluable relation can choose between yet. The propagation takes such a step only once nothing unambiguous is left -- a pinned `pi_E_E`, if there is one, then decides `mu_ra` linearly -- and where it must choose, it takes the root nearest the target's own stated value (a dropped user value keeps its sign). Measured on `examples/ob170114` with the source proper motions removed and `t_E`/`pi_E` pinned: the dropped `pi_E_E = +0.127` came back as `-0.127` without this, and the start logp fell from -74626 to -3.1e7.

**The scale of a value** is the declared one where it exists, else the one PROPAGATED from the sampled leaves through the relations (JDE Q5, 2026-10-14) -- else the engine RAISES naming the parameter; no constant is ever substituted. Propagation runs once, from every sampled seed at its anchor, as the root-sum-square of each step's response to moving each input by ITS scale: the Jacobian propagation the engine always did, taken as a secant one scale wide, which is the same to first order and stays defined at a kink (`|mu_rel|` at zero) and through a solver, whose inputs the engine reads off the call. A value the leaves cannot reach at their anchors is propagated the same way along the plan that determined it. A scale propagates only when every input has one: an absent scale is unknown, never `1e-9` (review 2.1.16, which this fixes). A relation is VIOLATED when its residual exceeds `CHANGE_TOL_IN_SCALES` of the residual's own scale (`sqrt(sum_j (dr/dx_j s_j)^2)`); a relation UNDEFINED at the current values (`omega = atan2(sesinw, secosw)` on a circular orbit) states nothing there. Where a symbol needs a scale and has none, the remedy is an `init_scale` in its `defaults.yaml`. (`orbit.m_total`, determined only by the body-mass solver, gets its scale through that solver now that the engine reads a solver's inputs.)

**Standalone solvers are one-way.** A solver registered `standalone=True` (`orbit.m_total` from the body masses, `tc` from a time of periastron, the transit chord from `cos i`, the eclipse-timing eccentricity) is a derivation `target := f(inputs)` no relation can express. Its answer is a value at `PRECEDENCE_DERIVED_MIXED`: it fills its target whenever the target is undetermined, and where the solve left the target held at that level or below (a `defaults.yaml` backstop, a value derived from defaults) it is pinned there and the tiers are solved again, until no solver's answer moves (at most ten rounds, else it raises). It never moves its own inputs and never overrides a data or user value.

**Constants** (`ConfigManager.add_constant`, review 8.6.23): an exact per-run number a relation needs -- the microlensing event's Earth velocity projected at t0_par, which turns the heliocentric relative proper motion into the geocentric one the model's t_E and pi_E are evaluated from. The engine evaluates it like a pinned value but it is never an anchor, a seed or a ledger row, so it can neither absorb nor be reported; a component re-supplies it whenever it changes (MulensEvent at stage 1 once the event's coordinates are read, again after t0_par is final, and at stage 3).

**`PRECEDENCE_LIKELIHOOD_BACKED`** (JDE Q3 / R-b): a component whose likelihood makes a parameter's start expensive to move declares it, `ConfigManager.declare_likelihood_backed(path)` in `register_parameters`, and every seed of that path below the level DECIDES at it -- while REPORTING the rank it came with, so a backed `defaults.yaml` value is still labelled "default" and still not `informed`. The declarations: the evolutionary model's track coordinates (`logmass`/`mass`, `initfeh`, `eep`, `age`), not the outputs it compares (a wrong mass puts the star on the wrong track); the SED's own `teffsed`, which its colors pin, not `radiussed`, which the photometry only measures as R/d; `mann` and `torres` the mass and radius they predict, per `constrain:`; and `MulensEvent` every lens COMPANION's sampled mass coordinate (a planet's `log_q`, or its `mass`/`msini` where the entry asks for those; a stellar companion's `logmass`), because the light curve measures a mass ratio from the caustic, independently of the event's physical scale (review 8.6.42). Without that last one a 2L1S config with `t_E` pinned and `q` unseeded left `log_q` the only `DEFAULT` seed upstream of `theta_E^2 = kappa M_tot pi_rel`: its settle drove it to a bound (q = 10 under the geocentric relations), the escalation then held it there while the higher tiers absorbed the rest, and DC2018 sweep starts lost ~1e6 nats (event 131 did not build at all). Now `q` keeps its seed and the event chain absorbs `t_E` (`tests/test_ks_engine_examples.py`). Its slot is just below `DERIVED_DATA` -- "a data level provenance ... between user and default" (JDE), and below rather than equal to a data hint because a hint is a measurement of the value itself. Worked case (`tests/test_ks_engine_examples.py`): `hat3_mist` with its mass and radius pins replaced by a pinned density, where the radius absorbs and the MIST mass keeps its seed; the old engine moved the mass, alphabetically.

**Roles come from the manifests.** Which elements are sampled, derived or inactive is `System._engine_roles()`, handed to `ConfigManager.set_engine_roles` right before each `finalize_user_params` -- after the solve-input snapshot, so a topology revision's second registration pass runs its stage-3 probes with the roles unknown, exactly as the first did, and the second solve is the same function of its inputs as the first. A stage 1-3 PROBE has no manifest yet; it reads the role off `defaults.yaml` through the component contract (`components.md`): a parameter with an `expressions:` block that lacks any of `lower`, `upper`, `init_scale` can only ever be derived, and anything else is read as sampled. Except for the components that have already declared their manifest: `System._declared_engine_roles` (`ConfigManager.role_provider`) hands those components' real roles to the probe, so the guess stays only for components not yet registered. The guess cannot tell a parameterization's sampled coordinates from its alternatives -- `orbit.vcve`, `secosw`, `sesinw`, the omega unit vector and `chord` all declare bounds and an init_scale -- so it read all of them as sampled, their `defaults.yaml` starts disagreed, and the probe settled them: e = 0.00011 for the default 0.0002 on `examples/kelt4`, and 1.000006 (past an e < 1 no single bound expresses) under the init_scale noise test. Registration order still limits it: the orbit registers after the planet, so a planet probing the orbit at stage 3 still guesses. Test: `tests/test_ks_engine_examples.py`.

**The ladder is one table, so an ordering is one edit.** The ordering sweep JDE asked for (lens/source distances swapped, both above the data level, `DEFAULT_WEAK` merged into `DEFAULT`, the `LIKELIHOOD_BACKED` slot, keep-in-order by file order alone or by reverse depth) was run by editing `PRECEDENCE_LADDER` (and `relaxation.KEEP_ORDER`, whose alternatives exist only for that measurement). The tables are in `docs/ks_engine_measurements.md`.

Tests: `tests/test_ks_engine.py` (the rule on toy relation sets), `tests/test_ks_engine_examples.py` (DC2018_128's negative mass, `hat3_mist`'s density, the lens distance absorbing a pinned `t_E`), `tests/test_fitmsini.py` (msini in both roles), `tests/test_engine_change_tolerance.py`.

## When a re-solved value counts as a change (reviews 1.1.9, 3.14.22)

The change test is `config.value_moved` (`relaxation.value_moved`): a move counts when it is at least `CHANGE_TOL_IN_SCALES` (1e-5) of the symbol's init_scale (JDE ruling 2026-10-06: "the best tolerance should be scaled by init_scale, if present"). It is also the satisfaction test of a relation (above), and so of whether a user value on a derived element holds. The old test was RELATIVE to the value's MAGNITUDE (`|new - old| / max(|new|, |old|) >= 1e-3`), which means nothing for a quantity with an arbitrary zero: ~2460 d on a BJD, so a `tp`-implied `tc` solved anywhere within ~7 yr of the 2460000 backstop was discarded (`examples/ob170114` with its `tc` seed replaced by its `tp`; every such orbit was then refused at build). Its other half -- "a strictly higher-ranked answer always replaces the value" -- needs no function under KS: a higher tier is fixed first and never traded.

**Why 1e-5 and not something nearer 1: the preliminary init_scale is a GUESS and can be orders of magnitude off** (JDE 2026-10-06), and the two directions of error are not symmetric. A scale too SMALL costs at most a needless (and tiny) settle; one too LARGE silently tolerates a real inconsistency -- 1.1.9's own failure. Measured when the scaled test landed (PR #399), probing at the engine start of the 19 shipped examples whose logp is cheap enough: the engine's init_scale over the probe-measured scale, across 392 sampled elements, runs 4.5e-6 to 1.6e4 with median 3.4 and 90th percentile 241; at 1e-5 even the worst guess puts the threshold at ~0.16 of the true scale. The floor is round-off: for tc (init_scale 0.001 d) 1e-5 is 1e-8 d, still ~20 ulps of 2.46e6.

**A symbol with NO init_scale now RAISES** where it is compared, naming it and the `defaults.yaml` to declare one in. The relative fallback 1.1.9 kept for 25 scale-less parameters is gone: where one of them is compared, its scale is propagated through the relations (JDE Q5), and none of the 25 needed a declared value on the shipped examples (`docs/ks_engine_measurements.md`). Three SAMPLED leaves did: `mulensevent.log_pi_rel`, `mulensevent.log_theta_E` and `source.u0te` had a scale only from a stage-3 `add_scale_hint`, which a stage-1 probe runs before; they now declare the same value in `mulensing/defaults.yaml` (DC2018_128's severed-rho configuration raised without it). Tests: `tests/test_engine_change_tolerance.py`, and the in-band tp seed in each omega quadrant in `tests/test_tp_seed.py`.

## Reading a start before stage 4 (`probe_start`)

**A stage 1-3 reader that needs a parameter's START must call `ConfigManager.probe_start(paths)`, not `resolve()` and not raw `user_params`,** whenever that start can be IMPLIED by the user's entries rather than written for the path itself. `resolve()` and `user_params` show only what was written. A start the entries imply through a relation -- `star.mass: 0.92` -> `star.logmass`; lens/source masses, distances and proper motions -> `mulensevent.t_E` -- exists only after `finalize_user_params` runs the relaxation engine at stage 4, so an earlier reader silently sees the defaults.yaml value, or nothing. That is the user-start contract (JDE 2026-09-11: produce the user's value or warn) failing one step removed: the user's number reaches the model, but a data-driven seed built at stage 1 from the WRONG number does too.

`probe_start` runs the same engine on the same snapshot `probe_derivable` uses (`ConfigManager._probe_solve`, the one snapshot/rollback both share) and returns `{path: ProbedStart}` instead of discarding the solve:

- `value` is INTERNAL units, `user_value` the path's USER units (a user `unit:` override honoured) via `ConfigManager.from_internal` -- the ConfigManager twin of `Parameter.from_internal`; never convert by hand (the reciprocal-factor invariant in `CLAUDE.md`).
- `rank`/`source` are the engine's provenance. `derivable` means the engine produced any start, a defaults.yaml one included; `informed` means the start traces back to a user entry or a component hint or seed (rank above `PRECEDENCE_DEFAULT`, the `probe_derivable` test). A reader whose seed would be a confident wrong answer on a bare default (a defaults.yaml `t_0` describes no event) must test `informed`.
- A path the engine cannot reach at all -- no entry, no hint, no initval, no relation -- comes back with `source == "not derivable"` and None values. That is an ANSWER, and the reader handles it explicitly (a named log line and a documented degrade), never with an invented number.
- An engine failure RAISES `RuntimeError` naming the paths. It is never "not derivable": the probe solves a subset of stage 4's inputs, so a failure is an engine or bookkeeping bug. `probe_derivable` inherited the same rule (review 2.1.17 -- it used to swallow every exception as "not derivable", flipping the then MMEXOFAST trigger).
- Paths are the canonical index form (`star.0.logmass`); a name-form or 2-part path raises `ValueError`, a path naming no declared parameter raises `KeyError`. A parameter no relation mentions is answered as a leaf, as finalize's "fallback to leafs" pass treats it.

**The limit: it sees only what is known NOW** -- user entries (seed 0 of an `initval` list), every hint pushed so far, and seed 0 of `seed_hint_sets`, which is what stage 4's seed-0 solve layers. A hint a later component pushes can still move the stage-4 start. It is the best a stage 1-3 reader can have, not a promise about stage 4.

**Not cached, by design.** The inputs (user_params, hints and their ranks, seed hints, overrides, links, the symbol map) are all mutable and read by `resolve()` deep inside the solve, so there is no cheap key that cannot go stale. Callers ask for every path they need in ONE call instead; one probe costs ~0.2 s on `examples/hat3` hat3_mist.

The worked examples:

- **The EEP seed (review 1.8.6).** `EvolutionaryModel._seed_eep_hint` runs at stage 1 and read `star.logmass` through `resolve()`, which answered 0.0 because every shipped params file seeds `mass`, never `logmass`; the seed walked the 1.0 solMass track (hat3_mist, mass 0.92: EEP 348 at a seed chi2 of 19.4 on the true track, against 338 at 0.16). It now probes logmass, initfeh, feh, radius, teff and age in one call.
- **The microlensing flux bootstrap (review 2.6.30(b)).** `MulensInstrument._probe_bootstrap_geometry` probes t_E, pi_E, each source's t_0/u_0/rho and the companion's s/log_s/q/alpha once per `load_data`, after the peak finder, and hands the reader to `_estimate_flux_components`, `_check_data_format` and `_binary_magnification_columns`. On `examples/ob170114` (t_E and pi_E derived from masses, distances and proper motions) the old raw-`user_params` read saw `t_E = None` and invented 30 d with no parallax; the probe sees the engine's 123.2 d and (0.110, 0.178). An uninformed t_0, u_0 or t_E now takes the no-geometry branch with a log line naming what is missing; an uninformed companion s/q/alpha logs and degrades to point-lens columns.

- **A star's sky position (review 1.1.10) -- the one reader that must NOT probe.** Links are applied at stage 4, so `resolve()` answered a linked `star.Source.ra: {initval: star.Lens.ra, sigma: 0}` with the defaults.yaml placeholder (180, 0) deg -- and with `user_modified` True, because the link's `sigma: 0` stays in `user_params`, so the `user_modified` / `in user_params` guards could not tell a link from a number. Five stage 1-3 readers ran silently against it: the astrometry tangent point (an abs dataset ~3e8 mas off), the microlensing line of sight and Earth-velocity conversion (KMT-2023-BLG-1454: t_E 6.394 for 6.438, light-curve logp +79.6 at identical parameters), the no-microlensing-data line of sight, the galactic-model proper-motion seeds and, with the link reversed, the BJD_TDB conversion (+4.2 s on every KMT time). `probe_start` was tried first and broke every microlensing acceptance fixture: the line of sight is what `MulensEvent.register_frame_constants` needs to give the engine Earth's projected velocity, and until it has that the geocentric proper-motion relations have no scale, so the probe raises. A position is never derived by a relation at stage 1 -- it is a number the user wrote or a link to such numbers -- so the five readers go through `components/star/position.py` (`probe_star_radec` / `require_star_radec`), which reads the user's own initval/mu or evaluates the link expression on its dependencies' starts, recursively, with no engine. An unstated position raises (or, for the optional pm seeds, skips) and never reaches the placeholder. A `rel` astrometry dataset uses no sky position and reads none. Tests: `tests/test_linked_radec.py` (a linked config equals its numeric twin in every reader and in the light-curve logp, both link directions).

## A decision on a solved start (`revise_after_starts`), and why finalize is not re-entrant

A few topology decisions depend on a start that exists only AFTER the engine has run -- the SED cannot know whether a star's data-derived temperature lies inside its bolometric-correction grid until stage 4 has solved it (review 2.9.15), and `probe_start` cannot answer it at stage 3 because the source-flux seeding that sets that temperature is itself a stage-3 hint. Such a component overrides `Component.revise_after_starts(system)`: called once, after stage 4, it records its decision on itself and returns one `(message, param_paths)` per revision. If any component revised, `System.prepare` runs stages 3 and 4 ONCE more for every component, so every manifest, mask and hint that reads the decision agrees with it, then logs each revision as a WARNING, records it as a solve diagnostic (`ConfigManager.record_diagnostic`, after the last finalize, which resets the list) and keeps it on `System.topology_revisions`, which the startup table prints in its caption.

**An estimate that READ a start too early (`reread_after_starts`, review 8.6.23).** A data-derived estimate that needs a start runs at stage 1 on `probe_start`, which sees only the hints pushed so far; a stage-3 hint can still move the solved start. Such a component overrides `Component.reread_after_starts(system)`: after stage 4 it compares what it read with `ConfigManager.solved_start(paths)` (the seed-0 start of the last solve, in `probe_start`'s `ProbedStart` shape), recomputes the estimate at the solved start where they differ, and returns one `(message, param_paths)` per recomputation. The same one extra pass of stages 3 and 4 runs (shared with `revise_after_starts`); the messages are logged at INFO and recorded as info diagnostics -- not in the startup caption, since the parameter set is unchanged. Then every component is asked AGAIN, and a non-empty answer RAISES: the estimate and the start it seeds depend on each other, and one pass is the contract (no iteration to a fixed point nobody has shown exists). Today's one user is the microlensing flux bootstrap (`src/exozippy/components/mulensing/mulensing.md`). Tests: `tests/test_bootstrap_geometry_start.py`.

**The second solve starts from the PRE-solve inputs** (`ConfigManager.snapshot_solve_inputs` / `restore_solve_inputs`). `finalize_user_params` is not re-entrant: it injects its solved starts back into `user_params`, so a second call reads every solved start as one the user WROTE -- PRECEDENCE_USER in the ledger, "user" in `initval_source`, and an entry in every stage-3 reader of `user_params`. Measured on the 2.9.15 reproducer before the snapshot existed: an inactive lens Teff reported "your start value is DROPPED" for a start the user never wrote, and the start logp moved. The snapshot holds the attributes `_probe_solve` rolls back, plus `seed_resolved` and the symbol map. Hints are deliberately NOT restored: they are component inputs, re-pushed by the second registration pass -- or, for a tie the revision dropped, kept from the first (the source-flux seed is still a measurement after the zeropoint prior that used it is cut). Tests: `tests/test_sed_no_grid_fallback.py`.

## Parameter naming convention

An element has **three** user-facing spellings, and `ConfigManager.resolve()` accepts all three: the 2-part **broadcast** `comp.param`, the **index** form `comp.<i>.param`, and the **name** form `comp.<Name>.param` (e.g. `star.Lens.distance`). Internally, instance names are standardized to indices (`star.0.distance`), and that translation is TOTAL for a list component: `System` calls each component's `normalize_config_block` hook BEFORE building the `ConfigManager`, so even a name a component *derives* rather than reads (Mann and Torres name each instance after the star it constrains) exists when standardization runs. Until 2026-09 they derived it in `__init__` instead, i.e. after the `ConfigManager` was built, so `mann.A.ks_offset` survived name-form forever and leaked into `master_symbol_map`, the provenance ledger and `export_solution` -- and a *link* on it was a hard error telling the user to use the spelling they had just used. Two exceptions remain by design: a flat-dict component keeps all three spellings verbatim (`sed.B.av` has no index to fold into), and `system_config=None` skips standardization entirely.

**The most specific spelling wins, for every field.** The two specific spellings each name one element and beat the broadcast, which covers only the elements no specific entry claims -- and that holds for the `unit:` and `init_scale` channels exactly as it holds for `initval`/bounds/`mu`/`sigma`. `resolve()` builds the candidate list once, in `_element_keys` (least specific first), and its five consumers split into two traversals of that ONE list: the loops that apply every match in turn (component `"overrides"`, user params) let the most specific land last, and the lookups that stop at the first hit (`unit:`, `propagated_scales`, `scale_hints`) go through `_lookup_keys`, which rotates the broadcast key to the end. Until 2026-08 the first-hit lookups scanned the list as written, so one config could have `star.teff: {unit: K}` **beat** `star.0.teff: {unit: ...}` for the unit and for an `init_scale` while **losing** to it for every numeric field. Not cosmetic on the scale channels: `init_scale` seeds the whitening probe, and for an unbounded element with no sigma it *is* the prior width.

**A STRUCTURAL prior refuses a params-file mu/sigma** (review 2.2.21): defaults.yaml `structural_prior: true` closes `mu`/`sigma` on that parameter (its initval stays open), checked once by `validate_structural_fields` at construction (it reads `links` too). The rule and its cases are in `components/parameter.md`, "Structural priors".

**The entry SHAPE has one internal spelling too: a dict of fields.** A params file may write a parameter as a dict, a bare number (`star.0.teff: 5800`) or a bare per-seed list (`star.0.teff: [5000, 6000]`); the two bare forms mean exactly `{initval: <value>}`, and `config.standardize_entries` translates them before any standardizer pass runs -- in `standardize_param_names` and in the `system_config=None` branch alike -- so `ConfigManager.user_params` holds dict entries and nothing else. A null entry (`star.0.teff:` with no value) RAISES, naming the key: it is ambiguous user input (a value not written, or a line not deleted), not a shortcut the boundary may translate (JDE 2026-09-30). Every reader goes through `config.user_entry(user_params, key)` (or `require_entry` inside an `.items()` loop), which returns the dict or `None` and RAISES `TypeError` naming the key if a non-dict ever reaches it -- a bare value past the boundary is a bookkeeping bug, not a spelling. Until review 1.1.7 the bare shape survived standardization and each of ~20 readers re-guessed it, differently: `_build_seed_overrides` skipped non-dict entries, so the documented bare per-seed list silently kept only seed 0; `Component.user_wrote_field`, `Orbit._user_seeded_initval`, `peakfind`/the since-removed external-seed loader/`globalsearch`'s "did the user name this start" checks and the init_scale sync all read a bare start as "the user wrote nothing"; `MulensInstrument._user_or_default` returned a bare value for whatever field was asked (`mu` included). The translation is a COPY: the user's file, and the GUI's ruamel document, keep the spelling they were written in. The RAW-params validators below, `validate_sigma_has_center` (mkparam calls it on the file it read) and mkparam itself still see the user's spelling and still accept a bare entry. Tests: `tests/test_bare_param_entries.py`.

**Naming one element under BOTH specific spellings is an error and raises.** The index and name forms are equally specific, so "most specific wins" cannot adjudicate, and the two traversals disagreed about it (index won the first-hit lookups, name won the apply-every-match loops). Rather than pick a winner, `_reject_duplicate_spellings` refuses the config, naming both keys. It runs at `ConfigManager` construction on the **raw** params -- before `standardize_param_names`, which is where the evidence is destroyed: pass 1 files both under the one index key, so whichever the YAML listed second silently overwrote the other, value, bounds and **prior** included. Content is not consulted; two entries that happen to agree are still one element addressed twice. `resolve()` carries the residual half of the same check, for the case construction cannot see: per-element `names` supplied by a component's manifest that are not its own config instances' names (`lens`'s per-source vectors, labelled with the SOURCE STARS' names -- `examples/ob161003`). Those keys survive *standardization*, though not all the way to `resolve()`: `Lens._rewrite_source_param_keys` renames each to its source slot inside `Lens.__init__`, before any stage-1 code, which is why this site reads the RAW keys rather than `user_params`. That check reads the keys the **user wrote**, not `user_params`, because `finalize_user_params` injects the engine's solution back under the index form and on ob161003 those coexist with the user's name-form entries by design.

**Broadcast + specific is NOT affected** and must not be: it is well defined ("most specific wins"), it is the idiom for "set every element, refine one", and shipped configs plus `SED._inject_grid_bounds`' `add_override` on `star.av`/`feh`/`teffsed` rely on it. Two consequences of the raise: the reported `unit` *string* (written by the user-params loop) can no longer disagree with the *scaling* (set by the first-hit scan), since at most one specific entry exists per element and both passes therefore read the same one; and a name that is also an index string is not a duplicate at all (the two spellings are then one string, and `validate_instance_names` bans all-digit names anyway). No shipped example moves -- all 19 configs prepare and resolve byte-identically, ledger and provenance included, and none names an element twice. Tests: `tests/test_param_specificity.py`.

**A broadcast key must cover the WHOLE vector, or it RAISES.** `standardize_param_names` Pass 2 expands `comp.param` into one indexed key per CONFIG ENTRY -- all it can see, since it runs at `ConfigManager` construction, before any manifest exists -- but a parameter's element count is a manifest `shape` and need not equal the config-list length, in **either** direction. Longer (HISTORICAL, and why the check was written): the pre-split `lens` had one config entry while its per-source vectors (`t_0`, `u_0`, `rho`, ...) carried one element per source, so `lens.t_0: 2450000` reached element 0 only and element 1 silently took the defaults.yaml backstop -- and because the same expansion carries `sigma`/`mu`/`lower`, a broadcast PRIOR reached one source and not the other, a silent posterior change on a 2S2L fit.  The 8.6.17 split removed that mismatch at the root (`source` has one entry per source body, `lens` one per lens body), so this direction has no shipped instance any more; the branch is kept because nothing stops a component declaring a `shape` longer than its config list. Shorter: `detrend_coeffs` has shape (total detrend columns,), which for two files sharing one column is 1 against a config list of 2, so Pass 2 wrote indexed keys for elements that do not exist. `ConfigManager._check_broadcast_covers_vector` refuses both, from `resolve()` -- the first place the real element count is known -- naming the per-element spellings that work. Not a fill: element *j* of a pre-split lens vector was a SOURCE and element *j* of `detrend_coeffs` is a COLUMN, so "instance *j*", the only thing a broadcast key can mean, is not what either wants. Checked only when the caller passes an explicit vector `shape`: `shape=()` (with or without `element=`) legitimately resolves one element of a longer vector, and comparing 1 against the config-list length there would reject every ordinary broadcast. The residual case a length test cannot see -- two instruments with two detrend columns between them -- is left open deliberately. (Closed for the live surface since #440: an OWNED vector -- `Parameter.element_owners`, parameter.md -- is addressed as `comp.<owner>.param_<k>`, and `ConfigManager.adopt_element_owners` refuses every broadcast and every `comp.<name|i>.param` key on it after stage 3, before this check is ever reached.) Costs users nothing: all 21 shipped example configs prepare unchanged, and none broadcasts onto such a parameter (`examples/ob161003` spells every per-source entry by the source star's name). Same sizing hazard as the per-element masks of the element roles, which `manifest.normalize_selector` closed on arrival by sizing from the parameter's own element count. Tests: `tests/test_param_specificity.py`.

## User-defined parameter links (`linking.py`)

Any of the five linkable numeric fields in a `params.yaml` entry (`initval`, `mu`, `sigma`, `lower`, `upper` -- `linking.LINKABLE_FIELDS`) may be a string expression referencing other parameters (`star.A.age: {initval: star.B.age, sigma: 0}`, `orbit.b.omega: {initval: "orbit.c.omega + 180", sigma: 0}`, `star.A.av: {lower: star.B.av}`). Semantics:
- `initval` link + `sigma: 0` → hard link: the element is never sampled and deterministically tracks the expression.
- `initval` link + `sigma > 0` (or a `mu` link) → soft link: sampled normally plus a Gaussian `pm.Potential` on the difference.
- `initval` link, no sigma → initialization seeding only (relaxation-engine snapshot, no runtime tie).
- `lower`/`upper` link → dynamic hard bound: the logit transform maps into the tensor-valued interval. **No `-log(span)` normalization potential (for the case where a dynamic bound is combined with a `sigma`, which IS normalized, see the truncated-normal section of `src/exozippy/components/parameter.md`)** -- the reparameterization already supplies it. With `lq = c + s*raw` the raw-space density is `q(1-q)` (section C cancels the raw `N(0,1)`) and `dval/draw = span*q*(1-q)*s`, so `p(val) = 1/(sqrt(2pi)*s*span)`: the conditional is exactly `U(lower, upper)` and its integral is independent of `span`, for any span. An explicit `-log(span)` would double-count, multiplying the joint by another `1/span` and rewarding the *bound source* for shrinking the interval (an ordering link `star.A.av: {lower: star.B.av}` with `av` in `[0, 100]` gave `av_B` a spurious `1/(100 - av_B)` factor pushing it to the wall; tight spans bias hard). This is review note 1.5; a term that was there until 2026-08-10. Do not "restore the normalization".
- `sigma` link → static numeric snapshot from the relaxation-engine solution. (`init_scale` is not linkable — it is stripped from user params.)

**A component may add a hard link too** (`ConfigManager.add_link(target, expr, origin)`, stage 3 only): the topology-implied ties of an orbit group (`Star._link_orbit_members`, `components/orbit/orbit.md`). It lands in `links` beside the user's, so every consumer below treats it alike, and is never a `user_params` entry; its `ParamLink.origin` keeps it out of the user's column of the ledger -- the engine ranks its target as a propagated value (the weakest input rank, capped at DERIVED_USER) rather than USER, and `initval_source` reports `solved`. The caller makes it hard with `sigma: 0` through its manifest `"overrides"` channel, and decides precedence against the user's own links first; `add_link` on a target that already carries an `initval`/`mu` link raises.

Referenced parameters contribute their values in **their own user units**; the result is read in the **target's user unit**. `ConfigManager` extracts links at construction (`extract_links` strips the strings from `user_params`), the relaxation engine asserts `initval`/`mu` links as directed PRECEDENCE_USER assignments each iteration, `Component._wire_user_links` builds the PyTensor closures (same-parameter element references are resolved inside `build_pymc` via `set_subtensor`; cross-parameter references use the lazy `add_parameter` recursion), and `graph.py` adds cross-parameter build-order edges. Tests: `tests/test_linked_params.py`.


**An unknown function in a link expression raises at PARSE time.** `sympify` turns any name it does not know into an `AppliedUndef`, so `sqr(star.B.age)` (a typo) and `log10(...)` (not a sympy name) used to parse cleanly -- the parser validated only free SYMBOLS. Hard and soft links then failed loudly in `sympy_to_pytensor`, but the two link kinds that never build a graph did not: a seed-only `initval` link and a `mu` link are consumed by `_apply_directed_links`, whose `float(expr.evalf())` can never evaluate an undefined function and whose failure is caught as "not evaluable yet" at DEBUG. The seed simply never applied, forever, silently. `linking._SUPPORTED_FUNCS` is now the one table of callable heads (sympy head -> `pytensor.tensor` name): `parse_link_expression` rejects anything outside it, naming the supported set, and `sympy_to_pytensor` builds its `_FUNC_MAP` from it -- the two used to be independent literals, and their only possible drift was the silent direction. `sqrt` and `**` are `Pow`, structural in sympy rather than `Function` subclasses, and are deliberately absent from the table.

## Input validation at construction

Four checks run on the RAW params, in `ConfigManager.__init__`, before `standardize_param_names` folds the name form into the index form and before the relaxation engine ever sees a number. They are there rather than deeper because that is where the user's own spelling still exists, and each one replaced a crash that named nothing:

- `_reject_renamed_arsun` -- the pre-rename `arsun` spelling, which would otherwise be an ignored key.
- `_reject_duplicate_spellings` -- one element addressed under both specific spellings (above).
- `_reject_list_valued_fields` -- a list in `lower`/`upper`/`mu`/`sigma`/`bound_scale`. A list means per-SEED start values and nothing else; seeds move the start, never the bounds or the prior. `resolve()`'s numeric loop tolerates lists by taking element 0 (that same per-seed convention), so `{sigma: [10, 20]}` sailed past the sigma application and died several frames later inside `apply_value`'s `float(list)`, as a bare TypeError with no parameter, field or file in it. What such a list usually means is "one value per element", which is spelled with one KEY per element. `init_scale` is exempt: it is warn-stripped moments later and pre-2026-07 restart files name it, so a fatal error there would break files that work today.
- `_reject_bare_string_values` -- a bare (non-dict) parameter value that is not a number. `extract_links` inspects dict entries only, so the bare link spelling `star.A.teff: star.B.teff` was never recognized as a link and reached `finalize_user_params`' `float(val)`, again naming nothing. It RAISES rather than being rewritten to `{initval: ...}`: the bare form cannot say whether the user meant a hard link, a soft link or a seed, so rescuing it would pick a model for them; the error prints the three dict spellings. A quoted number (`"5800"`) is still a number and is accepted.

Tests: `tests/test_bad_user_input.py`, `tests/test_param_specificity.py`, `tests/test_linked_params.py`, `tests/test_sigma_center.py`.

**A RETIRED system-config key RAISES with its migration, at the component that owned it.** System-config keys are not validated against a schema centrally, so a key a component no longer reads would otherwise be ignored in silence -- a config the user believes is in effect and is not. Each owner keeps a `REMOVED_KEYS` map of `{key: message}` and refuses the key in its constructor, naming what replaced it: `mulensing/bodies.py` for the MMEXOFAST keys (2026-10-01), and `planet/planet.py` for `mass_parameterization:` (review 2.14.9), whose message is a function of the value written so `log_q` and `linear` each get their exact replacement (`fitlogq: true`; `fitlogq: false` + `fitmsini: false`), and for `orbit_ndx:` / `star_ndx:` (owned by `orbit/bodies.py`'s `REMOVED_PLANET_KEYS`, because `planet_membership` reads them before the planet exists): a planet's orbit and host are the orbit blocks' groups, the one spelling (`components/orbit/orbit.md`).

**`citation:` is the one params-entry field that is neither a number nor a verbatim string.** It records what justifies an entry's prior; `resolve()` normalizes it through `config.normalize_citation` (a string is one citation, a list is several, both become a tuple) and carries it per element like the string fields. It is `CITATION_KEYS`, not `PHYSICS_KEYS`, so it never marks a prior user-modified. How it is reported is in `src/exozippy/components/parameter.md` ("Where a USER prior came from").

**A params file may carry RESERVED NON-PARAMETER keys, and they are split off before any of those four run** (`config.RESERVED_PARAM_KEYS` / `split_reserved_param_keys`, review 8.3.3). Today there is exactly one, `overdisperse:` -- the writer's declaration of whether the file's seeds still want scattering before the chains start, consumed by `samplers/_common.py`'s `_make_starts` and documented in `src/exozippy/samplers/samplers.md`. It must be split off, and split off FIRST, because a params file is otherwise a flat map of parameter paths and `finalize_user_params` registers every unmapped `user_params` key as a **leaf symbol** in the relaxation engine -- the same trap the "never write into `user_params`" invariant in `CLAUDE.md` describes, reached here from the user's side instead of a component's. Measured before the fix, on a two-key file: `overdisperse` became the sympy symbol `overdisperse`, entered `_last_resolved` as `0.0`, and the engine INJECTED BACK `{'initval': 0.0, 'derived': True}` over the user's own boolean. The split returns two NEW dicts and never mutates the caller's, because `System` keeps the file exactly as it was read and hands it to `structural_payload` and to `mkparam` afterwards. Reading it back out is `ConfigManager.overdisperse`, which is also where the "absent means true" default lives, so no consumer spells the default itself. A non-boolean value RAISES: a bare `overdisperse: "no"` would otherwise be truthy and mean the opposite of what it says.

The same pass **warns by name** on any other dot-less key whose value is a scalar. Every parameter path has a dot in it, so such an entry is either a reserved key or a mistake -- and the mistake is otherwise perfectly silent, becoming a leaf symbol with its own ledger row and its own inject-back initval for a parameter that does not exist. A dot-less key whose value is a DICT is left alone; only the scalar form is diagnosable this cheaply. Tests: `tests/test_overdisperse_declaration.py`.

**A key that matches no parameter is reported from `System.build_model`, and that is where it has to be** (review 2.3.16). The checks above catch what is wrong with a key's SHAPE; whether a well-formed key names anything in THIS model is a different question, and the answer does not exist until the parameters do. `diagnostics.ModelAuditor.check_unused_yaml` has always been the one authority for it -- `check_user_starts` defers to it in as many words -- but it was *reported* from `run.inspect_start`, i.e. run.py's startup reporting, so it fired for `exozippy <config>` and for nothing else. Measured cost: `DC2018_128_tightpriors.params.yaml` keyed a bound as `lens.DC2018_128.t_0` (the RUN name; the config declares `lens: - name: "Lens"`), the `t_0` tightening -- 5.76 of that file's ~27.6 nats -- never applied, and a nested-sampling job driven by `examples/DC2018/dc18_fullns_pilot.py`, which calls the sampler itself, ran over an hour before the mistake was found by reading the config. A params file is exactly where a silent no-op is most expensive: the whole point of the file is to constrain something.

Three properties of the placement, each deliberate. It is **build_model and not `finalize_user_params`**, which is where the item proposed it: `Parameter` objects are created in stage 6, so after `prepare()` alone `get_all_parameters()` is empty (measured, and pinned) and the config layer has nothing to compare a key against. It is **one emission** -- run.py's copy is deleted, so `exozippy <config>` does not say it twice. And it warns **once per System**, because a live System can legitimately be rebuilt and the params file cannot change between two builds of one.

**Why `standardize_param_names`' strict check does not already cover it**, since it looks like it should: that check refuses a 3-part key whose instance name is declared NOWHERE, but its accepted set is every `name:` declared by any list component -- deliberately, because a component's per-element names may borrow another's (`source.<star name>.rho`; see "Parameter naming convention"). The tightpriors config declares `galacticmodel: - name: "DC2018_128"`, so the mis-keyed name WAS declared somewhere and passed. Narrowing that check cannot fix this without breaking the borrowed-name spellings; reporting the residue after the build can. Both layers stand: the strict check is the first line of defence and still raises. Tests: `tests/test_unmatched_params_keys.py`.
