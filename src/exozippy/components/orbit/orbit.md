# Orbits

`src/exozippy/components/orbit/`: body groups and hierarchical topologies, the `tc` window,
and the two halves of the Eastman 2024 parameterization -- `fitvcve` (V_c/V_e) and
`fitchord` (the transit chord).

Read this before changing orbit topology, the eccentricity or inclination coordinate, or
anything that adds a branch mixture. Related: `src/exozippy/skyframe.md` (the frame the
Keplerian elements are defined in), `src/exozippy/components/parameter.md` (the element roles the
mode tables use), `src/exozippy/components/star/star.md` (the planet mass coordinate,
whose `rank: 5` argument is the same one).

## Hierarchical orbits and body groups

Every orbit is a two-body Keplerian arc between a `primary:` and a `companion:` **body group** (lists of star/planet instance names or `star.X`/`planet.X` paths; parsing in `components/orbit/bodies.py`). Multi-body groups are point masses at their barycenter, which is how hierarchical systems are built (KELT-4: `b` orbits `A`; `B` orbits `C`; `[B, C]` orbits `[A, b]` -- see `examples/kelt4`). Omitting both keys reproduces the legacy implicit topology (companion = planets whose `orbit_ndx` points at the orbit, primary = their host stars). Each orbit derives `m_primary`/`m_companion`/`m_total`/`a`/`K` from the member bodies' `star.mass`/`planet.mass` nodes (weighted-sum context nodes injected by `Orbit.add_parameter`), so orbits sharing a body are automatically mass-consistent. The relaxation engine gets per-orbit `m_total` initvals from a custom solver (sum of member masses) feeding the instance-scoped Kepler relation; relation symbols must stay mapped in `get_symbol_map` (`a`, `m_total`) or they instantiate as symbols shared across orbits.

`tc`'s **hard** bound is `tc_init +/- P/2`, one full period (tc and tc + P are the same solution), and it is declared at **stage 3** -- before the relaxation engine reconciles the two legal period spellings. So it must read the period the user actually seeded: `Orbit._seeded_period` prefers a directly seeded `period:` and falls back to `10**logP`. Reading `logP`'s resolved initval alone returned its defaults.yaml value (1.0 -> 10 d) for every fit that seeded `period:`, hard-bounding tc to `+/-5` d whatever the real period -- `examples/GaiaBH1` (P = 185.6 d) was shipping with that bound, and `examples/kelt4/kelt4_sed.params.yaml` carries a comment describing the workaround (seed `logP` directly). Still uncovered, because only the engine can get there: a period implied by `a` + the member masses. Tests: `tests/test_orbit_tc_window.py`.

**The same argument covers `tc` itself, through a seeded time of PERIASTRON.** `tp` is how the RV literature quotes an eccentric orbit, and a `orbit.<n>.tp` entry used to reach nothing at all: `tp` was not in `get_symbol_map`, so the relaxation engine filed it as an unmapped two-part leaf at RANK_USER and no relation could consume it (measured: `tc` stayed at its defaults.yaml backstop 2460000 while `tp` sat resolved at the user's value). The channel is **one-way**, and that is not a limitation to fix later: the tc <-> tp chain runs through `M = E - e sin E`, the transcendental sympy hangs on, which is precisely why RELATIONS says it carries no Kepler chain. So `symbolic_physics.tc_solver` is a standalone solver in the sense 8.1.5 established -- `register_custom_solver(..., standalone=True)`, KeyError as the "not yet" signal, RANK_DERIVED_MIXED so a user's own `tc` always wins. The direction it implements needs no Newton iteration at all, because conjunction is defined by a true ANOMALY rather than by a time: `physics.tc_from_tp` is `tc = tp + M(e, omega) P / 2 pi`, closed form, and the Kepler algebra lives once in `physics.mean_anomaly_at_conjunction` next to the pytensor `calc_tp_from_ecc` the model itself evaluates. The reverse is deliberately absent -- `tp` is a runtime Deterministic, so nothing ever needs a start value for it.

The window has to move with it, and `Orbit._seeded_tc` is where: stage 3 runs before the solver, so reading `tc`'s own resolved initval returns the 2460000 backstop for a `tp:`-seeded file and the solved tc then lands thousands of days outside its own hard bound -- a fatal start-value error naming a parameter the user never wrote. `_seeded_tc` computes the same implied conjunction from the same seeds, and only where the user did not write `tc` themselves (`_user_seeded_initval`), so the window and the solver cannot disagree about which value wins. Its `(e, omega)` come from `_seeded_ecc_omega`, which the bigomega half-plane remap now shares. Tests: `tests/test_tp_seed.py`.

Consumers are membership-based: `rvinstrument` (per-instrument `star_ndx`, default 0) sums `orbit.K` over every orbit containing the observed star (`Orbit.star_membership`; companion-side membership flips sign and rescales by `m_primary/m_companion`); `astrometryinstrument` rel mode references an orbit by name (`orbit:` key; legacy `planet_ndx` still resolves) and models the companion group relative to the primary group, adding the photocenter wobble of any orbit nested inside a group (SED-weighted when `band:` is given, dark-companion beta=0 otherwise, barycenter fallback with a warning); gaia/abs photocenter wobble sums the orbits whose primary group contains the target star. Stars only get sampled `ra/dec/pm_ra/pm_dec` when a gaia/abs dataset exists -- rel data are differential and need only the parallax scale.

## The ascending node is degenerate without RVs, and is FOLDED, not truncated

`(bigomega, omega_*, tc)` and `(bigomega + 180, omega_* + 180, tc')` are a reflection through the sky plane. Astrometry of every kind -- absolute, epoch, relative -- is identical between them; only radial information says which node is ascending. Review 1.8.3.

**The truncation is gone.** `_restrict_bigomega_halfplane` used to bound `ybigomega >= 0`, selecting one label with a hard wall, and a hard wall biases a posterior that hugs it: measured on `examples/HIP1349`, `Omega = 176.5 +/- 2.7` against DMSA's `172.6 +/- 3.4`, with ZERO origin-crossings in 16k draws (the crossing sweeps Omega through 90 deg at finite radius, so a truncated chain cannot reach the antipodal mass at all). What the wall actually cost is worth stating precisely: a posterior centred near it extends PAST it, and that mass is not represented anywhere else in the truncated support -- `(182, omega, tc)` is not the same solution as `(2, omega, tc)`, only as `(2, omega+180, tc')`. So the bound deleted real posterior mass and piled the rest against itself. Without it the chain moves through 180 deg continuously and the bias is gone. `_declare_node_degeneracy` keeps only the table note. It drops the bound, the `y_init >= 1e-6` nudge that existed only to keep a seed off it, the seed remap that used to move a `(180, 360)` start onto the surviving label, and -- with the remap -- the direction-vector SEED itself: that was a manifest option only because the flip had to beat the relaxation engine, and with nothing to flip the engine's own `Eq(xbigomega, cos(bigomega))` seeds the pair, exactly as the astrometry-WITH-RVs branch has always relied on. Setting it anyway would apply a shape-wide option to every orbit, degenerate or not; measured on `examples/kelt4`, that moved the planet orbit's unseeded node from 0 to 90 deg for no reason.

**The predicate is PER ORBIT.** `_node_degenerate_orbits` asks which orbits astrometry measures and which radial data measure, separately, from the same membership maps `amplitude_constrained_orbits` uses -- so an RV-constrained orbit in a mixed system is not degenerate and gets neither a fold nor a table note. The old test was system-wide ("any astrometry and no `rvinstrument` anywhere"), which truncated it for nothing.

**The fold is applied ONCE, where the draws are decoded**, and that is the part that matters beyond reporting. With both half-planes open, two chains sitting at `bigomega` and `bigomega + 180` describe the same physical solution -- so Rhat on the unfolded coordinate reports non-convergence for chains that agree exactly, the mode reporter sees two clusters that are one mode, and the seed ledger doubles. `System.fold_degenerate_draws` is called from `run.py` at the seam between sampling and post-processing, which is the point BOTH paths (fresh draws and a reloaded trace) arrive at, and everything below consumes what it leaves. Folding per consumer is exactly how they come to disagree.

- **The component rewrites only the RAW sampled coordinates** -- `xbigomega`, `ybigomega`, `secosw`, `sesinw` (sign flips) and `tc` (moved to the other conjunction) -- and `pm.compute_deterministics` regenerates every derived variable from them in one pass. The alternative, flipping each derived quantity by hand, needs a list of everything that moves (`omega`, `esinw`, `ecosw`, `tp`, `ts`, `sinw`, `cosw`, `vcve`, `bigomega`...), and such a list goes stale silently the next time one is added, reporting a parameter that no longer agrees with the draws it came from.
- **Which half-plane it folds ONTO is chosen from the draws, not fixed at `[0, 180)`.** A fixed cut manufactures bimodality the moment a posterior straddles it: a chain centred on 178 deg with a 3 deg width would come out as a lump at 179 and a lump at 1, which is this item's own complaint in a new form -- and straddling the seam is exactly what the truncation used to prevent and now permits. `bigomega` is 180-periodic here, so the centre is the **axial** mean direction (the circular mean of `2 bigomega`, halved) and a draw folds only when it lies more than 90 deg from it. The item offers this as "rotate the cut to `bigomega_init +/- 90`"; taking the centre from the draws rather than from the seed is the same idea without trusting a start value.
- **`tc`'s shift is `(M_c(omega + pi) - M_c(omega)) P / 2 pi`**, through the same `physics.mean_anomaly_at_conjunction` the tp seed solver uses, then wrapped by whole periods back into tc's own window. That window is exactly one period wide, so there is always exactly one representative inside it and the folded draw stays encodable -- which is why the wrap is not a detail but the thing that makes the fold closed.
- **The two labels are effectively DISCONNECTED for a single chain, and that is measured, not assumed.** The partner's `tc` is half a period away while tc's raw coordinate is scaled to the TIMING precision, so the excursion is ~1e5 raw units -- far past `_RAW_CANCELLATION_CLIP`, where the logit-uniform correction deliberately stops cancelling the raw `N(0, 1)`. Measured on the test system: the observation likelihood is identical between the labels and the four sign-flipped coordinates' prior terms cancel exactly, while `tc`'s do not (`orbit.tc_raw` moves by -2.97e10 against a correction capped at +5e7). Two consequences. What removing the truncation actually buys is that a posterior may now straddle 0/180 CONTINUOUSLY instead of piling against a wall -- which is the bias the item measured. What the fold is for is chains or seeds that START in different labels, which is exactly the Rhat case: it cannot rescue a chain that needed to migrate, because no chain will.
- **The stored `lp` is left alone.** The two labels have the same physical posterior density -- the observation term is identical and every prior term is symmetric under the reflection -- so a folded draw's `lp` is still its `lp`. Where the raw excursion trips the cancellation clip above, the difference the clip introduces is an artifact of the sampled coordinate rather than a density, and re-deriving `lp` from the folded raws would record the artifact instead of removing it.
- **Only the flipped draws are re-encoded.** A decode/encode round trip is the identity only to ~1e-15, and a fold that perturbs the draws it decided to leave alone is a fold nobody can check.
- The regenerated deterministics come back in INTERNAL units, because PyMC recomputes them from the model graph and knows nothing about the conversion already applied to the rest of the posterior; `run.py` converts just those back with `_convert_posterior_to_user_units(..., only=...)`.
- **A failure here never kills a finished fit.** The fold is wrapped: a component that raises leaves the draws unfolded with a warning saying the diagnostics are then computed on both labels at once, and a failure to regenerate the deterministics says plainly that the derived columns of that trace are unreliable. Both are honest about what the reader is looking at.
- `src/exozippy/config.md` used to list the bound among the manifest's deliberate structural values; that entry now names the seed and points here.

Tests: `tests/test_node_degeneracy.py`.

## The Kepler solve

Every Keplerian evaluation in the tree goes through `physics.solve_kepler(M, ecc, circular=False)` -- `get_true_anomaly`, `get_sky_position`, `get_radial_velocity`, transit's two, and the Roemer-delay one in `ltt.py`.

**One kernel above the solve, one state accessor above the kernel** (review 4.8.2). The five call sites used to each re-derive the same angle identities and project the ELEMENTS straight to their own observable; they now all consume `physics.state_vector_terms(t, tp, n, ecc, sinw, cosw, circular)` -- the one place the Kepler solve becomes `(sinf, cosf, r_over_a, sinwf, coswf, vx_phase, vz_phase, ecc_factor)` -- and compose it with their own amplitude and orientation factors. `Orbit.state_vectors(t, a_scale, orbit_map, relative)` sits on top of the kernel and returns the full sky-frame state `(X, Y, Z, VX, VY, VZ)` per body (X = North, Y = East, Z growing away from the observer, so `VZ` carries the RV sign); `get_sky_position` is its position half, and a consumer that can take a full state -- microlensing lens/source orbital motion is the motivating one -- should take it from HERE rather than adding another elements-to-observable projection. This is also the seam for the eventual N-body swap (review 8.8.15): an integrator backend replaces `state_vectors`' interior, and the things that will NOT survive it are already marked in its docstring (the factored-out `a_scale` amplitude -- a Keplerian self-similarity -- and `relative=True` as an omega + 180 flip rather than a subtraction). The projections that collapse their amplitude before the kernel (`get_radial_velocity`'s `K`, transit's `a/R*`, ltt's `a_rel` + barycentric `factor`) are the consumers 8.8.15 says must change when that day comes; they are kernel consumers, not `state_vectors` consumers, precisely because their amplitudes are pre-collapsed and bit-identity mattered on the refactor. Refactored bit-identically (start logp compared as raw float64 bytes on kelt17, hd80606, GaiaBH1, kelt4, HIP1349, hat3, ob09020). Tests: `tests/test_state_vectors.py` (velocities against central differences of the positions; Z's node convention), plus the conventions pinned by `tests/test_skyframe.py` and `tests/test_astrometry.py`, which now run through the kernel path.

**Index before the solve, not after** (review 6.8.1). `get_true_anomaly` takes an optional `orbit_idx`; with it the solve is done on that one orbit rather than on the whole `(N_times, N_orbits)` grid with every other column discarded. `rm.py` was the caller that sliced afterwards, so an N-planet system paid N times over for one Rossiter-McLaughlin curve; `get_sky_position` already indexed its inputs first, and this is that pattern.

**A structurally circular orbit skips the solve entirely** (review 6.8.2). At `e = 0` the mean, eccentric and true anomalies all coincide, so `(sin M, cos M)` is not an approximation -- it is the answer, and it is the exact one where exoplanet-core returns a converged iterate. On `examples/kelt17`, the shipped circular fit, this moves the start logp by 4.9e-9 nats (3.3e-12 relative), in the direction of the exact value.

- **`circular` is a STRUCTURAL claim the caller makes, never a runtime test**, and both halves of that matter. Structural, because a `pt.switch` would build the Newton solve anyway -- which is the whole cost -- and hand `where`'s VJP a branch to multiply by zero. A claim about the PIN and not about the value, because an eccentricity that merely *starts* at zero can move, and treating it as circular would silently give the whole run the wrong RV phase.
- `Orbit.circular_orbits` is the one place that judgement is made: `sigma: 0` **and** `initval: 0` on **both** `secosw` and `sesinw`, which is how `examples/kelt17` writes a circular fit. It is conservative everywhere it cannot be sure -- a V_c/V_e orbit (whose circular case is a pin on a coordinate whose inversion is singular exactly there), an unresolved parameter, anything unpinned -- because being wrong costs a wrong model while being conservative costs the solve we were already paying.
- `_all_circular(orbit_map)` is all-or-nothing on purpose: the saving is in not BUILDING the solve, and a mixed vector has to build it for the eccentric columns anyway. Splitting the vector and reassembling with `set_subtensor` would save arithmetic and cost a graph that no longer matches the simple one; not worth it until someone measures a system where it matters.

Tests: `tests/test_circular_fast_path.py`.

## Transit and occultation durations, and what they measure (review 8.8.7)

`planet.t14` / `tfwhm` / `tau`, their occultation twins `t14s` / `tfwhms` / `taus`, the occultation impact parameter `planet.bs`, and the eclipse time `orbit.ts` are ordinary **derived Parameters**. They were bare `pm.Deterministic`s built inline in `transit.py`, which cost two things: an RV-only fit could not state them at all, and no fit could put a prior on one. They are geometry, not photometry -- every input is a planet or orbit parameter -- so they are declared **wherever there is an orbit**, transit data or not.

**That is the whole inference path, and it needs no new machinery.** A derived Parameter with a user `mu`/`sigma` gets `build_pymc`'s Gaussian branch, and the gradient runs back through the expression into the eccentricity vector. So `planet.b.tfwhm: {mu: ..., sigma: ...}` really is a measurement of `e sin(omega)` and `orbit.b.ts: {mu: ..., sigma: ...}` really is a measurement of `e cos(omega)` (Winn 2010 eqs 14-16 and 33; Charbonneau et al. 2005) -- the point the item makes, which is why this is not a reporting change.

Where the durations live is decided by their inputs, not by EXOFASTv2's layout: **`ts` is on `orbit`** because e, omega, tc and P all are and `tc` itself is an orbit parameter, while the durations are on `planet` because they need the radius ratio and `a/R*`. `bs` is `calc_b` at the other conjunction, a separate function rather than a flag because a manifest entry names one function and these are two parameters.

**EXOFASTv2's `tt` is deliberately absent.** The review item lists it, but its definition could not be checked from this tree, and a duration reported under a name whose meaning we guessed is worse than one that is missing -- the same discipline this file already applies to EXOFASTv2's V_c/V_e Jacobian sign.

**The START is the part that needed code**, and it is a one-way channel exactly like `tc_solver`: the forward model is a Kepler solve and its inverse has no closed form. Two 1-D bisections in `symbolic_physics`, registered on `orbit.ecc` and `orbit.omega`:

- The **duration ratio** `T_S/T` gives `e sin(omega)`. The textbook `(1 + e sin w)/(1 - e sin w)` is **exact only at a central transit**: once `b` and `b_S` differ, the two arcsin brackets no longer cancel and the first-order form is off by tens of percent at `b ~ 0.5`. The solver therefore inverts the exact ratio by calling `planet.physics.contact_duration` with `xp=np` -- the same function the likelihood evaluates, made backend-agnostic (the `skyframe.py` idiom) so there is no second copy to drift. Same for `ts`, through `orbit.physics.ts_from_ecc_omega`.
- Gated on **what the user WROTE** (`initval` or `mu`), never on what resolved. `ts` and the durations are derived, so the engine computes values for them every iteration; seeding `(e, omega)` back from those would be a fixed point dressed up as an inference, and would stamp RANK_DERIVED_MIXED provenance on an eccentricity nobody constrained.
- `orbit.omega` has **one** registration, `omega_solver_combined`. `custom_solvers` is a dict keyed by the target path, so a second `register_custom_solver("orbit.omega", ...)` would silently REPLACE the circular-orbit convention rather than add to it. Order is precedence: a stated eclipse time is a measurement and wins; the circular convention applies only where the sqrt(e) pair is exactly zero, i.e. where there is nothing to measure.
- A bisection that does not bracket returns `None` and the seed is left alone -- an observable no eccentricity reproduces is a statement about the config, not a failure of the engine.

Inject and recover, over `(e, omega)` from 0.05 to 0.6 and omega over the full circle: handing a fit the `ts`, `T_FWHM` and `T_{S,FWHM}` its own geometry produces recovers `e` to better than `1e-3` (worst case `3.7e-4`, at `e = 0.6`) and `omega` to better than `0.1 deg` (worst `0.032 deg`). Without it the start is the defaults.yaml `e = 2e-4`, i.e. no information at all. Tests: `tests/test_duration_constraints.py`.

## The V_c/V_e eccentricity parameterization (`fitvcve`)

`fitvcve: true` on an orbit block samples **V_c/V_e** and the direction of omega instead of the sqrt(e)cos/sin(omega) pair (Eastman 2024, PASP; arXiv:2309.14410, review 8.8.3). It exists because a transit-only fit in the sqrt(e) pair recovers eccentricities that are measurably *wrong* -- the paper's measurement over 330 simulated systems -- while the transit duration constrains `V_c/V_e = sqrt(1 - e^2)/(1 + e sin omega)` (eq 4) tightly. Per orbit, through `Orbit.ECC_MODE_TABLE`: `vcve`/`xomega`/`yomega` sampled, `ecc`/`omega`/`tp`/`esinw`/`ecosw` derived, and `secosw`/`sesinw` **reported** (role 3) so both parameterizations produce the same table rows; on a sqrt(e) orbit the reporting runs the other way and `vcve` is the reported one. Default off EXCEPT on a transit-only orbit, where it and the chord half turn on together (see "The transit-only default" below).

Everything below is what the paper does **not** address, because DE-MC does not care and a gradient sampler does:

- **The inversion is a quadratic and BOTH roots are kept.** `A = 1 + x^2 sin^2 w`, `B = 2 x^2 sin w`, `C = x^2 - 1`, and `B^2 - 4AC = 4(1 - x^2 cos^2 w)` -- so the half-discriminant is neat and dropping the factor of 2 gives roots that look plausible and are **wrong** (it did, in the first draft; `tests/test_vcve.py` round-trips the inversion against eq 4 over an (e, omega) grid for exactly that reason). The paper selects a root with a discrete sign parameter `S`, which is piecewise constant (no gradient) with a logp that jumps at `S = 1`. Instead the likelihood is **marginalized** over the two roots: `System._add_branch_mixtures` adds one `logsumexp` over the `2^k` root combinations of the `k` V_c/V_e orbits. Cost is `2^k` logp evaluations per step, logged, with a warning past two orbits.
- **The mixture needs no data component to know about it.** It substitutes the ecc node into the RV-level term sum (`pm.logp(rv, ...)` for the observed RVs plus the stored potentials -- *not* `model.logp()`, whose graph has already had RVs rewritten to value variables, so a held node is absent) and adds `logsumexp(...) - L_ref`, cancelling the as-built copy exactly. Two consequences, both wanted: a term that does not depend on `ecc` factors out identically, and one that does -- the Jacobian, the collision bound, a future orbit-crossing penalty coupling two orbits (review 8.8.9) -- is replicated per branch, making each branch's weight `log w + log|J| + barriers`, which is the form review 8.4.4 specifies for folded likelihoods. **Two branches routinely name the SAME node** -- two V_c/V_e orbits are two elements of one `ecc` vector -- so a combination applies its branches' substitutions **one after another** rather than merging them into one dict, which kept only the last and silently marginalized over 3 of the 4 combinations. That composes only because each replacement is written *relative* to the node it replaces (`set_subtensor(ecc[i], ...)`, so the second pass rewrites the first's base too); `register_branch_alternative` **checks** that and raises otherwise.
- **The primary branch is the UPPER root.** The roots' product is `C/A`, so for `V_c/V_e < 1` they have opposite signs and the physical one is always the upper; "prefer the lower eccentricity" (EXOFASTv2's choice *among physical roots*) would pin the forward model at `e = 0` with no gradient across that whole region. Which branch is primary decides only what the trace reports as `orbit.ecc`; the posterior is the mixture's.
- **Shields, hard and soft.** The discriminant is floored at zero *inside* the sqrt (so a NaN is unbuildable) and the roots are clipped into `[0, MAX_ECC]`; the **unfloored** discriminant drives a `soft_lower_bound`, because the floored one is flat across the whole imaginary region and a flat penalty has no gradient to follow out -- the same argument as `ecc_from_sqrte` being unclipped. The floor goes on the radicand, never on the result (`sqrt'(0)` is infinite and `pt.maximum`'s zero gradient then makes `0 * inf = NaN`).
- **The Jacobian keeps the prior uniform in e, and its SIGN is the term.** `V_c/V_e` is the sampled coordinate, so the derived eccentricity inherits `p(e) ~ |d(V_c/V_e)/de| = |e + sin w| / (sqrt(1-e^2)(1 + e sin w)^2)`, which diverges as `e -> 1`: that is exactly the paper's "strongly biases e toward high eccentricities" (section 3). Flattening it means adding the RECIPROCAL, so `Orbit._add_vcve_terms` adds **minus** `physics.vcve_log_jacobian` (which returns the honest derivative, because that is what a finite difference can check). Adding the derivative instead *doubles* the bias, and no comparison against `|dv/de|` can tell the two apart -- so the direction is pinned by measuring the implied density on `e` for flatness, and the potential's own sign is pinned against that at the call site (`tests/test_vcve.py`, two tests, deliberately separate from the finite-difference one). EXOFASTv2 applies a Jacobian for the same transformation; its sign convention is deliberately not restated anywhere here, because it could not be checked from this tree. The term is built from the `ecc`/`omega` NODES so the mixture makes it a per-branch weight, which is right: the two roots have different Jacobians. The chord half's `|d(chord)/d(cos i)|` is a separate, independent factor (the paper's eq 6 is the joint determinant; they are applied independently so either half can be switched on alone).
- **`vcve`'s upper bound is the image of the eccentricity cap, not a preference**: `sqrt((1 + MAX_ECC)/(1 - MAX_ECC)) = 141.4`, i.e. eq 4 at `omega = -90 deg`, where the planet transits at apastron and so moves slowest. A comfortable-looking `2.0` (the first draft) caps `e` at 0.6 for such an orbit and silently excludes the eccentric transiting planets the parameterization exists to measure. The bound is inert on a sqrt(e) orbit, where `vcve` is reported and role 3 gets neither prior nor barrier -- which is also why widening it moved no shipped example.
- **`vcve` carries `rank: 5`**, exactly as `planet.log_q` does, so the relaxation engine's Condition B always rewrites *it* rather than pushing back on `ecc`/`omega`. Without it the parameter's mere DEFAULT competed with the sqrt(e) defaults and the engine rewrote `ecc`/`omega` to satisfy it -- moving the start of four shipped examples and, through `K`, their planet masses. The symbolic bridge is written forward (`vcve (1 + e sin omega) = sqrt(1 - e^2)`) so one params file drives either parameterization.
- **The start avoids the degeneracy.** `V_c/V_e = 1` at `omega = 0` IS the circular orbit and is exactly where the discriminant vanishes, the roots merge and `de/d(V_c/V_e)` is infinite. The defaults start at `V_c/V_e = 0.99` with `omega = 90 deg` (`xomega = 0`, `yomega = 1`), where the discriminant is 1 -- for the same reason `secosw`/`sesinw` start at 0.01 rather than 0.
- **`tp`, `esinw` and `ecosw` get their own `(e, omega)` expressions** on a V_c/V_e orbit, because their usual forms consume the sqrt(e) pair -- which such an orbit *reports*, and a reported element is consumed by nothing. `calc_tp_from_ecc` is also strictly better behaved: writing the true anomaly at conjunction as `f = pi/2 - omega` cancels the `sqrt(e)` factor, removing both of `calc_tp`'s singularities at `e = 0` (review 1.8.2) -- which the mixture had made reachable *systematically*, since an unphysical branch clips to exactly zero. It agrees with `calc_tp` up to a whole period, which every consumer is invariant to.

## The transit-chord parameterization (`fitchord`)

The geometric half of the same method, and the other half of the pair the paper validated. `fitchord: true` samples the **transit chord** -- `sqrt((1 + p)^2 - b^2)` in units of `R_*`, the length of the planet's sky-projected path across the disc -- and derives `cos i` from it, per orbit, through `Orbit.INC_MODE_TABLE`. The reason is the duration: `T ~ (P/pi)(1/a_R) * chord * (V_c/V_e) / sin i`, so the chord and V_c/V_e are what a transit measures, while `cos i` reaches it only through `b = kappa cos i` with `kappa = a_R (1-e^2)/(1 + e sin omega)` itself fitted.

- **The inversion is a square root, so there is no mixture** -- one branch, unlike the eccentricity half's quadratic. What the chord *cannot* recover is the **sign** of `cos i` (a transit at `i` and at `180 - i` is the same transit), and that is not a root choice but the orbit's existing `i180:` convention: it travels into `calc_cosi_from_chord` as the `chord_sign` context node. Sampling it would reintroduce exactly the piecewise-constant coordinate the V_c/V_e half avoided. Where astrometry is also present -- which *measures* that sign -- `fitchord` warns that it is restricted to one branch.
- **The shield discipline is shared**: the radicand `(1+p)^2 - chord^2` is floored *inside* the sqrt (so a NaN is unbuildable and a chord past `1+p` gives a central transit, not a crash), while the **unfloored** radicand drives `orbit.chord_geometry`, a soft bound whose gradient points back to a geometry that transits.
- **The Jacobian keeps the prior on the inclination isotropic**, and as with V_c/V_e the sign IS the term: uniform-in-chord induces `p(cos i) = |d(chord)/d(cos i)|`, which vanishes at a central transit and diverges at a grazing one, so `Orbit._add_chord_terms` adds **minus** `physics.chord_log_jacobian`. Pinned by measuring the implied density on `cos i` for flatness, plus a finite-difference check of the magnitude -- deliberately two tests, because the finite difference passes under either sign. Applied as a factor **independent** of the eccentricity half's (the paper's eq 6 is the joint determinant; their product is it), which is what lets either half be switched on alone.
- **A chord needs a radius ratio, so not every orbit has one.** `chord` is INACTIVE (pinned, no potential, no table row) on an orbit whose companion group holds no planet or SEVERAL -- two planets sharing an orbit have two different chords, and an explicit `fitchord: true` there raises rather than picking one -- and also on any orbit in a system with **no transit data at all**, where the quantity is arithmetic rather than a result. `examples/GaiaBH1` is why that second condition exists: it models a black hole as a `planet` block, so "has a planet" is true and "could transit" is emphatically not.
- **`cos i` is DERIVED, not reported**, the opposite of the sqrt(e) pair on a V_c/V_e orbit -- the transit model consumes it (through `planet.b`), which is precisely what role 3 forbids. The chord is the reported one on a `cosi` orbit.
- **The seed bridge is a small solver, and `a/R*` is now a first-class engine quantity** -- those are two halves of one story, told in the order it happened. The first version of this bridge had to recompute Kepler's third law by hand because **nothing resolved `a/R*`**: `planet.ar` comes from `planet.a`, which comes from Kepler, and the engine had a relation for neither. That gap had already been worked around once, in `Planet._initial_semimajor_axes`. So the gap was closed instead -- `planet/symbolic_physics.py` now states the three relations `physics.py` already computed (`m_total = m_p + m_*`, Kepler for `a`, `ar = a/R_*`), all three at `rank: 5` so Condition B rewrites *them* and never the mass, radius or period they come from (they are derived Parameters; a seed on one cannot reach the model anyway). Consequences worth knowing: `prepare()` got **faster** (2.8 s -> 2.0 s on kelt17, because resolving `ar` early also unblocks `esinw` and takes an iteration out of the loop), `Planet._initial_semimajor_axes` is now a read of `self.a.initval` rather than a second copy of Kepler, and a user's `planet.ar` seed is finally *meaningful to the engine* rather than silently inert.
- **The chord itself is still a solver, on measured grounds.** With `ar` resolved the obvious next line is the relation `chord^2 + b^2 = (1 + p)^2`, and it works -- but it costs **+7.6 s of sympy per System** (2.0 s -> 9.6 s on kelt17), because the equation is quadratic in the chord and transcendental in `omega`, and the engine attempts every unresolved symbol in it. `planet.log_q` carries a solver for exactly this reason ("so the inversion never reaches `sp.solve`"), and this one is now ten lines that read the engine's own `ar` and `esinw`, so no physics is duplicated in it either. Verified: `cos i = 0.089` -> `chord = 0.98409`, the same value the relation gave. The reverse direction is deliberately absent: where `cos i` is sampled the chord is a reported *output*, and where the chord is sampled a user's seed lands on it directly.
- **A circular orbit had no `omega` at all, and that was a live bug.** `Eq(omega, atan2(sesinw, secosw))` is undefined when the sqrt(e) pair is pinned at zero -- which is how a circular fit is written (`examples/kelt17`) -- so the engine left `omega` unresolved forever, and with it `esinw`, `ecosw` and V_c/V_e's reported start. Meanwhile the RUNTIME has always had a convention there: `physics.calc_omega` returns `pi/2`, "so the RV phase stays perfectly aligned". The engine and the model therefore disagreed about `omega` for every circular fit. `orbit/symbolic_physics.py`'s `omega_solver` states that convention where the engine can use it, for the exactly-zero case only (anywhere else the relation is well posed and must be left alone). It moves no logp -- these are all derived quantities -- but kelt17's reported `vcve` start goes from the unsolved default 0.99 to the correct 1.0, and its `omega` from unresolved to `pi/2`.
- **`chord`'s bounds** are `[0, 2]`: the image of the radius-ratio cap, as `vcve`'s is the image of `MAX_ECC`. It carries `rank: 5` for the same reason `vcve` and `planet.log_q` do -- the engine's Condition B must rewrite the chord, never `cos i`, `a/R*`, `p` or the eccentricity.

**The transit-only default.** An orbit that a transit measures and *nothing else* does gets **both** halves turned on by itself (`Orbit._transit_only`, from the shared `Orbit.amplitude_constrained_orbits` predicate that `Planet._mass_constrained` also asks -- the two must never disagree about what "measured by RVs" means). They flip together because that is the pair the paper validated; `fitvcve: false` carries `fitchord` with it, unless `fitchord` was named explicitly. The flip is logged per orbit with the key that turns it off. **No shipped example moves**: all six transit examples also have RVs, so the only demonstration is `examples/hat3_transitonly.yaml` -- hat3 with the RVs removed, which also flips `planet.mass` to `log_q` and turns Chen on, both pre-existing defaults for that topology.

The only thing `Orbit._reject_wip_parameterizations` still refuses is a params entry naming `orbit.<name>.b`, which would otherwise be silently ignored: the impact parameter is `planet.<name>.b` and the scaled semi-major axis is `planet.<name>.ar`. Only the **last** dotted segment selects a parameter, so an orbit *called* `b` (kelt4) is untouched. Tests: `tests/test_vcve.py`, `tests/test_chord.py`, `tests/test_wip_guards.py`.
