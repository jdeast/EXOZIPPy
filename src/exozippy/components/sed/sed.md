# Bands, filters, limb darkening, and the SED

`src/exozippy/components/band/` carries filter identity and limb darkening;
`src/exozippy/components/sed/` carries the broadband photometry, the bolometric-correction
grid and the cross-component flux predictions.

Read this before touching limb darkening, filter resolution, the BC grid or an SED flux
hook. Related: `src/exozippy/components/instrument.md` (the instruments that reference a
band), `src/exozippy/components/mulensing/mulensing.md` (the `zeropoint` consumer),
`src/exozippy/components/parameter.md` (how the `loggsed` barrier reports itself).

## Bands, filters, and SED flux constraints

The Band component is the single carrier of filter identity and limb darkening: instruments (`transit`, `mulensinstrument`, optionally `astrometryinstrument`) reference a `band:` block by name; each band's `filter:` string is resolved through the shared alias table (`src/exozippy/filters/filternames.txt`, columns Keivan/MIST/Claret/SVO/VOID) into canonical names at load time. Transit LD (q1/q2/u1/u2) lives on Band, not on the transit component.

`ld_law:` is `quadratic` (Kipping q1/q2, u1/u2 derived) or `linear` (u1 sampled, **no `u2`** -- its second coefficient is exactly 0). An unrecognized spelling raises at load; **bands may declare different laws**, expressed through the per-element roles (`Band.LD_MODE_TABLE`, fed to `parameterization.mode_manifest`): `u1` is derived on the quadratic bands and sampled on the linear ones, while `q1`/`q2`/`u2` are INACTIVE on a linear band -- not parameters of it, so they are pinned (u2 at exactly 0, via `inactive_value`), carry no potential, and print no table row. A mixed system used to be a hard **error**, because `Parameter.build_pymc` derived a whole vector or none of it; before that, `any(law != "linear")` chose quadratic for everyone and silently gave a declared-linear band a free `u2`. The documented workaround (quadratic everywhere with the linear bands' `q2` pinned at 0.5) is no longer needed and its prior-in-q1-rather-than-u1 cost is gone. Which coordinate the unread-band autopin pins is therefore per band too (`Band.LD_SAMPLED_PARAMS`): a `sigma` on a derived element is a silent no-op, so pinning `u1` on a quadratic band would pin nothing. **Every consumer of `u2` must still guard with `"u2" in band.manifest`** and fall back to `pt.zeros_like(u1)` -- that case is now "every band is linear", where the parameter does not exist at all (`mode_manifest` omits a parameter no instance uses); `transit.py` (both sites) and `rm.py` do. `limbdark.quad_limb_darkened_flux` needs no linear branch: the Green's-basis coefficients are exact at `u2 = 0`.

**A band whose limb darkening nothing reads pins it itself** (`Band.ld_consumers` / `_pin_unread_limb_darkening`, logged at INFO once per band). The complete consumer set is `transit` (unconditional -- any transit referencing the band), `mulensinstrument` (only when `lens.finite_source` is on; the magnification takes `u1` nowhere else), and an `rvinstrument` `rm:` block (its `rm_band`, or band 0 when unset -- `rm.resolve_rm_indices`); `astrometryinstrument`'s `band:` is **not** a consumer, it takes only the filter identity for the SED fluxfrac. The predicate is per band instance (one system can hold a transit band and a mulens-only band) and reads each consumer's raw `config`, not its parsed band map -- `MulensInstrument.band_map` is built in stage 3, so whether it exists yet depends on component ordering. The pin is `sigma = 0` on the **sampled** coordinates (q1/q2, or u1 under `ld_law: linear`) through the manifest `"overrides"` channel, which layers **under** the params file, so an explicit user entry still frees it. This is what makes declaring filter identity free: a `band:` block on a point-source microlensing fit used to add two RVs no likelihood term read (`examples/ob08092`: -5.23 nats at the start; now bit-for-bit identical to having no band block), and flipping `finite_source` is again a one-line edit rather than an edit plus remembering to add or remove two pins. Tests: `tests/test_band_autopin_ld.py`.

### Limb darkening is per (star, band), and the pairing is now explicit

Physically the coefficients belong to a (star, band) pair; in the code they live on the band **instance** alone, so two hosts sharing one band instance silently shared their limb darkening. The LOCKED design (`notes/ld_atm_prior.txt`, 2026-08-04) does **not** move to map-indexed LD vectors (`band.u1[ld_map]`) -- named blocks referencing a filter string are already legal, `band: [{name: I_A, filter: I}, {name: I_B, filter: I}]`, so a second instance is the spelling for a second star. What was missing was anything checking that the instance and its readers agree, and that is what `Band._resolve_ld_stars` (stage 3) now does.

- **One predicate answers both questions.** `Band.ld_consumers(system)` returns an `LDConsumer(label, band, star)` per registration; `_ld_consumer_indices` is `{c.band for c in ...}`. The two questions -- *which* bands are read (the autopin) and *whose* limb darkening each read is -- were on their way to being answered by two lists, which is how a new consumer gets remembered in one place and forgotten in the other. Adding a consumer means adding it to `ld_consumers`, once.
- **`star_ndx:` on the band block stays the single source of truth** (it is what `transit._build_dilution` reads for the SED deblending host, its only consumer). What changed is that it is **validated** against the registrations when declared, and **derived** from them when not -- so the historical default of 0 no longer silently stands in for a source star that is really star 1.
- What each consumer registers: **transit** -> the host stars of the planets it models (`planet.star_ndx`); **mulensinstrument** -> the SOURCE star, `lens.source_map[0]`, and only under `finite_source` (a point source takes no limb darkening at all); **rvinstrument `rm:`** -> the primary star of the RM orbit.
- **A contradiction raises; an intrinsic ambiguity warns.** A consumer needing a star the band does not carry, or two consumers of one band needing different stars, raises and points at a second band block with the same filter -- advice the user can act on. A single transit light curve covering planets of several hosts only *warns*: one light curve models every planet, so its limb darkening is ambiguous no matter how many band blocks exist, and refusing would gate a configuration with no legal spelling. Set `star_ndx:` there to say which host is meant.
- Model-inert on the shipped set: start logp and the free-RV set are bit-identical on all five examples that exercise it, and the only movement anywhere is `band.star_indices` going 0 -> the source star on the three finite-source microlensing fits (`KMT-2019-BLG-1806` and `ogle0383` to 1 `'Source'`, `ob161003` to 2 `'SourceA'`), none of which has a transit to read it. That correction is the point: those bands' coefficients describe the source's atmosphere, and the value they carried named the lens.

This is the prerequisite for the limb-darkening atmosphere prior (review 8.5.2), which has to know whose (teff, logg, feh, av) a band's coefficients are being predicted from. Tests: `tests/test_band_ld_star.py`.

Everything that turns those (u1, u2) into an occultation flux goes through the one shared helper `components/limbdark.py:quad_limb_darkened_flux(b, r, u1, u2)` -- `transit.py` (likelihood and plotting) and `rm.py` (the Rossiter-McLaughlin blocked flux). Never open-code the dot product: exoplanet-core's `quad_solution_vector` returns `s` in starry's Green's basis, so the coefficients are `c0 = 1 - u1 - 1.5*u2`, `c1 = u1 + 2*u2`, `c2 = -0.25*u2` (Agol, Luger & Foreman-Mackey 2020), **not** the mu-power `[1 - u1 - u2, u1, u2]`. The naive basis is exact at `u2 = 0` and silently wrong otherwise -- rm.py carried it undetected (up to ~87% of the transit depth at u2 = 0.3, with flux > 1 near egress) precisely because every test that exercised it used u2 = 0. `transit/physics.py:calc_planet_visible` is the one deliberate exception: it occults the *planet* by the star, a uniform disk where `s0/pi` is the whole answer. Tests: `tests/test_limbdark.py` pins the helper against brute-force disk integration.

The SED component supports n stars: each `.sed` filter row's `photType: {pos: [...], neg: [...]}` (with `blend:` as an alias for `pos`; entries are star names or indices) builds a +1/0/-1 blend matrix; blended rows are flux sums, `neg` makes the row a differential magnitude (`-2.5*log10(F_pos/F_neg)`). An empty `filters:` list is legal — the SED then only serves cross-component flux predictions (`predict_star_appmag`, `predict_blend_appmag`, `predict_flux_fraction`). BC tables for missing filters auto-generate from the model spectra (`components/sed/make_bc.py`, CLI `scripts/make_bc_tables.py`).

**The BC grid's support is enforced on all four of its axes, and the fourth one is the interesting case.** `SED._inject_grid_bounds` reads the grid's (teff, logg, feh, av) extents at `__init__` and puts them on star Parameters through `ConfigManager.add_override`. `teffsed`, `feh` and `av` are **sampled**, so two finite bounds put them on the logit transform and the grid extent is their exact support -- they cannot leave the grid at all. `loggsed` is **derived** (`calc_logg_from_logmass` on `logmass` and `radiussed`), so the same bound becomes the house soft barrier `Parameter.build_pymc` adds for a derived element, with the steepness **measured** at startup by `whitening.measure_barrier_scales` and pinnable per element with `bound_scale:`.

- `star.loggsed` exists as a Parameter *for that reason*. It was an inline expression inside `SED._predicted_appmag_node` until 2026-08, so there was nothing for the override channel to bound -- and **bounding `logmass` and `radiussed` separately does not bound their combination**, which is what `loggsed` is. `_predicted_appmag_node` and `compile_plotters` now read `star.loggsed.value`; the quantity the barrier restrains and the quantity the interpolator is handed must be the same node.
- **The barrier is a restoring force, not a wall, because the interpolator never fails.** `bc_grid.RegularGridInterpolator` is built with `fill_value=None`, so it computes `out_of_bounds` and then **discards** it: an off-grid point is **linearly extrapolated off the edge cell** -- not NaN, not `-inf`. What was missing was never a rejection but a gradient pointing back, and a `-inf` wall would have been strictly worse (NUTS has nothing to follow). Off-grid logp and dlogp are finite in both the C and the JAX backends; verified by sampling from a deliberately off-grid start with `nuts_sampler="numpyro"`, which pulls the chain back onto the grid.
- **On-grid fits are untouched**: five of the seven shipped SED configs keep a bit-identical start logp and the two kelt4 ones move by 1-2 ulp (1.5e-11 out of 8e4) from graph reassociation.
- **`examples/gj1214` starts OFF the grid, and ships a deliberately softened barrier because of it.** Its M dwarf sits at `loggsed = 5.0223` against a NextGen logg ceiling of 5.0, so that fit has been scored on extrapolated bolometric corrections since it shipped. NextGen is the only BC grid whose tables ship, so there is no drop-in replacement today, and **a modestly extrapolated correction beats refusing to fit** as long as the caveat is explicit. Its params file therefore carries `star.A.loggsed: {bound_scale: 25.0}` -- transition width 0.25 dex, i.e. **half a NextGen logg cell**, slope 17.6 nats/dex -- which costs the start 0.91 nats instead of the measured barrier's 434, while still charging 4.41 nats half a cell past the edge and 8.80 a full cell past. The half-cell anchor is the point: linear extrapolation past the edge reuses the last cell's slope and its error grows roughly quadratically, so half a cell out is where it becomes comparable to the in-grid interpolation error and a full cell out is where it clearly exceeds it. Do not pick a scale that zeroes the penalty -- that is silent extrapolation again.
- **The off-grid notice keys on the VALUE, never on the barrier being active**, so softening cannot silence it; `SED._declare_grid_support` warns per star and `_barrier_advice` switches the second half of the message between "measured, so effectively clamped to the edge -- here is `bound_scale:`" and "DELIBERATELY WIDENED, admitted at N nats", quoting the penalty it actually computes from the potential's own formula. A warning and not a raise precisely because such fits have been running. One known gap: `mkparam` carries `bound_scale` across for parameters it emits, but a **derived** parameter gets no entry at all, so a `bound_scale` on `loggsed` is lost in a generated restart file -- the gj1214 params file says so next to the key.
- The barrier **declares itself** to the reporting layer (`supersedes_bounds=True`), because `_own_prior_str` reports a derived parameter carrying two finite bounds as `U(lo, hi)` -- exactly the prior a barrier is not. See "Reporting component-added priors" in `src/exozippy/components/parameter.md`, including why it passes a non-default `support_phrase`.

Tests: `tests/test_sed_grid_barrier.py`.

**The SPECTRA grid behind the figure is a different grid from the BC grid, and it is not a full rectangle.** `models/NextGen/BCs/NextGen.spectra.csv` spans logg -0.5 to 6.0 where the BC tables stop at 5.0, and holds 12796 of its 23716 rectangle nodes. `NextGenPlot._interp_spectra` brackets a draw blindly with `_findNearestGridPoints`, so two things follow. Off the whole spectra grid it **extrapolates** off the bracketing cell (`interpn(..., bounds_error=False, fill_value=None)`) and warns per axis -- the same ruling as the BC interpolator, and necessary because scipy's default `bounds_error=True` raised inside `SED.plot`, which `run.py` calls **unguarded** before sampling. A bracketing node the grid does not contain **raises**: leaving its flux at the initialized 0.0 behind a `warnings.warn` (what this did until 2026-08) interpolates the published figure against a fabricated zero. Inside the BC grid's own box -- teff [2600, 10000], logg [0, 5], feh [-4, 0.5], where the three sampled axes are hard-bounded -- the shipped grid is complete, so neither fires; above logg 5.0, which `examples/gj1214`'s start already exceeds, 385 of the 660 (teff, feh) nodes on the logg = 5.5 plane are absent. Tests: `tests/test_sed_spectra_plot.py`.

**The `teffsed`/`fbolsed` floor potentials keep their `-log(sigma)`** (`SED._fractional_floor_logp`). Their sigma is a *fraction of the star's own* teff/fbol, i.e. a function of a sampled parameter, which is precisely the case where the house convention keeps the normalization -- `components/relations.py:_add_penalty`, where mann keeps it for a fractional sigma and torres drops it only because its scatter is a constant in dex. Dropped, the term leaves a `d/dx log(x)` tilt worth exactly one nat of free likelihood per e-fold, pushing teff and fbol up for no physical reason. The 2pi is dropped, matching `_add_penalty`. The term is unit-dependent and so mostly a large constant (`fbol ~ 5e-10` internally): it moved `examples/gj1214`'s start logp by +20.874 and `examples/kelt4`'s by +62.256. Tests: `tests/test_sed_floor_normalization.py`.

EXOFASTv2 has the same defect, so this is a BUG FIX rather than a divergence, and it should not be advertised as a parity break: EXOFASTv2's sigma here is a fraction too, and it drops the normalization anyway. Dropping additive constants is right when sigma is constant -- a term that does not vary cannot move a posterior -- and wrong when sigma is a fraction of a sampled quantity, which is the case in both codes. Nor is a note of that kind wanted here in any case: the whole SED -> bolometric-correction path already departs from EXOFASTv2, so flagging one term as THE parity break would imply the rest is closer than it is.

**`sed/symbolic_physics.py` is conditional on the `sed:` block.** It sets `comp_key = "star"` so its two defaulting relations (`teffsed = teff`, `radiussed = radius`) instantiate once per star -- but `Star.register_parameters` declares those parameters only inside its `if in_system("sed")` branch, so registering the relations regardless put two phantom leaf symbols per star, each with a default-armor value and a ledger row, into every non-SED config. The mechanism is one optional module-level hook, `relations_apply(system_config)`, checked by `ConfigManager`'s `symbolic_physics.py` walk; absent, relations always apply (the right default for a file keyed on its own block). It is the symbolic-side analogue of the per-child `JITTER_RELATIONS` registration: which configs a relation applies to is a fact only the relation's own file knows. Tests: `tests/test_sed_relations_conditional.py`.

Filter profiles and stellar-model data are **package-level**, not SED-component-level, because the MIST evolutionary grids need them too: `src/exozippy/filters/` (profiles, `filternames.txt`, `filter_magsys.txt`) and `src/exozippy/models/` (`extinction_law.ascii`, plus one subdirectory per model family -- `NextGen/BCs/{facility}/`, `MIST/MISTv1.2/BCs/`, `MIST/MISTv2.5/EEPs/`). `bc_grid.DEFAULT_FILTER_ROOT` / `DEFAULT_MODEL_ROOT` are the two anchors; the SED's `model_root:` config key overrides the latter. The gitignored NextGen spectra CSVs cache under `models/NextGen/BCs/` alongside the tables they generate.

**`model_root:` must reach every consumer, and two of them used to ignore it.** `SED._ensure_model_data` passed `DEFAULT_MODEL_ROOT` to `make_bc.ensure_model_data`, which takes a root -- so a configured root downloaded 259 MB of spectra into a directory nothing reads and then downloaded them again. And the model's plot class was imported through the fixed dotted namespace `exozippy.models.<model>.BCs.plot`, which can only resolve inside the installed package: `sed.load_model_plot_module` keeps the dotted import for a path inside the package (so module identity matches a normal import) and spec-loads anything else, caching it in `sys.modules`. `sed.plot_class_from` then selects the one **subclass of `components.sed.plot.Plot`** defined in the module, raising on zero or several -- the old ast-parse-and-take-the-first-`ClassDef` silently instantiated a helper class defined above it. `plot.Plot` reads the spectra, the wavelength grid and the grid yaml under `self.model_root`; its fall back to the packaged NextGen spectra survives but is an explicit `is_file()` test plus a warning saying the *figure's* curve is a NextGen spectrum while the fit's BCs were not, in place of a bare `except:` + `print()`. Tests: `tests/test_sed_model_root.py`.

**A band-referenced filter whose facility has no BC tables is generated, not dropped** (`SED._collect_band_filters`). `build_bc_grid` already auto-generates for a filter listed in the `.sed` file, and for a missing column inside an existing facility; the band filter with a missing facility was the one case that silently dropped the SED flux constraint it exists to carry (the mulensing zeropoint tie, the transit dilution, the astrometry fluxfrac). The cost that comes with letting it through: a band filter whose tables genuinely cannot be built now fails the fit rather than quietly weakening it -- as a `.sed` filter already does. Still skipped, with a warning that says why: a label with no SVO identity at all, neither in the alias table nor SVO-shaped (`examples/gj1214`'s `MIRILRS`), for which there is no bandpass to synthesize from. Tests: `tests/test_sed_band_filters.py`.

**Filter profiles are read from the package and written to the machine cache.** `filters/filter.py` used to write its downloaded `.filter` pickles into the installed package directory -- a `PermissionError` on a read-only site-packages and source-tree litter in a dev checkout, and its `os.makedirs` was unconditional, so even READING a shipped profile created a facility directory there. Reads now try the shipped package directory first (20 profiles ship) and `filter_cache_root()` -- the `$XDG_CACHE_HOME/exozippy/filters` sibling of `utilities/zenodo.py`'s download cache, honouring the same `EXOZIPPY_CACHE_DIR` switch -- second; a download goes to the cache, falling back to the package directory when the cache is switched off (which is what "off" meant before it existed) and to a temp directory when neither is writable. The SVO zeropoints those downloads scrape are validated before they are believed: HTTP status, table count, that the rows read are LABELLED as zeropoints, that the unit cell names the expected quantity, and that each value is `--` or a finite positive float. Every failure raises, and raising is the point -- the scrape happens inside `_set_attrs`, before `_create_filter_file`, so refusing is refusing to cache a wrong number forever. Tests: `tests/test_filter_cache.py`, `tests/test_filter_svo_zeropoints.py`. `bc_grid._load_alias_table` and `plot._read_spectra_csv` are both cached on `(path, mtime, size)` -- the 250 MB spectra table was re-read and re-json-parsed (5.5 s) on every `Plot` construction; tests `tests/test_filter_alias_cache.py`, `tests/test_sed_spectra_cache.py`.

Cross-component hooks when a `sed:` block exists: `mulensinstrument` ties each light curve's `f_source` to the SED-predicted source mag through a per-lightcurve `zeropoint` (default 0 +/- 0.2 mag; `sed_constrains_blend: true` opts f_blend in); `transit` dilutes depths by the host's SED flux fraction in the band; `astrometryinstrument` derives its photocenter `fluxfrac` from the SED when given `band:` + `companion_star_ndx:`.

`zeropoint` is an ordinary **derived** `Parameter` (`mulensinstrument.zeropoint`, one element per light curve, `force_node: True`), not a hand-built node: `physics.calc_zeropoint` is its expression and `Parameter.build_pymc`'s derived-with-sigma branch supplies the Gaussian. **Derived, never sampled** -- `zp = m_SED + 2.5*log10(f_source)` is determined exactly by f_source and the SED, and no data constrains it separately, so sampling it would add a dimension identified only by its own prior. Until 2026-08 it was not a Parameter at all: `_build_sed_flux_constraint` resolved the config block itself and read only `mu`/`sigma`, so a user's `initval` (and their `unit:`) were silently inert. The **node layout** changed with it and the content did not: the per-instrument `mulensinstrument.<name>.zeropoint` Deterministics became the one vector `mulensinstrument.zeropoint`, and the per-instrument `.zeropoint_prior` potentials became the one `gaussian_prior.mulensinstrument.zeropoint`. Summing N scalar potentials as one vector instead moves a start logp by ~1 ulp (measured: exactly 1 on KMT-2019-BLG-1806), and nothing else. Three deps are injected as **context nodes** by `MulensInstrument.add_parameter` (`context_dep_names`, the `Orbit` group-mass idiom): `m_source_pred` (the SED forward model, which cannot be spelled as a manifest dep), plus `zp_center`/`sed_constrained`. The mask exists because a light curve with no `band:` or whose filter is missing from the BC grid has nothing to tie to -- `calc_zeropoint` returns `zp_center` there, so its Gaussian penalty is exactly zero, reproducing the old loop's `continue`. It is a `pt.switch` on an explicit 0/1 mask and **not** a NaN test, since switch's gradient multiplies the unselected branch by zero and `0 * NaN` is NaN. `sigma: 0` still raises (in `_zeropoint_context`) rather than falling through to `build_pymc`'s generic "sigma=0 has no effect on a derived parameter" warning. Because the SED forward model is read through `predict_*` rather than declared as a dep, `SED._predicted_appmag_node` lazily materializes the star Parameters it needs (`SED._ensure_star_nodes`) -- the zeropoint expression is built at stage 6 and can get there first.
