# Bands, filters, limb darkening, and the SED

`src/exozippy/components/band/` carries filter identity and limb darkening;
`src/exozippy/components/sed/` carries the broadband photometry, the bolometric-correction
grid and the cross-component flux predictions.

Read this before touching limb darkening, filter resolution, the BC grid or an SED flux
hook. Related: `src/exozippy/components/instrument.md` (the instruments that reference a
band), `src/exozippy/components/mulensing/mulensing.md` (the `zeropoint` consumer),
`src/exozippy/components/parameter.md` (how the `loggsed` barrier reports itself).

## Bands, filters, and SED flux constraints

The Band component is the single carrier of filter identity and limb darkening: instruments (`transit`, `mulensinstrument`, optionally `astrometryinstrument`) reference a `band:` block by name; each band's `filter:` string is resolved through the shared alias table (`src/exozippy/filters/filternames.txt`, columns Keivan/MIST/Claret/SVO/VOID) into canonical names at load time. Transit LD (q1/q2/u1/u2) lives on Band, not on the transit component.

`ld_law:` is `quadratic` (Kipping q1/q2, u1/u2 derived) or `linear` (u1 sampled, **no `u2`** -- its second coefficient is exactly 0). An unrecognized spelling raises at load; **bands may declare different laws**, expressed through the per-element roles (`Band.LD_MODE_TABLE`, fed to `parameterization.mode_manifest`): `u1` is derived on the quadratic bands and sampled on the linear ones, while `q1`/`q2`/`u2` are INACTIVE on a linear band -- not parameters of it, so they are pinned (u2 at exactly 0, via `inactive_value`), carry no potential, and print no table row. A mixed system used to be a hard **error**, because `Parameter.build_pymc` derived a whole vector or none of it; before that, `any(law != "linear")` chose quadratic for everyone and silently gave a declared-linear band a free `u2`. The documented workaround (quadratic everywhere with the linear bands' `q2` pinned at 0.5) is no longer needed and its prior-in-q1-rather-than-u1 cost is gone. Which coordinate the unread-band autopin pins is therefore per band too (`Band.LD_SAMPLED_PARAMS`): a `sigma` on a derived element is a silent no-op, so pinning `u1` on a quadratic band would pin nothing. **Every consumer of `u2` must still guard with `"u2" in band.manifest`** and fall back to `pt.zeros_like(u1)` -- that case is now "every band is linear", where the parameter does not exist at all (`mode_manifest` omits a parameter no instance uses); `transit.py` (both sites) and `rm.py` do. `limbdark.quad_limb_darkened_flux` needs no linear branch: the Green's-basis coefficients are exact at `u2 = 0`.

**A band whose limb darkening nothing reads pins it itself** (`Band._ld_consumer_indices` / `_pin_unread_limb_darkening`, logged at INFO once per band). The complete consumer set is `transit` (unconditional -- any transit referencing the band), `mulensinstrument` (only when `lens.finite_source` is on; the magnification takes `u1` nowhere else), and an `rvinstrument` `rm:` block (its `rm_band`, or band 0 when unset -- `rm.resolve_rm_indices`); `astrometryinstrument`'s `band:` is **not** a consumer, it takes only the filter identity for the SED fluxfrac. The predicate is per band instance (one system can hold a transit band and a mulens-only band) and reads each consumer's raw `config`, not its parsed band map -- `MulensInstrument.band_map` is built in stage 2, so whether it exists yet depends on component ordering. The pin is `sigma = 0` on the **sampled** coordinates (q1/q2, or u1 under `ld_law: linear`) through the manifest `"overrides"` channel, which layers **under** the params file, so an explicit user entry still frees it. This is what makes declaring filter identity free: a `band:` block on a point-source microlensing fit used to add two RVs no likelihood term read (`examples/ob08092`: -5.23 nats at the start; now bit-for-bit identical to having no band block), and flipping `finite_source` is again a one-line edit rather than an edit plus remembering to add or remove two pins. Tests: `tests/test_band_autopin_ld.py`.

Everything that turns those (u1, u2) into an occultation flux goes through the one shared helper `components/limbdark.py:quad_limb_darkened_flux(b, r, u1, u2)` -- `transit.py` (likelihood and plotting) and `rm.py` (the Rossiter-McLaughlin blocked flux). Never open-code the dot product: exoplanet-core's `quad_solution_vector` returns `s` in starry's Green's basis, so the coefficients are `c0 = 1 - u1 - 1.5*u2`, `c1 = u1 + 2*u2`, `c2 = -0.25*u2` (Agol, Luger & Foreman-Mackey 2020), **not** the mu-power `[1 - u1 - u2, u1, u2]`. The naive basis is exact at `u2 = 0` and silently wrong otherwise -- rm.py carried it undetected (up to ~87% of the transit depth at u2 = 0.3, with flux > 1 near egress) precisely because every test that exercised it used u2 = 0. `transit/physics.py:calc_planet_visible` is the one deliberate exception: it occults the *planet* by the star, a uniform disk where `s0/pi` is the whole answer. Tests: `tests/test_limbdark.py` pins the helper against brute-force disk integration.

The SED component supports n stars: each `.sed` filter row's `photType: {pos: [...], neg: [...]}` (with `blend:` as an alias for `pos`; entries are star names or indices) builds a +1/0/-1 blend matrix; blended rows are flux sums, `neg` makes the row a differential magnitude (`-2.5*log10(F_pos/F_neg)`). An empty `filters:` list is legal — the SED then only serves cross-component flux predictions (`predict_star_appmag`, `predict_blend_appmag`, `predict_flux_fraction`). BC tables for missing filters auto-generate from the model spectra (`components/sed/make_bc.py`, CLI `scripts/make_bc_tables.py`).

**The BC grid's support is enforced on all four of its axes, and the fourth one is the interesting case.** `SED._inject_grid_bounds` reads the grid's (teff, logg, feh, av) extents at `__init__` and puts them on star Parameters through `ConfigManager.add_override`. `teffsed`, `feh` and `av` are **sampled**, so two finite bounds put them on the logit transform and the grid extent is their exact support -- they cannot leave the grid at all. `loggsed` is **derived** (`calc_logg_from_logmass` on `logmass` and `radiussed`), so the same bound becomes the house soft barrier `Parameter.build_pymc` adds for a derived element, with the steepness **measured** at startup by `whitening.measure_barrier_scales` and pinnable per element with `bound_scale:`.

- `star.loggsed` exists as a Parameter *for that reason*. It was an inline expression inside `SED._predicted_appmag_node` until 2026-08, so there was nothing for the override channel to bound -- and **bounding `logmass` and `radiussed` separately does not bound their combination**, which is what `loggsed` is. `_predicted_appmag_node` and `compile_plotters` now read `star.loggsed.value`; the quantity the barrier restrains and the quantity the interpolator is handed must be the same node.
- **The barrier is a restoring force, not a wall, because the interpolator never fails.** `bc_grid.RegularGridInterpolator` is built with `fill_value=None`, so it computes `out_of_bounds` and then **discards** it: an off-grid point is **linearly extrapolated off the edge cell** -- not NaN, not `-inf`. What was missing was never a rejection but a gradient pointing back, and a `-inf` wall would have been strictly worse (NUTS has nothing to follow). Off-grid logp and dlogp are finite in both the C and the JAX backends; verified by sampling from a deliberately off-grid start with `nuts_sampler="numpyro"`, which pulls the chain back onto the grid.
- **On-grid fits are untouched**: five of the seven shipped SED configs keep a bit-identical start logp and the two kelt4 ones move by 1-2 ulp (1.5e-11 out of 8e4) from graph reassociation.
- **`examples/gj1214` starts OFF the grid, and ships a deliberately softened barrier because of it.** Its M dwarf sits at `loggsed = 5.0223` against a NextGen logg ceiling of 5.0, so that fit has been scored on extrapolated bolometric corrections since it shipped. NextGen is the only BC grid whose tables ship, so there is no drop-in replacement today, and **a modestly extrapolated correction beats refusing to fit** as long as the caveat is explicit. Its params file therefore carries `star.A.loggsed: {bound_scale: 25.0}` -- transition width 0.25 dex, i.e. **half a NextGen logg cell**, slope 17.6 nats/dex -- which costs the start 0.91 nats instead of the measured barrier's 434, while still charging 4.41 nats half a cell past the edge and 8.80 a full cell past. The half-cell anchor is the point: linear extrapolation past the edge reuses the last cell's slope and its error grows roughly quadratically, so half a cell out is where it becomes comparable to the in-grid interpolation error and a full cell out is where it clearly exceeds it. Do not pick a scale that zeroes the penalty -- that is silent extrapolation again.
- **The off-grid notice keys on the VALUE, never on the barrier being active**, so softening cannot silence it; `SED._declare_grid_support` warns per star and `_barrier_advice` switches the second half of the message between "measured, so effectively clamped to the edge -- here is `bound_scale:`" and "DELIBERATELY WIDENED, admitted at N nats", quoting the penalty it actually computes from the potential's own formula. A warning and not a raise precisely because such fits have been running. One known gap: `mkparam` carries `bound_scale` across for parameters it emits, but a **derived** parameter gets no entry at all, so a `bound_scale` on `loggsed` is lost in a generated restart file -- the gj1214 params file says so next to the key.
- The barrier **declares itself** to the reporting layer (`supersedes_bounds=True`), because `_own_prior_str` reports a derived parameter carrying two finite bounds as `U(lo, hi)` -- exactly the prior a barrier is not. See "Reporting component-added priors", including why it passes a non-default `support_phrase`.

Tests: `tests/test_sed_grid_barrier.py`.

Filter profiles and stellar-model data are **package-level**, not SED-component-level, because the MIST evolutionary grids need them too: `src/exozippy/filters/` (profiles, `filternames.txt`, `filter_magsys.txt`) and `src/exozippy/models/` (`extinction_law.ascii`, plus one subdirectory per model family -- `NextGen/BCs/{facility}/`, `MIST/MISTv1.2/BCs/`, `MIST/MISTv2.5/EEPs/`). `bc_grid.DEFAULT_FILTER_ROOT` / `DEFAULT_MODEL_ROOT` are the two anchors; the SED's `model_root:` config key overrides the latter. The gitignored NextGen spectra CSVs cache under `models/NextGen/BCs/` alongside the tables they generate.

Cross-component hooks when a `sed:` block exists: `mulensinstrument` ties each light curve's `f_source` to the SED-predicted source mag through a per-lightcurve `zeropoint` (default 0 +/- 0.2 mag; `sed_constrain_blend: true` opts f_blend in); `transit` dilutes depths by the host's SED flux fraction in the band; `astrometryinstrument` derives its photocenter `fluxfrac` from the SED when given `band:` + `companion_star_ndx:`.

`zeropoint` is an ordinary **derived** `Parameter` (`mulensinstrument.zeropoint`, one element per light curve, `force_node: True`), not a hand-built node: `physics.calc_zeropoint` is its expression and `Parameter.build_pymc`'s derived-with-sigma branch supplies the Gaussian. **Derived, never sampled** -- `zp = m_SED + 2.5*log10(f_source)` is determined exactly by f_source and the SED, and no data constrains it separately, so sampling it would add a dimension identified only by its own prior. Until 2026-08 it was not a Parameter at all: `_build_sed_flux_constraint` resolved the config block itself and read only `mu`/`sigma`, so a user's `initval` (and their `unit:`) were silently inert. The **node layout** changed with it and the content did not: the per-instrument `mulensinstrument.<name>.zeropoint` Deterministics became the one vector `mulensinstrument.zeropoint`, and the per-instrument `.zeropoint_prior` potentials became the one `gaussian_prior.mulensinstrument.zeropoint`. Summing N scalar potentials as one vector instead moves a start logp by ~1 ulp (measured: exactly 1 on KMT-2019-BLG-1806), and nothing else. Three deps are injected as **context nodes** by `MulensInstrument.add_parameter` (`context_dep_names`, the `Orbit` group-mass idiom): `m_source_pred` (the SED forward model, which cannot be spelled as a manifest dep), plus `zp_center`/`sed_constrained`. The mask exists because a light curve with no `band:` or whose filter is missing from the BC grid has nothing to tie to -- `calc_zeropoint` returns `zp_center` there, so its Gaussian penalty is exactly zero, reproducing the old loop's `continue`. It is a `pt.switch` on an explicit 0/1 mask and **not** a NaN test, since switch's gradient multiplies the unselected branch by zero and `0 * NaN` is NaN. `sigma: 0` still raises (in `_zeropoint_context`) rather than falling through to `build_pymc`'s generic "sigma=0 has no effect on a derived parameter" warning. Because the SED forward model is read through `predict_*` rather than declared as a dep, `SED._predicted_appmag_node` lazily materializes the star Parameters it needs (`SED._ensure_star_nodes`) -- the zeropoint expression is built at stage 5 and can get there first.
