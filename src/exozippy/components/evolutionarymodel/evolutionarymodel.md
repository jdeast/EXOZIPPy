# Evolutionary models (`components/evolutionarymodel/`, MIST tracks)

**The star side needed no edit when this landed, and still has none.** `star/defaults.yaml` carries the two coordinates an evolutionary track is indexed by -- `initfeh` (initial metallicity) and `eep` -- alongside the present-day `age` a track returns, and the `in_system("evolutionarymodel")` branch of `Star.register_parameters` declares all three, masked per star by the `mist:` / `parsec:` switches. Without an `evolutionarymodel:` key the branch never fires and neither entry is ever materialized: verified by dumping the fully resolved parameter state (values, bounds, units, provenance ranks, parameter list, manifests, derived set) of all 19 shipped example configs before and after the entries were added -- byte-identical, no new parameters.

**So the component declares NO parameters of its own** (empty manifest, potentials only, like `components/torres`). It samples `star.logmass`, `star.initfeh`, `star.eep`, `star.feh`, `star.radius`, `star.teff`, `star.age`; interpolates `(logmass, initfeh, eep)` over the MIST grid for `feh_mist`/`radius_mist`/`teff_mist`/`age_mist`; and ties each sampled quantity to its prediction with a Gaussian potential floored at EXOFASTv2's mass-dependent `percenterror`. Declaring its own `evolutionarymodel.<name>.initfeh`/`.eep` pair (what the first draft did) would leave the star's copies materialized, free, bounded and read by nothing -- two unconstrained nuisance dimensions per star, plus a second spelling for every user entry. One instance per star, `star:` + `constrain:`, via the `StellarRelation` mixin; `CONSTRAINABLE` is `(feh, radius, teff, age)` rather than `(mass, radius)`, declared through the mixin's `constrainable` class attribute so `_parse_constrain` and `constrain_schema_entry` stay one implementation.

- **The `mist:`/`parsec:` mask is a real per-element role, and it is NOT the same question this component answers.** `Star.register_parameters` masks `initfeh`/`eep`/`age` by `mist or parsec`, so a star that opted out is inactive -- no raw coordinate, no potential, no table row. But `mist:` DEFAULTS TO TRUE, so every star in a config carrying an `evolutionarymodel:` block is opted in by that default, whether or not any instance of this component names it. Those stars would get three free, bounded, likelihood-free parameters. `_pin_unmodeled_stars` pins them (`sigma: 0` through `ConfigManager.add_override`, so a user entry still frees them) on every star no instance names -- `Band._pin_unread_limb_darkening`'s precedent, for the same reason. The mechanisms compose rather than overlap: the mask answers "did this star ask for a track", the pin answers "did anything actually give it one", and `Star.structure_consumers` -- which is asked for this component's `star_indices`, the mann/torres idiom -- answers "does anything read radius/teff/feh". That last one read the `mist:` switches until it was corrected here, which left three likelihood-free dimensions on every star no block named. A block naming no star at all warns and pins everything rather than dying inside `pt.stack([])`.
- **Grid extents become bounds through `add_override`, never `user_params`** (`_inject_grid_bounds`, the SED's reasoning verbatim): `RegularGridInterpolator` is built with `fill_value=None` and linearly EXTRAPOLATES past its axis edges, so `star.logmass`/`initfeh`/`eep` are validity-limited to the loaded grid. Note the trimmed shipped grid spans initfeh `[-2.5, 0.5]`, not defaults.yaml's `[-4.0, 0.5]` -- the defaults.yaml bounds on `initfeh` and `eep` are **placeholders**.
- **`here_be_dragons` is EXTENDED at load over each track's unresolved-age tail** -- the one thing `mist_grid` rewrites. Where evolution outruns the model's timestep the tabulated ages come out equal, and the generator adds +1 yr to each successive duplicate to keep them increasing. When such a run ends just *before* the end of a track, the bumping lifts those ages above the genuinely-later unique ages that follow (hence the 16 backwards steps and the `+/-2**32` derivatives), **and the generator's counter skips those unique rows** -- so the flag falls back to 0 across exactly the worst part of the track. Track (90 solMass, -2.25 dex) counts from EEP 615, drops to 0 for EEP 618-631 (`dEEP_dage` up to 2e9), then resumes at 4. `_flag_from_first_unresolved_age` makes it a plain 1,2,3,... count from the first unresolved step to the end of the track: past that point the model is not tracking time properly whether or not a given row is a duplicate. Detection is a step of **exactly 1.0 yr** (or <= 0), never `<= 1.0` -- real fast evolution is dense in (0,1) yr from EEP 2 and the loose test would flag every massive track's whole PMS. Applied as an element-wise `maximum`, so it only ever raises the flag and **becomes a no-op once the generator does this itself, which is where the fix belongs**. On the shipped grid: 1158 rows raised, dragon coverage 6.03% -> 6.09%, every age decrease then inside a flagged tail, `here_be_dragons` monotone from its first flag on all 2223 tracks. `_unflagged_nonmonotone_tracks` warns about any decrease left outside a tail, which should never happen. `dEEP_dage` itself is NOT repaired -- it is genuinely ~3e3/yr at EEP 1 of a 110 solMass track, so no threshold separates real from meaningless; the Jacobian's clip bounds it instead.
- **The EEP -> age Jacobian is `-log|dEEP/dage|` with a two-sided CLIP** (`DEEP_DAGE_MIN`/`MAX`), which is what makes the flat prior `eep` gets for free from its logit transform a flat prior in AGE. Same sign as EXOFASTv2's `ageweight` (`chi2 -= 2*alog(da/dEEP)`); the yr -> Gyr rescale is an additive constant and is dropped. **The clip's upper end is load-bearing and a bare floor there is a bug**: the potential rewards a SMALL derivative, so the `1e-30` floor the first draft used was +69 nats of unbounded attraction toward a table defect, and it is reachable -- the tabulated derivative crosses zero between the `+/-2**32` entries on the non-monotonic-age tracks. That is the opposite problem from `calc_jitter`'s radicand floor (an infinite *gradient*), so do not transfer that precedent here.
- **`normalize=True` on all four penalties**, a deliberate departure from `massradius_mist.pro`'s bare chi2: every sigma is a function of sampled parameters (`mstar`, or the prediction itself), so `-log(sigma)` is not a constant. `components/mann`'s reasoning, not `components/torres`'s.
- **`feh_mist == 30.0` is DATA and must not be "repaired".** [Fe/H] is `log10(Z/X) - log10(Z/X)_sun`, which diverges as the surface hydrogen fraction X goes to zero; 30.0 is the stand-in the grid generator substitutes to dodge the divide-by-zero, and it means "this photosphere has essentially no hydrogen left" -- real, and reachable only in the highest-mass stars. Those rows carry `here_be_dragons > 0` because the track is less trustworthy there, not because the number is wrong. So a solar-metallicity star genuinely does not match such a track point and the ~5e5-nat feh penalty it earns is the correct answer. A version of `mist_grid` forward-filled the last "normal" value across those rows on the theory that 30.0 was an error sentinel; that fabricated a solar-metallicity prediction for a hydrogen-exhausted photosphere. Pinned by `test_the_hydrogen_exhausted_feh_survives_the_load_unchanged`. The one genuine limitation is the grid's, not the reader's: inside the single cell where the table steps from an ordinary [Fe/H] to 30.0, linear interpolation returns a large intermediate the track does not support; fixing it means tabulating a smooth variable (surface X, or uncapped `log10(Z/X)`) at generation time.
- **`trim_to_complete_grid`'s completeness check must tolerate per-EEP duplicate rows.** It was written as `MultiIndex.equals`, which is order- and duplicate-sensitive and so False for EVERY grid, complete or not -- the component could not load at all. It is a set difference now, shared with the trim itself via `_missing_pairs`.
- **The ~128 MB `*.grid.parquet` files are gitignored and do not ship, and are FETCHED ON FIRST USE.** `mist_grid._resolve_grid_file` routes a missing default grid to `models/MIST/eep_grid.ensure_eep_grid`, which is the ONE reader of the published grids (Zenodo record 21893308, size- and md5-pinned, verified and cached in place plus machine-wide via `utilities/zenodo.py` -- the same machinery the NextGen spectra use). Nothing downloads at import; the fetch happens in stage 1a on the first fit that asks for a track. An explicit `model_root:` is used **as given and never auto-populated** (it is a statement about which grid to use), and only MISTv2.5 is published -- both raise. The v2.5 filename is `eep_grid.eep_grid_filename`'s, not reimplemented here: that spelling already exists twice on purpose (the authoring script and `eep_grid`, kept byte-identical so a locally built grid and a fetched one are interchangeable) and a third copy is a third thing to keep in agreement. No test may depend on a real grid -- use `conftest.write_synthetic_mist_grid`.
- Only MIST is implemented. `mist: False` with no `parsec:` **raises** when a block names that star, `parsec: True, mist: False` raises (it would silently get MIST), and `mist: True, parsec: True` warns.

`mist:`'s historical default is `True` (absent -> opted in) and `parsec:`'s is `False`; every shipped example spells the opt-out `mist: False` outright. Setting either with no `evolutionarymodel:` block still does nothing and **does not raise** -- inert-but-ready by design, so a config written before the component landed keeps working unchanged. This deliberately reverts the star half of review 5.10 (`Star._reject_wip_keys`, PR #158); the orbit half (`Orbit._reject_wip_parameterizations`, review 5.11) stands.

`eep`'s spelling is **Equivalent Evolutionary Point**, per MIST's own `README_tables.pdf`. MIST is inconsistent -- Dotter (2016) and `models/MIST/generate_interpolated_missing_tracks.py` say "phase" -- but "point" is the spelling that does not collide with the separate `phase` column in the MIST track format (the FSPS phase type: -1 PMS, 0 MS, 2 RGB, ...), which an evolutionarymodel component may well surface. Its bounds are MIST's: `upper: 1710` is Table II's terminal primary EEP (end of the white dwarf cooling sequence) and the `354.1661` start sits just past the intermediate-age main sequence (IAMS, EEP 353).

The third key of review 5.10, **`sedfile:`, is deleted outright** rather than gated: `Star.sedfile` was read by nothing, and the implemented broadband-photometry path is the separate `sed:` block, whose own `SED.sedfile` (from that block's `file:` key) is the attribute everything consumes.

- **Plots: one Kiel diagram** (`{prefix}_kiel.pdf`), described once as a Chart so matplotlib and the GUI share it. Three traces per star: the full EEP track interpolated at the draw's (logmass, initfeh) with `here_be_dragons` rows cut (do not draw a curve through the hydrogen-exhausted regime as if it were reliable -- the fit may still go there, the penalty is smooth), the MIST prediction at the fitted EEP carrying the **systematic floor as error bars**, and the fitted point carrying its **posterior interval**. Both marks' bars are drawn only once a posterior exists: the fit's are summaries that do not exist before one, and the MIST mark's are suppressed with them so a pre-flight chart shows the two marks alone rather than implying a measured uncertainty it does not have. The floor still sizes both axis windows either way, so adding the bars later cannot push a mark off-chart. Both axes reversed, per the Kiel convention. `logg` is neither a grid column nor a constrained quantity -- MIST tabulates radius, and mass along a track is the grid's own mass axis -- so both loggs come from `calc_logg_from_logmass` and differ only in which radius they take, which is the comparison the chart exists for; the MIST mark's logg error bar is the fractional radius floor propagated as `2*f_R/ln(10)`, and the mass contributes nothing because it carries no floor. `plot_data(point=None)` returns `[]` on purpose: this component has no observations, so there is no data-only preview to give.
- **Two plotting windows, both widened rather than allowed to hide a star** (`KIEL_EEP_WINDOW = (202, 630)`, the main sequence through the red giant branch, cutting the drawn arc; `KIEL_LOGG_WINDOW = (3.0, 5.0)`, the y axis, excluding giants). Both are presentation, never bounds -- the fit may sit anywhere the grid covers. `_extend_window` folds "very near the edge" and "outside the edge" into one comparison by pushing a violating edge out to `value -/+ margin`, `margin = 10%` of the nominal span (0.2 dex; ~43 EEPs). The EEP window is **per star** (one giant must not drag every other star's arc up the RGB); the logg window is the **union** (there is one axis), and includes the fit mark's systematic bars. `y_range` is stated ascending because `plotrender._apply_axes` applies it BEFORE `y_inverted`. The logg cut is deliberately NOT applied to the track rows -- it is the axis, so widening it cannot open a gap where the curve had already been cut away.
- **The Teff axis follows from those two windows and is set explicitly** (`x_range`, `_padded_range` over the marks-with-error-bars plus the track rows INSIDE the logg window, +/- `KIEL_X_PAD_FRAC = 0.05`, matplotlib's own default margin). Autoscaling is what left more than half a panel empty: a main-sequence star's arc runs on down the red giant branch to ~3000 K at `logg < 3`, which the y window clips away, but both renderers' autoscale still counts those points -- on `examples/hat3` the axis covered 5500-3000 K to show 5400-4600 K. Nothing finite on the chart returns `None` and the key is omitted, i.e. autoscale, which is the honest answer when there is nothing to scale to.
- The EEP axis is **not** one of `mist_grid.OUTPUT_COLUMNS`** (those are the six interpolated quantities); it is the grid axis the rows are indexed by, and `interpolate_track` leaves it alone, so `grid["eep_pts"]` is row-aligned with the returned track by construction. `OUTPUT_INDEX["eep_pts"]` is a `KeyError` -- it was one in both `_seed_eep_hint` and `_track_curve` until 2026-08-25, which made the EEP seed search die on every fit that reached it.
- **`mist_grid.interpolate_track`** blends the four surrounding tracks in (logmass, initfeh) with the likelihood interpolator's own weights, so the EEP seed search and the fit see one surface -- neighbouring tracks differ everywhere, most of all in age, and the nearest-node search this replaced could seed a fit half a cell away in both axes. It **clamps** outside the axes rather than extrapolating, which is the one place it deliberately differs from the likelihood's interpolator: a seed wants the nearest point the models actually cover.
