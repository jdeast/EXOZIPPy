# Running a fit, restart files, and trace reuse

`src/exozippy/run.py` drives a fit; `src/exozippy/mkparam.py` writes the next params file
from a finished one; `src/exozippy/trace_meta.py` decides whether an existing trace may be
reused.

Read this before changing the run flow, the restart-file writer, or anything that reloads
`<prefix>_trace.nc`. Related: `src/exozippy/whitening.md` (the other persisted-state
reload, with a deliberately different policy), `src/exozippy/samplers/samplers.md`.

## The entry point

`run.run_fit(config, user_params=None)` accepts in-memory dicts for both arguments (no YAML files needed; data paths resolve relative to cwd). When `user_params` is omitted it falls back to reading `config["parameter_file"]` from disk. It is also re-exported from the package root -- `from exozippy import run_fit` -- and with `System` and `__version__` it is the whole of `src/exozippy/__init__.py`'s `__all__`: the run-a-fit surface this package promises, and everything outside it is internal (the extension API for writing a component is declared separately, in `components/components.md`). The re-export resolves lazily, because `run` imports from the package and an eager import would have the two modules initializing each other. Review 8.13.6; tests: `tests/test_public_api.py`.

**The `parameter_file:` key is omittable, and an empty params file means the same thing.** A fit can start with no user overrides at all: `defaults.yaml`, the components' data-derived hints and the relaxation engine supply the start values between them, and since the global search (`components/globalsearch.md`) a blind fit seeds its own period and epoch from BLS/Lomb-Scargle. Requiring the KEY while the FILE it names may legally be empty was a distinction with no content, so `System.__init__` now defaults `user_params = {}` with an INFO line naming where the values come from -- INFO and not a warning, because this is a supported way to write a config rather than a mistake to apologize for. `load_yaml` returning `None` for an empty file is normalized to `{}` for the same reason: an empty file must not be a third state every consumer spells `user_params or {}` for. Two things deliberately do NOT change: a key that IS present must still name a file that exists (that is a typo, not a choice, and stays a `FileNotFoundError`), and `config_manager.param_file` is left unset when no file was read, since error messages quote it to say which line to edit and there is no such line. Tests: `tests/test_optional_parameter_file.py`.

## The startup audit table honors `print_to_table`

`inspect_start` prints one row per parameter element before the fit starts, and two flags decide which rows exist (`run._prints_in_startup_table`). `print_to_table: false` is a **veto**, checked first: the startup table is a table, and it was the one table that ignored the flag (review 3.14.9). Making it a veto rather than a default is what gives a *user* a way to suppress a row -- `print_to_table` is a params-file key, while every parameter that opts INTO this table does so through `debug_print` in its component's `defaults.yaml`, which a user cannot edit. `debug_print` then decides among what is left: `True` shows a DERIVED parameter a reader needs at the start anyway (`star.mass`, `orbit.period`, the microlensing timescales), `False` hides a sampled one, and `None` -- the default -- means "show it if the sampler moves it".

The item that asked for this named `orbit.n` as the live case; that half is wrong and is recorded so it is not re-derived. `orbit.n` is derived, so the sampled-only default already excluded it, and it is the only `print_to_table: false` in the shipped tree -- the shipped startup tables are therefore unchanged. The reachable form of the defect is a user marking a SAMPLED parameter not-for-tables. Tests: `tests/test_inspect_start.py`.

**What those flags govern is ROWS, and nothing else.** The flat-direction warning after the table is sampler HEALTH -- its own text says one unconstrained parameter destroys HMC efficiency -- and it used to be collected inside the row loop, which `continue`s on `_prints_in_startup_table`. So a sampled parameter a user had marked `print_to_table: false`, or a component had marked `debug_print: false`, could come back from the whitening probe with a NaN multiplier and earn no warning at all: a cosmetic table flag silently disabling a diagnostic (review 2.3.7). `run._flat_probe_directions` now walks `mult_map`/`is_sampled` per element independently of row printing; the per-element semantics are unchanged (inactive elements skipped -- an inactive element is not sampled and has no direction to be flat along; a parameter with no `mult_map` entry counts as flat, because the probe reports one entry per sampled raw variable; nothing at all is reported when there is no whitening report, since unmeasured is not flat). No shipped default hits the defect, so no shipped run's warnings change. The same rule applies to anything else that lands under this table: if it is about the fit rather than about the table, do not read the print flags to decide it.

**A row whose start IS an expression's value is read off the compiled graph, at the start point.** `raw_v = p.initval` is the first source and the user/solved table the second; a parameter with NEITHER -- no `initval` and no entry -- gets its row from what the built graph computes. Two things were wrong there. The gate was `p.expression is not None`, a whole-vector test (1.10.9's), so a vector derived one element at a time through `element_expressions` failed it and got NO ROW AT ALL -- the reachable form is a missing row, not a wrong one, since a parameter WITH an initval never reaches this branch (review 3.14.16, premise corrected by measurement). Across the shipped tree exactly one parameter reaches it and prints, `examples/ob09020`'s `lens.alpha`, which now reads 189.082 deg -- that example's published `alpha_0`, recorded in its own params file as the acceptance check. And the evaluation itself was `p.expression().eval()`, which evaluates the graph with its RVs still in place and therefore DRAWS FROM THE PRIOR; `diagnostics.ModelAuditor.values_at_start` is now the one owner of "what does this node actually have at the start" (`check_user_starts` reads the same function), replacing the RVs by their value variables and feeding `transformed_inits`. It compiles nothing when no parameter qualifies. The posterior-side twin of the gate is `System._set_comp_posterior`; the two tables now agree on what "derived and therefore evaluable" means.

## `maxtime:` is never silently ignored

`run.warn_maxtime_unsupported` says so when the selected sampler cannot honor `maxtime:`. Today that is `numpyro`, `blackjax`, `nutpie` and `nested` (`MAXTIME_UNSUPPORTED_METHODS`), and **the reason is per method, not one sentence for all four** -- the three external NUTS backends run the whole chain outside Python's per-draw loop (the JAX ones inside one jitted scan, nutpie inside Rust), so there is no point at which a wall-clock check could raise the `KeyboardInterrupt` that the maxtime mechanism turns into a graceful stop. PyMC agrees and says so out loud: `pm.sample` **raises** for a `callback` with any `nuts_sampler` but its own, which `tests/test_run_maxtime_support.py` pins upstream so that a future PyMC forwarding callbacks turns into a failing test rather than a permanent warning. `nested` is there for a different reason and was added while review 2.3.6's consumer table was being re-verified: nested sampling stops on its own evidence criterion, `nested_sample` takes an iteration cap (`maxiter`) and no wall clock, and run.py forwards neither -- so `maxtime` under `nested` had been silent too.

A silently ignored key is worse than a refused one: the whole point of `maxtime` is that a scheduler-bound job stops itself before the queue kills it, so a user who sets it and gets nothing has no partial trace AND no idea why. `demc` already warned for the same reason on the samplers side (`samplers.md`). The check runs **after** the missing-backend import fallback, so a config asking for numpyro on a box without it -- which lands on PyMC NUTS, where maxtime IS honored -- is not warned about a limit that will be applied.

This is also why `maxtime` is NOT in `METHOD_ONLY_SAMPLER_KEYS`: a consumer list would replace four accurate reasons with one method tuple, and two channels warning about one key is one too many.

## A typo in a reserved block is never silent either (review 2.3.10)

`system.KNOWN_BLOCK_KEYS` is the ONE owner of the sub-key vocabulary of `modes:`, `mkparam:`, `gui:` and `modeling:`, and `run.warn_unknown_block_keys` the one reporter -- modelled on `warn_unknown_sampler_keys` so the file has one shape for this rather than two. Before it, `modeling:` warned through an inline loop of its own and the other three said nothing at all: `modes: {ledgr: false}` left the seed ledger ON and `mkparam: {forse: true}` left the invalid-seed refusal ARMED, each delivering the opposite of what the user wrote with no message. `introspect.py` published a second literal copy of all four lists to the GUI and now fills them from the same table, exactly as it already filled `sampler` from `run.KNOWN_SAMPLER_KEYS`.

`warn_unknown_config_blocks` runs all four at **startup**, not at each block's point of use, and that is the point: `mkparam:` is read by `mkparam.py`, `gui:` by `gui/status.py`, and `modeling:` not until wrap-up, so a warning where the key is consumed would reach the user hours into a fit -- or, for a fit that died first, never. `run:` is deliberately NOT checked: it is the free-form documentation block nothing reads, and a vocabulary for it would be a vocabulary for prose. `sampler:` keeps its own, richer check (`KNOWN_SAMPLER_KEYS` plus the method-only table). Tests: `tests/test_known_keys.py`, which cross-checks each block against the reads in the module that consumes it, in both directions.

**An empty SYSTEM config is refused; an empty PARAMS file is not** (review 2.3.11, JDE 2026-09-11). `yamlio.load_system_config` -- what both console scripts now call -- refuses an empty document, and one that parses to something other than a mapping, **naming the file**. Both CLIs used to walk off the end of `load_yaml`'s `None`: `AttributeError: 'NoneType' object has no attribute 'get'` from inside `run_fit`, or the same from `config.get("prefix", ...)` in `exozippy-modes`, neither naming anything. An empty system config cannot mean anything -- it declares no component, no prefix and no parameter file. The asymmetry with the paragraph above is the ruling and not an oversight, so the guard is in `load_system_config` and **not** in `load_yaml`, which the params path shares: `load_yaml` still returns `None`, `System.__init__` still normalizes it to `{}`, and an empty params file is still a supported way to write a fit. Both halves are pinned in `tests/test_empty_config.py` so a later tidy-up cannot move the guard down into the shared loader.

## No sampler branch is handed a start, because `Model.initial_point()` IS the start (reviews 1.3.6, 4.3.1, 2.3.18)

**The defect.** `System.get_raw_start` existed to **override** `Model.initial_point()` -- its own docstring said so -- and `System.apply_polished_starts` writes the seed polish into each `Parameter.raw_initval` as a NONZERO raw offset. The plain-NUTS branch read none of it: `pm.sample` got an explicit `step=pm.NUTS(...)` and no `initvals=`, and pymc's own docstring says of `init`, verbatim, *"This argument is ignored when manually passing the NUTS step method"* -- so the **default** sampler for every non-microlensing fit began at `Model.initial_point()`, the creation-time initvals frozen at RV creation. It looked correct by construction for as long as the anchor WAS the start: pre-polish every logit element's `raw_initval` is 0, which is exactly what `initial_point()` holds. A polish is what separates them. That was review 1.3.6.

**What that cost is NOT the whitening.** The whitening is a reparameterization baked into the graph as `pytensor.shared` variables and the samplers sample `raw`, so every gradient is in whitened coordinates wherever the chain starts; and `pm.NUTS(target_accept=)` with no `scaling`/`potential` builds a `QuadPotentialDiagAdapt` **identity** metric on raw -- the right metric precisely because the graph is already whitened -- which takes nothing from the start point but its size and a step-size heuristic. What is lost is the **co-location of the start with the metric**: the polish deliberately runs BEFORE the probe so the scales are measured around the polished point, so starting at the anchor hands NUTS's first adaptation windows curvature the metric was never measured for. That is the ob140939 mechanism, on the default sampler alone.

**Passing `initvals=` fixes the physical start and breaks the raw one, which is why it is not the answer.** 1.3.6's two-line fix (PR #263) was measured on `examples/kelt4` RV-only and HELD: it starts at a better PHYSICAL point (0.967 Mjup against master's 1.053, truth ~0.878) and a far worse RAW one, and with an identity metric and steps of order one raw unit that is what matters. `max |raw|` of the start came out **684** with `measure_scales: false` -- the configuration `tests/test_integration_kelt4.py` uses -- and **10.58** with measurement on; the 1-draw integration test then scattered to 6.7 Mjup and went red. Master is not frozen by comparison, it moves -20% identically on all eight seeds, which is what a well-conditioned short trajectory looks like. The 684-against-10.58 gap is **review 2.3.18**: the polish runs under `if not reusing_trace:`, independently of the whitening, and stores its displacement in PRELIMINARY scale units, so `set_whitening` was what re-expressed it and `measure_scales: false` stopped that running at all.

**The fix is structural, and it is the combination neither master nor #263 has** (review 4.3.1): the polished physical start AND `raw = 0`, where the identity metric is calibrated. `System.recenter_whitening_anchor` makes `Model.initial_point()` the polished start BY CONSTRUCTION, and every explicit start on the pymc side is then deleted -- no branch can forget one, because there is nothing to pass. It is called once per fresh run, **between the polish and the whitening probe**, so the probe measures its contours around the new anchor; **before** the `reusing_trace or measure_scales` guard, so it is independent of `measure_scales` and closes 2.3.18; and never on the trace-reuse path, where the anchor comes out of `whitening.json` and re-centering on a start nothing will sample from would silently re-coordinate the trace. The two mechanisms -- fold the displacement into the logit ANCHOR, `Model.set_initval` for the Gaussian path whose center is its prior mean and may not move -- are in `src/exozippy/whitening.md`. Measured on kelt4 RV-only, `max |raw|` of the start the sampler begins from:

| | no re-centering | re-centered |
|---|---|---|
| `measure_scales: false` | 684.07 | **0.0** |
| `measure_scales: true` | 10.58 | **0.0** |

**The explicit `step` is KEPT rather than dropped in favor of a live `init`, and that is the deliberate half.** `initvals`' own docstring entry reads *"Initialization methods for NUTS (see ``init`` keyword) can overwrite the default"*, so making `init` live would let an `adapt_diag` jitter move the chain back off the polished point -- the exact pathology `seed_polish` exists to prevent. Keeping the step is what makes the model's own initial point authoritative -- and review 5.3.3a (below) then deleted the `init` key outright, so the step is now the only thing holding that door shut: a future pymc honoring `init` alongside an explicit step would have nothing to honor.

**nutpie's `init_mean` was already inert, so the deletion FIXED that branch rather than simplifying it.** Measured against nutpie 0.16.11 + pymc 6.3.2 through both spellings (`nuts_sampler_kwargs=` and the newer `nuts=`): `init_mean` leaves the first draw exactly where a no-start run leaves it, while `Model.set_initval` moves it by the requested offset. The mechanism is in nutpie's own source -- `CompiledPyMCModel._make_model(init_mean)` takes the argument and never uses it, handing `self.initial_point_func` to `PyMcModel` instead -- so for a pymc-compiled model the start comes from the MODEL. run.py's nutpie branch was therefore a **second live instance of 1.3.6's bug class**, and nothing had noticed.

**What still takes an explicit start, and why.** The three in-house samplers (`ptde`, `ptde_async`, `demc`) keep `raw_starts=`: a multi-seed start SET is more than one point, and `Model.initial_point()` holds only seed 0. `nested_sample` takes none for a different reason -- nested sampling draws its live points from the prior -- and run.py says so at the call site.

**The guard, and how it survived the change it was watching.** `tests/test_nuts_start.py` is 1.3.6's every-call-site guard, carried across from the held PR and **preserved in spirit rather than deleted**, because deleting it would have removed the only structural protection against this bug class -- which is how 1.3.6 survived months. It is split by mechanism: the in-house branches keep their `raw_starts=` assertions unchanged; the pymc-side branches are guarded by the MECHANISM (run.py calls the re-centering, and before both the probe and every dispatch) plus a dynamic test that `Model.initial_point()` equals `get_raw_start(model)` equals `get_mcmc_init(model)`, element for element, after a polish has demonstrably moved the start. That is strictly stronger than "a kwarg was passed", which the old form could satisfy by passing a *wrong* dict. `nested_sample`'s exemption is still asserted to FIRE. `tests/test_set_initval_contract.py` pins `Model.set_initval` itself -- on the installed pymc and on the declared 6.0.0 floor -- because a correct start is now structural, so a silent upstream regression would mis-start every fit rather than erroring.

## Wrap-up: no diagnostic may kill a finished fit

Everything after `pm.sample` returns is a REPORT on a fit that already finished, and its irreplaceable artifacts -- the trace, the mode report, the restart file, the modeling draft -- are cheap to lose and expensive to recreate. So every wrap-up step runs inside `run.nonfatal_wrapup(what)`, which warns with the traceback and carries on. The plotting block between the tables and `write_param_file` was the one stretch of bare calls in an otherwise wrapped wrap-up, and a degenerate-KDE crash inside `save_multipage_trace` (which any short or stopped run can provoke) therefore skipped the restart file and the final `paper.tex` regeneration of a multi-day fit. The guard is per COMPONENT, not per loop: one component's broken diagnostic costs its own figure and nothing else. `draws` is seeded empty before the guarded `get_draws`, because the modeling draft reads `draws[0]` past the wrap and must degrade to its data-only specs rather than `NameError`.

**The convergence-summary write was the last bare call, and what it cost is measured.** `summary_path.write_text(_format_summary(...))` sat between two guarded stages with no wrap and no `wrapup.stage` line (review 2.3.12; every neighbour got one in PR #214). It is a disk write plus an `az.summary`, so it fails for the ordinary reasons -- a full disk, a degenerate summary. Executed on the kelt4 RV-only example (tune=2/draws=1, the `tests/test_integration_kelt4.py` vehicle) with `_format_summary` raising `OSError`, against the same run without: the injection cost `_mcmc_RV_phased_b.pdf`, `_mcmc_RV_unphased.pdf`, `_trace_detailed.pdf`, `_paper.pdf` and its aux files, `_summary.txt`, **and `kelt4.params.2.yaml` -- the restart file** -- and `run_fit` raised, so the CLI reported failure for a fit whose sampling had finished. Wrapped, the same injection leaves every one of those in place. **Two neighbours are deliberately left alone**: `analyze_idata` is load-bearing downstream (`burn_diag` is read by the tables, the prose and the restart file), and the mode gate's raise is intentional -- a `> max_invalid_frac` run loses its corner plot and restart file BY DESIGN ("don't seed the next fit from a broken run"), recoverable with `modes: {force: true}` plus trace reuse. Do not "finish the job" by wrapping either.

The `except` is deliberately broad -- enumerating what a third-party plotting stack can raise is exactly the list that goes stale, and the invariant is that NO diagnostic from ANY component kills a finished fit. `KeyboardInterrupt`/`SystemExit` are not caught: somebody interrupting wrap-up wants it to stop. What the guard must never become is a silent swallow; `exc_info=True` is what puts the traceback in the log and so in the GUI's `status.json`. Tests: `tests/test_run_wrapup_guards.py`.

## Wrap-up must never go silent, and must never go serial (reviews 2.3.5, 6.11.3)

**Every wrap-up stage announces itself** through `run.WrapupProgress`: one INFO line naming the stage and how many items it will chew through, stamped with elapsed time since wrap-up began, plus a closing total. Measured on `examples/ob09020` (2026-08-26), the log's last three lines were the sampler finishing, the hot-chain clustering, and the gradient-fallback notice -- **then nothing at all for 38+ minutes**, and from outside the process the only way to tell "computing" from "hung" was to sample `/proc/<pid>/stat` twice and see one core pinned. That cost a wrong diagnosis in the session that found it. There is deliberately no fixed denominator ("stage 3 of 9"): the stage list is conditional (per-mode outputs only for a multimodal fit), and a total that lies is worse than none.

Inside a stage, the long poles carry their own heartbeat rather than being narrated per item. The one that matters is the gradient-free DE polish (`samplers.ptde.polish_seed_starts`, interval `ptde.POLISH_PROGRESS_S`, default 30 s), which logs sweeps-against-cap, elapsed, an upper-bound ETA and each seed's gain so far. **Wall clock, not "every N sweeps"**: one sweep of a binary-lens model can take milliseconds or minutes, so a sweep count that is chatty on one model is mute for 40 minutes on another. A sub-interval polish logs nothing, which is why the test suite stays quiet.

**And the beat fires from inside a sweep, not only between them (3.4.4).** One sweep is ONE batch of `n_seeds * pop_size` evaluations, and while that batch was a single blocking `pool.map` the check between sweeps could not run until it returned -- so a wedged VBM evaluation, the exact case this feature exists for, produced silence forever and the "nobody has to read `/proc/<pid>/stat`" claim was false precisely when it mattered; a merely slow sweep bought silence for its whole length. On a pool that offers `apply_async` (every `multiprocessing.Pool`) the batch is now collected one result at a time, in submission order, and the wait wakes on a quarter-interval poll (floored by `ptde.POLISH_POLL_MIN_S`) and after every result that lands. A mid-batch line names the sweep as IN PROGRESS and how many of its proposals have come back -- a repeating `17/64 proposals back` is what computing looks like, a frozen one is what hung looks like -- and the opening batch that scores the populations gets the same treatment. Every beat shares one rate-limit clock, so beating per proposal produces no more lines than beating per sweep. A pool with only `map`, the serial path, and the case with the heartbeat AND `eval_timeout` both off keep the single blocking call.

`polish_seed_starts` and `polish.polish_raw_starts` also accept an `eval_timeout` (per-logp-call wall-clock budget; a call that exceeds it is scored `-inf` and the Metropolis test rejects it) together with a `pool_recycler`, because the pool that hung is unusable afterwards -- but **`run.py` does not pass one, deliberately**. `sampler: eval_timeout:` is classified in `METHOD_ONLY_SAMPLER_KEYS` as consumed by the PTDE family alone, and `warn_method_only_sampler_keys` tells a `demc` / `demcz` / `nested` user it is IGNORED. The polish runs on EVERY method, so honoring it there would make that warning -- landed by 2.3.6, the review about sampler keys that silently do nothing -- lie in reverse for a gradient-free model under `demc`. Which methods "consume" the key is a config-vocabulary ruling, not a heartbeat fix; the plumbing is in place so the wiring is one argument once that ruling is made.

**The hot-mode polish gets the sampler's cores, and `cores=None` means AUTO everywhere.** Two halves, and 6.11.3 is what happened without either. First: `discover_hot_modes(..., cores=)` forwards the grant `run.py` resolved, so a user's `sampler: cores:` governs this stage exactly as it governs sampling. Second, and the reason the omission was silent: `cores=None` used to mean SERIAL in `polish._resolve_polish_cores` while it meant "take the machine" in `samplers/_common.create_pool` two modules away -- same word, opposite meaning, in two functions that fork the same kind of pool. So the hot-mode polish, which passed nothing, ran the DE engine -- the branch EVERY gradient-free (VBM-backed) microlensing fit takes -- on 1 core of 36 for 38+ minutes on a single candidate, immediately after a sampling phase that had been using 27.

There is now **one** rule, `_common.default_cores()` (`CORE_FRACTION` of the physical cores, capped at `n_phys - 1` so the OS and the user's shell keep one), and `None` resolves to it in the polish, in `create_pool` and in `nested.py` -- which had a third hand-written copy that had dropped the `n_phys - 1` arm entirely. Nothing about a polish wants fewer cores than the sampling either side of it, so the default says so; **a caller that wants serial passes `cores=1`**, which is a statement rather than an omission, and the tests that want serial do exactly that. `polish_raw_starts` still ANNOUNCES which branch it got (worker count, or SERIAL naming the `cores` value it was handed), and `tests/test_run_wrapup_guards.py::test_every_polish_call_site_passes_a_core_grant` pins the forwarding across the whole package -- now guarding the user's configured grant rather than guarding against serial.

**A Ctrl-C during wrap-up cannot cost the trace, and now says so.** The trace is written to disk before any of this runs; everything after is a report derived from it. Sampling documents its own interrupt behavior, wrap-up documented none, so an impatient Ctrl-C felt like it might throw away a multi-day fit. `run_fit`'s `KeyboardInterrupt` handler now names the saved trace and points at `exozippy-modes <config.yaml>`, which regenerates the remaining reports without re-sampling. It fires only for an interrupt during wrap-up -- the phase comes from `GuiReporter.last_phase`, which is recorded even when GUI status output is off (the default), because it is the run's own record of where it is, not a monitoring artifact. During sampling the same claim would be false assurance, so it stays silent there.

## The restart-file writer (`mkparam.py`)

`mkparam.write_param_file(config, ...)` writes the next `params.yaml` from a finished fit's trace -- called automatically at the end of `run.py`, from `scripts/mkparam.py`, or directly. Config block `mkparam:` (`n_seeds`, `force`).

**Nothing here is called a prior unless it is one, and that is the whole reason for the names.** What the file mostly contains is `initval` -- a START VALUE, which moves where the next fit's chains begin and cannot move that fit's posterior. A prior is a term in the logp, and only `mu`/`sigma` are that. The module, the function, the config block and the file header all say "param", never "prior" -- EXOFASTv2's equivalent routine is named the other way, and is the cautionary tale rather than the model. The cost of conflating them is concrete and this codebase already guards one spelling of it: `config.validate_sigma_has_center` refuses a `sigma` with no `mu`, because such a prior would be centered on whatever start value resolved -- often a MAP this very tool wrote -- and so would double-count the data. `_apply_existing_constraints` is the other guard: a previous file's `mu`/`sigma` (a real prior) and `lower`/`upper` (real bounds) are copied across **verbatim** and never recentered on the new MAP; a `sigma > 0` entry whose center was implicit in its old `initval` gets that promoted to an explicit `mu` so it cannot follow the MAP on the next round trip.

**A DERIVED parameter's constraints come through the pass-through loop, not that one** (`_CONSTRAINT_FIELDS`, review 2.3.13). Only parameters mkparam EMITS reach `_apply_existing_constraints`, and a derived parameter is never emitted -- it has no `_raw` companion in the trace, so writing it a start value would install the redundant constraint the "physically sampled variables" filter exists to prevent. Its entry therefore falls to the loop at the end of `write_param_file`, which re-emits an untouched existing entry if and only if it states a constraint. That set is `config.PHYSICS_KEYS` minus `mu` (a center with no width is not a prior), and `bound_scale` belongs in it for the reason `lower`/`upper` do: dropping it silently re-stiffens a soft barrier the user deliberately widened. `examples/gj1214`'s `star.A.loggsed: {bound_scale: 25.0}` is the live case -- see `components/sed/sed.md` -- and it used to be discarded as an initval-only stale guess, so the example's softened barrier had to be re-added by hand after every restart cycle. What that loop must NOT grow into is emitting derived parameters generally: it reads the user's file and never the trace, so the entry carries no MAP `initval` for a value the model recomputes and would silently override.

**Seed 0 is the best VALID draw, not `np.argmax`'s.** The restart file's seed 0 is the trace MAP, and both of the obvious ways to find it are wrong in the direction that silently writes a bad start value. `np.argmax` returns the index of the first NaN it meets, so one non-finite lp anywhere in the trace made that draw the "MAP"; and a *finite* lp is not proof a draw is usable, because the runaway-lp failure mode produces enormous finite values that win any ranking by construction -- which is exactly why `outputs.modes` labels them -1. `_map_draw_from_lp` therefore ranks with `np.nanargmax` over an lp array masked by the mode pass's own per-draw labels, the same label -1 exclusion `_sample_seed_draws`' stratified path already made; the MAP path was the last leak. When nothing is rankable it returns None and the caller takes the same "last draw of chain 0" fallback a trace with no lp at all gets, rather than `argmax`'s silent index 0. The ALL-invalid trace is a different question and is refused outright upstream (`_refuse_invalid_seed_draws`); this masking is what makes a PARTIALLY invalid trace safe, which that gate deliberately does not cover.

The function is `write_param_file`, not `mkparam` -- the module keeps the tool's name (which is what the config block and the CLI are called), while the call site says what it does and what it returns. There is no `backup_params`: the output path is auto-versioned (`foo.params.yaml` -> `foo.params.2.yaml`), so the input is never written over. **The version bump loops until the name is unused**, and that is the point rather than a detail: bumping once protects only the input, so two fits started from the same `foo.params.yaml` both resolved to `foo.params.2.yaml` and the second silently destroyed the first's restart file (it happened, 2026-08). The loop's exit condition is "nothing is there", not a counter, so a directory holding versions 2..40 lands on 41. It is deliberately not atomic against a concurrent writer -- the realistic collision is sequential runs, and a lock file would be a heavier promise than "never destroy an existing restart file" needs. A config naming no `parameter_file` versions the same way from the name the file would have had, rather than hardcoding `.2.yaml`.

## Reproducing a fit (`sampler: {seed:}`, review 2.14.4)

`run.py` used to pass no `random_seed` anywhere, so a user could not reproduce their own fit. The `sampler: seed:` key now reaches every sampler. When the key is ABSENT a seed is DRAWN from the OS entropy pool, logged, stamped on the trace as `posterior.attrs["random_seed"]`, and echoed into the restart file's header by `mkparam` -- so the default stays "different every run" while the run that actually happened stays reproducible after the fact. A hardcoded default would be strictly worse than no seed: it would correlate every user's chains while looking responsible. The full contract, including why `ptde_async` is the one method a seed cannot make reproducible and what to use instead, is in `src/exozippy/samplers/samplers.md`.

The seed is a COMMENT in the params file, not a key: that file is parameter overrides, and `sampler:` belongs in the config. Two things a seed deliberately does not cover: `run.get_draws`' posterior-spaghetti selection (unseeded on purpose -- see its docstring; a fixed subset would read as "the" 50 curves) and `ptde_async`'s arrival order.

## Trace staleness (`trace_meta.py`)

`<prefix>_trace.nc` carries the `evaluator.structural_hash` of the config + params that produced it (root attrs `exozippy_structural_hash`, plus the payload it was hashed over so a mismatch can name what changed). All three reloads check it -- `run.py`'s `recompute_trace: false` branch, the `exozippy-modes` CLI, and `mkparam.write_param_file` (whose restart file seeds the *next* fit, so a stale trace there corrupts a run that has not happened yet). A mismatch **raises `StaleTraceError`**; there is no opt-out key. This is deliberately harsher than the neighboring whitening reload, which warns and re-measures: whitening can be honestly recomputed at load time, whereas foreign draws cannot be repaired, and reusing them silently regenerates every posterior, LaTeX table and plot under the new labels. A trace with **no** hash (written before this existed) is "unverifiable", not stale -- one warning, then it loads. The hash is snapshotted at the **end** of `System.__init__` (`System.structural_fingerprint()`) -- after the components have normalized their own config blocks, before `prepare()`. That placement is measured, not assumed, and it matters: `Mann.__init__`/`Torres.__init__` derive `name:` from their `star:` key and write it back, so a snapshot taken before the component loop spells those instances `'0'`/`'1'` and one taken after spells them `'B'`/`'C'`. `mkparam` recomputes rather than being handed the live System's fingerprint, and that is only safe because the two agree: across kelt4 (RV-only and rv+transit+sed), ob08092 and ob140939, the config dict is mutated in exactly those `__init__` spots and **zero times by stages 1-7** (harness + method in the PR discussion). If a future component starts writing into config during `load_data`, mkparam's raise is a *true* positive -- `config` and the params file are what it merges the MAP into, so if they are not what was fitted its output is wrong regardless. A happy side effect of the placement: the derived `name:` is the only thing in the payload that reflects a relation component's `star:` target, so swapping which star a `mann:`/`torres:` block constrains now changes the hash; before, it did not. Known blind spots -- shared with the GUI's stale/live decision, so do not widen `structural_hash` without considering that consumer: data-file **contents** (only paths are hashed), numeric `mu`/`sigma` magnitudes, and numeric `mu`/`sigma` magnitudes in `user_params`.

**Per-instance config keys ARE hashed, via a DENYLIST** (`evaluator._NON_STRUCTURAL_INSTANCE_KEYS`, since 2026-08-15). Everything inside a component instance reaches the payload except an explicitly cosmetic few (`plot`, `label`, and `file`/`files` only because `structural_payload` already hashes those under its own `files` key -- `path` is *not* dropped). The direction is the whole point and must not be inverted back: nearly every instance key selects part of the model (`light_travel_time`, `gp`, `likelihood`, `mask`, `ld_law`, `data_format`, `rm`, `exptime`, `ninterp`, `band`, `star_ndx`, the SED's `mag`/`err` photometry...), so an allowlist is a hand-maintained list of *everything*, and one forgotten entry fails **silently** -- the trace reloads under a model it was never sampled from. `light_travel_time` was exactly that, and it defaulted to on. A denylist fails the other way: a forgotten cosmetic key merely forces an honest re-run. Adopting it invalidated every trace on disk once, deliberately; that one-time cost buys never silently reusing foreign draws again. Note also that any pre-2026-08 transit trace predates the Roemer correction entirely, so re-run rather than reload.

**The posterior's unit system is stamped too** (`exozippy_posterior_units`, always `"user"`), because the save path runs `_convert_posterior_to_user_units` on the way to netCDF and a trace written before that conversion existed holds INTERNAL-unit draws -- radians rather than degrees, solar rather than jupiter masses. Those are numerically plausible and nothing downstream can tell them apart from the numbers, which is the whole reason the stamp had to exist. `check_posterior_units` runs from `check_trace_freshness`, the one choke point every reload passes through, and its result is advisory: it never changes the freshness verdict, because which units the draws are in is a different question from whether they came from this model. A missing stamp **warns** and loads -- it is the `trace_meta` unverifiable case, not the stale one, since the conversion is older than the stamp and refusing every unstamped trace would invalidate working ones to catch a shrinking population. An unrecognized stamp warns by name (a trace from a future format). Nothing ever **converts** on a guess: multiplying by the factor would corrupt every trace already in user units, which is nearly all of them, and the numbers offer no way to decide. The remedy is `recompute_trace: true`, and the warning says so.

The stamp also records the code that produced the draws -- `exozippy_version` plus, when running from a checkout, `exozippy_git_commit` / `exozippy_git_describe` / `exozippy_git_dirty` (dirty = uncommitted *tracked* changes; untracked example data and notes are ignored or every run would flag) -- and a `StaleTraceError` quotes them and prints the `git worktree add <commit>` + `poetry install` lines that recreate that code. This is **diagnostic only: nothing ever compares versions**. A version or commit difference never raises, so newer code with a structurally unchanged model still reuses its trace; only the structural hash decides staleness. Traces stamped from an installed wheel say the source cannot be checked out; traces predating the metadata say so plainly rather than printing a git command with a missing commit. Tests: `tests/test_trace_staleness.py`.

## A sampler key some method ignores must say so (reviews 2.4.2, 2.3.6)

`store_hot_chains` is forwarded only to `ptde_async`; `rung_thin_factor` and
`rung_thin_start` only to `ptde`. All three are in `KNOWN_SAMPLER_KEYS`, so
`warn_unknown_sampler_keys` stays silent, and the branch that would read them
is simply never taken -- setting `store_hot_chains` under `method: ptde` meant
hot-chain mode discovery never ran and nothing said so.

`METHOD_ONLY_SAMPLER_KEYS` maps each such key to the methods that DO consume
it, and `warn_method_only_sampler_keys` reports the mismatch. Two deliberate
properties: it warns only for keys the user EXPLICITLY set (they all have
defaults, and warning about a default nobody wrote would fire every run and
teach people to ignore the log), and it is called AFTER `method` is resolved
and lowercased -- not beside `warn_unknown_sampler_keys`, which runs early
enough that `method` may still be None because auto-selection has not happened.

**2.4.2 landed the mechanism for three keys; there were more than twenty.** `chains`
is the one that mattered: run.py forwards it to the HMC branches and to
`demc`/`demcz` and to nothing else, so under `method: ptde`/`ptde_async` --
the recommended default for every microlensing fit -- a user's
`sampler: {chains: 16}` did nothing at all, and those samplers sized their
population from the parameter count instead (`_common.resolve_n_chains`; the
PTDE spelling is `n_chains`). Measured end to end on `examples/kelt4` RV-only,
2026-09-11: `chains: 5` gave **5** chains under `method: nuts` and **30**
under `method: ptde`. It is the single most likely spelling of "give me more
chains".

**What keeps it fixed is the partition, not the list.** `KNOWN_SAMPLER_KEYS`
is now exactly `METHOD_ONLY_SAMPLER_KEYS` plus `ALL_METHOD_SAMPLER_KEYS`, with
no overlap, and `tests/test_method_only_sampler_keys.py` asserts that in both
directions. The defect was never any one key -- it was that a key could join
the vocabulary with nobody ruling on whether some method silently ignores it.
A new `sampler:` key now fails that test until it is classified.

Four keys sit in `ALL_METHOD_SAMPLER_KEYS` despite being only PARTIALLY
honored, because on no path are they inert and a warning would therefore be
false: `cores` (not passed to `sample_jax_nuts`, but it governs the seed polish
and the post-hoc `lp` fill everywhere), `min_ess`/`max_rhat` (the PTDE early
stop, but also the convergence-report thresholds every path prints), and
`maxtime`, which keeps its own channel -- `warn_maxtime_unsupported` names a
per-sampler REASON rather than a consumer list. That channel gained `nested`
while this table was being re-verified: nested sampling stops on its own
evidence criterion and `nested_sample` takes an iteration cap and no wall
clock, so `maxtime` under `nested` had been silent too.

Two properties of the scoring, each a way the generalized table could have
started lying. An unrecognized `method:` value falls through to the nuts branch
(`samplers.md`), so `_effective_sampler_branch` scores it as `nuts` --
otherwise `method: nutts` would be told `chains` is ignored by the very branch
that reads it. And the message names whichever side of the split is SHORTER,
so `draws` under `nested` reads "every method except nested reads it" instead
of listing the eight that do.

Add a key to whichever table applies in the same commit that adds it to the
vocabulary. Tests: `tests/test_method_only_sampler_keys.py`.

## `init:` is retired, not made live (review 5.3.3a)

The `init` sampler key was read and forwarded to `pm.sample` for as long as
run.py existed, and it was inert for just as long. That is worth stating
carefully, because the obvious reading -- "dead code" -- is wrong and sends the
next reader looking for an unused variable that does not exist. The key was
read, bound to a local, and passed by name; what was dead was its EFFECT.
pymc's own `pm.sample` docstring says of `init`, verbatim, *"This argument is
ignored when manually passing the NUTS step method"*, and the plain-NUTS branch
passes `step=pm.NUTS(...)`. Fifteen shipped example configs carried
`init: adapt_diag`, and it never did anything in any of them.

**It is DELETED rather than enlivened, and the reason is the seed polish.**
Making it live means dropping the explicit step, and `initvals`' own docstring
entry reads *"Initialization methods for NUTS (see ``init`` keyword) can
overwrite the default"* -- so a live `adapt_diag` would be licensed to jitter
the chain off the polished start, which is the exact pathology `seed_polish`
exists to prevent (the ob140939 postmortem). Keeping the explicit step is what
makes the start authoritative. So the key goes, and the comment on the `# 4.
Sample` header that claimed "we use adapt_diag to start exactly at our
estimated means" goes with it: it was false in both halves, since `init` was
ignored and `adapt_diag` jitters rather than sitting on a mean.

A retired key gets its own channel. `RETIRED_SAMPLER_KEYS` maps it to what
became of it and `warn_retired_sampler_keys` says so, excluded from
`warn_unknown_sampler_keys` so one stale line earns one message. A user who
wrote `init:` was following documentation that used to look right, and "Did you
mean 'method'?" tells them nothing; the retired message names the pymc rule and
says to delete the line. Tests: `tests/test_run_dead_residue.py`.
