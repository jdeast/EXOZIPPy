# Whitening and barrier scales

`src/exozippy/whitening.py`: the startup probe that measures every sampled element's
whitening scale from the data, the soft-bound barrier steepness measurement, and the
persisted state next to the trace.

Read this before touching `init_scale`, `bound_scale`, or anything that reloads a trace.
Related: `src/exozippy/components/parameter.md` (what the scales are applied to),
`src/exozippy/run.md` (trace staleness, which is the sibling reload policy).

## Whitening (`whitening.py`)

The whitening scale of every sampled element is **measured from the data at startup**, not hand-tuned. `build_pymc()` builds the model with *preliminary* scales (`defaults.yaml` `init_scale`, a component scale hint, a user `sigma`, or the scale the relaxation engine propagates through the relations; a SAMPLED element with none of them raises, review 3.14.22) and stores the whitening constants in `pytensor.shared` variables. `run.py` then re-centers the anchor on the polished start (`System.recenter_whitening_anchor`, below), compiles logp once and runs `whitening.measure_and_whiten(system, model, raw_start)`: the same bracket+bisect probe PTDE uses for chain initialization, at wider dynamic range, and each `Parameter.set_whitening()` multiplies its shared logit-space scale by the measured 0.5-nat step **in place** -- no rebuild, no recompile, and the posterior is provably unchanged (a logit element's raw coordinate is flat and its uniform prior is the logit Jacobian, for any scale: `src/exozippy/components/parameter.md`, "The raw coordinate of a logit element is FLAT"). After the rescale a unit step along any raw direction costs ~0.5 nats -- the "curvature = -1" conditioning the retired curvature check asked users to approximate by editing `init_scale`. Sampler-block key `measure_scales: false` skips all of it (keeps preliminary scales) -- but it gates the MEASUREMENT only, never the **restore** on the trace-reuse path below: "do not probe this run's start" is a statement about a run that is about to sample, and run.py's guard reads `reusing_trace or measure_scales` for that reason (review 2.3.3). Design points:
- **The whitening has two halves -- a SCALE and an ANCHOR -- and both are measured, not fixed** (review 4.3.1). `set_whitening` is the scale half and deliberately does **not** touch `logit_q_inits`/`q_floors`; `System.recenter_whitening_anchor` is the anchor half and runs once, between the seed polish and the probe. `set_whitening` returns the post-rescale raw-unit scales, which run.py hands to PTDE (`raw_scales=`) so `_make_starts` skips its own probe, and `_raw_transform` is synced for multi-seed starts.
  - **Both halves are legal to move for the same reason, and it is a statement about the DENSITY rather than about invariance.** A logit element's raw coordinate is flat and section C's Jacobian alone makes its prior uniform, so `sv_logit_q_inits` and `sv_scale_logits` are *both* pure parameterization and neither enters the posterior. The anchor is exactly as free as the scale.
  - **The old invariance argument is RETIRED, and this is its replacement.** `set_whitening` used to read "the anchor stays exactly where build_pymc placed it, so the update is a pure scale change in logit space", and pinned a displaced start through a rescale with `lq = lq0 + scale*raw` being invariant under `(scale, raw) -> (scale*m, raw/m)`. That is no longer what carries the production path: after re-centering, `raw_initval` is 0 on every logit element, the start **is** the anchor, and `lq = lq0 + scale*0 == lq0` for *any* scale -- so the start cannot move however far the scale does. The invariance is still what makes `set_whitening`'s `raw_initval /= m` line correct and is still exercised, by a caller that rescales a displaced start *without* recentering first (`tests/test_polish.py::test_set_whitening_keeps_polished_start_at_same_physical_point`); dropping it would make such a rescale silently move the start.
  - **`q_floors` stays meaningful.** Its threshold is a property of the BOUNDS and the whitening scale, not of the anchor, and it still does its job in `raw_from_initval` (keeping an alternate seed's physical value off a wall where `logit(q)` diverges). What is new is that the *re-centered anchor* can itself land inside it, if the polish drove an element onto a wall. That **warns** and is not clamped: clamping would move the polished physical start -- breaking the bit-identity below -- and would override an optimizer's result with a guess, which is the opposite of the rope-not-gates rule. `build_pymc`'s own on-the-bound nudge stands unchanged for the start value a user or the engine supplies.
  - **Why a second mechanism exists for the Gaussian path.** There `val = gaussian_mus + gaussian_scales * raw` with `raw ~ N(0,1)` *as the prior*, and `gaussian_mus[i] = mus[i] if has_mu else inits[i]` -- so for any element carrying an explicit user `mu` the center **is** the prior mean, and folding a start displacement into it would move the PRIOR: a change to the model, not to the coordinates. An added offset fails the same way by a longer route (`val = mu + scale*(raw + off)` with `raw ~ N(0,1)` has prior `N(mu + scale*off, scale)`). Those elements keep their nonzero `raw_initval` and `Model.set_initval` carries it into the model's own initial point instead. `tests/test_set_initval_contract.py` pins that contract -- including on the declared pymc floor -- because after this change a correct start is STRUCTURAL, so a silent upstream regression would mis-start every fit rather than erroring.
  - **The payoff: `Model.initial_point()` is the polished start by construction**, so no sampler branch is handed one and none can forget (review 1.3.6 was one branch of five forgetting). `System.get_raw_start` no longer *overrides* the model's initial point -- it equals it. See `src/exozippy/run.md`.
  - **Start logp is BIT-IDENTICAL across the re-centering**, as it must be: the polished physical point is the same point in either coordinate system. If a nat moves, the anchor has been treated as a posterior term somewhere.
- **The seed polish re-whitens too, between its rounds, on both engines** (review 2.4.14 for DE, `polish.polish_rounds`; the L-BFGS engine joined the same loop on 2026-10-07, see `samplers/samplers.md`, "The seed polish: one driver, two engines"): after each round it re-centers the anchor and runs `measure_and_whiten` at the polished point, so the next round steps in measured units rather than preliminary ones -- the probe measures scales AT the start, and a polish whose steps are taken in badly-scaled units is hobbled exactly where it is needed (on `examples/ob140939` the preliminary units left L-BFGS crawling 2-7 nats below the optimum; one re-whitened round closes that to <= 0.3). Those intermediate measurements are never persisted: run.py still re-centers and runs `prepare_whitening` once after the last round, and THAT is the whitening the run samples under and saves. Successive `set_whitening` calls compose multiplicatively and the logit-uniform prior is exact for any scale, so the intermediate rescales leave the posterior unchanged; the only thing a probe moves in logp is the soft-bound barrier steepness, which is why each round measures its gain from its own post-probe start. `measure_scales: false` turns the in-polish re-whitening off with the rest (later rounds are then plain restarts).
- **The probe runs on the sampler's worker pool, every call under `eval_timeout`, and says how far along it is** (review 2.6.41). It used to call logp one element at a time in the main process: on OGLE-2013-BLG-0341 (cannon, ~225 s per three-lens logp, 112 cores) it ran 12.85 h with 111 cores idle and no line between "probing 62 raw element(s)" and the cancel, and 62 elements x tens of evaluations each cannot fit a 3-day wall serially at all. Each element's bracket+bisect search is a coroutine (`_probe_element_gen`), and `_probe_on_pool` keeps every element's next one or two evaluations in flight at once on a pool forked for that probe pass (`run.py` passes the sampler's `cores` grant and `sampler: eval_timeout:`; so does `polish_rounds` for its between-round probe). Things that look optional and are not:
  - **The pooled and serial probes are BIT-IDENTICAL**, by construction rather than by tolerance: both drive the same coroutine, which asks for its steps in the old serial order, and logp is a pure function of the point. `tests/test_whitening_pool.py` checks it on a toy and on `examples/kelt4`'s RV-only build (scales, anchors, barrier scales, start lp). A change that makes the two paths differ by one ulp has changed the measurement, not the scheduling.
  - **The pool is forked per probe pass, never reused across a rescale.** The whitening lives in `pytensor.shared` variables, which a forked worker holds a COPY of; a pool forked before `set_whitening` probes the old coordinates. The escalation re-probe and the barrier-feedback re-measure each fork their own.
  - **At most one evaluation per worker is in flight**, so the `eval_timeout` clock -- which starts at submit -- times the call and not a queue wait (the `ptde_async` livelock in `samplers/samplers.md` cannot happen here).
  - **The serial path stays** for `cores: 1` and for a cheap logp: below `PROBE_POOL_MIN_LOGP_S` (0.05 s, timed on the start's own evaluation) forking and IPC cost more than they save, unless an `eval_timeout` is set, which always takes the pool since a timeout cannot be enforced in-process. The start's own evaluation stays in-process either way (it is the point the polish already evaluated).
  - **A timed-out element is a FAILED PROBE, and gets exactly that contract**: it keeps its preliminary (declared or propagated) scale, a WARNING names it, and that is all. It is not "flat" -- a flat LOGIT element is booked at the reach and ESCALATED (`_flat_logit_is_clipped`), which here would re-probe the very direction that hung -- so it is kept out of that path, listed under `probe_diagnostics["timed_out"]` instead of `"flat"`, and reported with multiplier 1.0 (the scale it kept), so the startup table does not call it a direction logp ignores. The pool is recycled (a hung worker cannot be killed alone) and every other in-flight evaluation is resubmitted unchanged, so the other elements' results are unaffected.
  - **Progress**: one line per `PROBE_PROGRESS_S` (60 s) of wall clock -- elements done / total, logp evaluations, in flight, elapsed, ETA at the element rate so far -- and a closing total once any line was written. A probe inside one interval logs nothing, which keeps a fast model's log quiet.
  - **The seed ledger shares this machinery** (review 2.6.43): `probe_points` is the multi-center form (elements are `(center, key, i)`), `_probe_elements` its one-center case; the ledger passes its own `label`, element names and timeout sentence. One driver, so a fix to the pool reaches both. See `run.md`.
- Elements whose raw N(0,1) **is** the prior are never rescaled. That is **every non-logit element** -- anything without two finite bounds -- not only the unbounded-with-sigma ones: only on the logit branch is the raw coordinate flat with the whole prior in the Jacobian, so only there is a rescale a pure change of variables. An unbounded element with **no** sigma has prior `N(initval, init_scale)` -- the one place `init_scale` is a posterior term rather than conditioning -- and multiplying it by a probe-measured (i.e. data-measured) factor would make the prior width data-dependent. `build_pymc` warns when it builds one; give the element two finite bounds or a sigma to state the prior yourself. Relatedly, the sanitized `[0, 1]` dummy bounds `build_pymc` feeds the logit branch on non-logit elements are load-bearing: their real `+/-inf` bounds put `-inf + inf*sigmoid` = NaN in the *unselected* branch of the `pt.where`, and only a canonicalization rewrite (not a guarantee) kept it out of the gradient. A flat probe direction (NaN multiplier) keeps its preliminary scale and is flagged after the startup table. A multiplier clipped at one of the probe's limits (preliminary scale off by more than ~6 orders of magnitude too tight or ~14 too loose) is **escalated**: the clipped correction is applied and just those elements are re-probed in the new coordinates, repeating until nothing is clipped (capped at `_MAX_ESCALATION_ROUNDS`, whose exhaustion warns naming the defaults.yaml scale to fix). The reach is a product of rounds, deliberately, so it is not a hardcoded number of orders of magnitude on either side.
- **The too-tight side used to have a third limit, a sampler device rather than a property of the posterior, and it is GONE (review 1.2.9) -- do not bring it back.** `parameter.py` cancelled a raw `N(0,1)` on every logit element with a `+0.5*raw**2` term clipped at `|raw| = 1e4` (the PTDE runaway guard), which put a near-vertical quadratic wall in logp there. For an element whose preliminary scale was too tight by more than ~4 orders the 0.5-nat contour the probe found WAS that wall: the multiplier came back as exactly 1e4, inside the escalation window, so no round ran, no warning fired and the model was left silently under-whitened -- the ob140939 divergence family (review 1.2.1). That was patched by raising the clip to 1e6 for the probe's duration, and the wall stayed in force while sampling. Review 1.2.9 removed the cancellation itself: a logit element's raw coordinate is flat, so there is no wall, nothing to raise and nothing to restore, and the clip marks derive from the probe's own step limits alone (`_CLIP_HI = 0.5 * _WHITEN_MAX_STEP`). One thing the wall did WAS needed: it guaranteed a logit element a contour within reach, so an element too tight by more than one round's reach (~9 orders) measured "the wall", was flagged and escalated. Without it such an element probes FLAT, which on its own would keep the preliminary scale and stop. A logit element is never genuinely flat (its Jacobian prior alone costs 0.5 nats within `|delta lq| ~ 1.5`, see "What flat means" below), so `_flat_logit_is_clipped` books a flat logit probe AT the reach, `_CLIP_HI` reads that as clipped, and escalation runs exactly as before -- driven by a statement about the measurement instead of a term in the density. A flat NON-logit element keeps NaN, because there flat can be real. If a wall ever reappears in raw space, the clip marks must learn about it, or the probe will again report it as a measured scale. The escalation test is on the LATEST measured multiplier, never the cumulative one: after a successful escalation the cumulative is outside the window BY CONSTRUCTION, which is what used to re-probe resolved elements and then call them "still unresolved".
- **Soft-bound barrier steepness is measured too** (`whitening.measure_barrier_scales`): with the model whitened, each barrier-carrying element's natural scale is its quadrature response to unit raw steps — n_sampled+1 forward evals of the parameter transform graphs, replacing the old sympy forward-Jacobian scale pass (deleted). Barrier scales live in a `pytensor.shared` per parameter; a user `bound_scale:` (params.yaml or defaults.yaml, physical units, barrier transition width = 0.01 x scale) pins an element against the measured update — this is the *only* user-facing scale knob left, and unlike the old init_scale it is honestly a posterior choice, not conditioning. If updating the barriers moves the start's logp (a bound is active at the start), `measure_and_whiten` re-measures once against the final barriers — otherwise the probe/barrier feedback is exactly zero.
- The **absolute** whitening + barrier state is persisted to `<prefix>_whitening.json` next to the trace. A reload (`recompute_trace: false` with an existing trace) restores it instead of re-probing — raw draws only decode correctly under the whitening they were sampled with; any model mismatch is detected up front and falls back to a fresh measurement. Physical Deterministics in the idata are unaffected either way. "Up front" means **every** vector the apply step would write: both whitening vectors (not just `scale_logits`, whose lone length check let a bad `gaussian_scales` abort mid-loop after earlier parameters had already been written, and still return True), the **anchor**, and the barrier vector, plus a coverage check that counts **barrier-only** (derived) parameters — barriers are posterior terms, so a file that omits one describes a logp that was never sampled. What must never happen is a partial apply.
- **The file carries the ANCHOR, and that is what the schema version is for** (review 4.3.1). A raw draw decodes through `lower + span*sigmoid(anchor + scale*raw)`, so the anchor is half of what a stored draw *means*. It used to need no recording because it could not move: `set_whitening` left `logit_q_inits` exactly where `build_pymc` put it, so a rebuilt model reproduced it by construction. Since `System.recenter_whitening_anchor` folds the polished start into it, it can, and an unpersisted moving anchor would make a reused trace decode against the wrong center — **silently**, because every number involved stays physically plausible. So `version: 2` adds `logit_q_inits` and the validator requires it; `version: 1` files (scales only) stay readable forever and their absent anchor is a property of that schema rather than a gap to guess at — `tests/fixtures/DC2018_128_whitening.json` is a shipped one, and `test_runaway_logp_regression.py` restores it to give its pinned raw draws their meaning. The exemption is checked in **both** directions: a version-1 file that carries an anchor is refused, because a version-2 file relabelled `1` would otherwise get its anchor ignored while its scales applied, which is the partial apply everything else here refuses. Tests: `tests/test_whitening.py`, `tests/test_whitening_anchor.py`.
- **Fresh run vs trace reuse are different situations and `whitening.prepare_whitening` is where they split** (run.py calls only that). About to *sample*: the whitening is a free choice of coordinates, so it is measured and persisted unconditionally, superseding whatever file was there (the draws it described are about to be superseded too) — that path is correct and must not regress into raising. (`load_whitening`, the warn-and-fall-back loader, is the standalone form of the same policy: it is what a tool restoring a state into a build it is about to sample or probe should call.) About to *decode draws that already exist*: it is a property of those draws, so `restore_whitening_for_trace` restores it and **never re-measures and never writes**. A file that fails validation raises `StaleWhiteningError` (naming the file, the validation reason, and `recompute_trace: true`), exactly as `trace_meta` raises `StaleTraceError` — "whitening can honestly be re-measured" is an argument about a run that is about to sample, not one decoding old draws. A **missing** file is the `trace_meta` unverifiable-fingerprint case, not the stale one: warn, keep the *preliminary* scales, probe nothing (a trace sampled with `measure_scales: false` has no file and the preliminary scales ARE its coordinates), and above all write nothing — a re-measured file would look genuine on the next reload and launder a detected mismatch into a silent one. Physical Deterministics in the idata are unaffected either way; what breaks is everything recomputed from the raw draws (mode labels, the seed ledger, a recomputed lp, model curves drawn at a stored draw). Reproduced on DC2018_128: one dropped barrier entry moved a pinned draw's logp by 575 nats and its lens mass by 1.4%. Tests: `tests/test_whitening.py`, `tests/test_trace_staleness.py`.
- **The posterior is invariant to the scale; the logp's normalization is not.** The raw-space logp of a logit element integrates to `1/(sqrt(2 pi) scale_logit)`, so a log evidence computed straight from the compiled logp moves with every rescale. That constant is computed, not built into the model, and the bridge-sampling lnZ adds it back: `src/exozippy/components/parameter.md`, "The model logp is a prior density only up to a constant".
- User-side `init_scale` (params.yaml) is stripped with a warning; `mkparam` no longer writes it; it is not linkable.

## What "flat" means, and why a wide uniform prior is not flat

A common worry: if a parameter's `init_scale` is tiny against a wide uniform
span, does the probe call it flat, keep that tiny preliminary scale, and leave
the chain unable to cross its own prior? Measured 2026-10-27 (re-measured for
review 1.2.9; the 2026-08-18 numbers differed only in the first row), on a
likelihood-free logit element at the middle of `[0, 10]` (the only logp is the
prior):

| preliminary scale/span | measured multiplier | post-whiten scale/span |
|---|---|---|
| 1e-9  | 3.69e8, in one round | 0.369 |
| 1e-3  | 368  | 0.368 |
| 0.1   | 3.75 | 0.375 |

**A wide uniform direction is never flat, and 0.37 is derivable rather than
tuned.** The natural objection is that a logit element's raw coordinate has no
density of its own, so the raw geometry ought to be flat. It has no density of
its OWN; what it carries is the JACOBIAN. For `val` to be exactly uniform the
raw density must be `|dval/draw|/span = q(1-q)*s`, so the raw-space log
density is `log q + log(1-q)` (plus a constant) -- the standard logistic in
`lq`, peaked at `lq = 0` and going as `-|lq|` in the tails.

That non-flatness IS the uniformity: a uniform density in `val`, pulled back
through a nonlinear map, is a NON-uniform density in `raw`. A flat raw geometry
would mean a non-uniform `val`.

The fixed point follows in closed form. At the peak `log q(1-q) = log(1/4)`;
dropping the probe's 0.5 nats gives `q(1-q) = e^-1.886 = 0.1517`, so `q = 0.8135`
and `|lq| = 1.473`. The contour is therefore at `|raw| = 1.473/s`, and since
`dval/dlq = span/4` at the midpoint (`s = 4*init_scale/span`), whitening drives

    scale/span -> 1.473/4 = 0.368

independent of where it started. Checked against the measurements above:
`s = 4e-3` predicts a multiplier of 368.2 (measured 368) and `s = 0.4` predicts
3.68 (measured 3.75).

`flat_scale=NaN` (so the element keeps its preliminary scale) is therefore
reserved for a genuinely degenerate NON-logit direction (a non-logit element
with no sigma whose likelihood ignores it). It is not the wide-uniform case,
and since review 1.2.9 it is never a logit element's result at all: by the
argument above a logit element that probes flat out to `_WHITEN_MAX_STEP` is
too tight by more than the reach, so `_flat_logit_is_clipped` books it at the
reach and it escalates.

The pathological end resolves by ESCALATION. 1e-9 now resolves in round one
(the reach is ~9 orders, `_WHITEN_MAX_STEP = 1e9`); past that, a flat round
is booked at the reach and the next round measures the rest
(`tests/test_whitening.py` resolves a scale 28 orders too tight in three
escalation rounds). Before review 1.2.9 the binding limit was the probe-time
raw-cancellation clip at 1e6, so the 1e-9 row took two rounds; before review
1.2.1 the same case pinned at the sampling clip (1e4) and stayed 4.6 orders
under-whitened with no warning.
